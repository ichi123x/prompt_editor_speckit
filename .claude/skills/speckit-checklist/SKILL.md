## Checklist Purpose（チェックリストの目的）: 「英語のユニットテスト」

**重要な概念**: チェックリストは**要件記述のためのユニットテスト**です - 特定のドメインにおける要件の品質、明確さ、完全性を検証するものです。

**検証/テストのためではない**:

- ❌ 「ボタンが正しくクリックされることを確認する」ではない
- ❌ 「エラー処理が機能することをテストする」ではない
- ❌ 「APIが200を返すことを確認する」ではない
- ❌ コード/実装がspecと一致しているかどうかを確認するものではない

**要件品質の検証のため**:

- ✅ 「すべてのカードタイプについて視覚的階層の要件が定義されているか?」（完全性）
- ✅ 「'目立つ表示' は具体的なサイズ/配置で定量化されているか?」（明確さ）
- ✅ 「ホバー状態の要件はすべてのインタラクティブ要素間で一貫しているか?」（一貫性）
- ✅ 「キーボードナビゲーションのアクセシビリティ要件は定義されているか?」（カバレッジ）
- ✅ 「ロゴ画像の読み込みに失敗した場合の挙動をspecは定義しているか?」（エッジケース）

**比喩**: あなたのspecが英語で書かれたコードであるなら、チェックリストはそのユニットテストスイートです。実装が動作するかどうかではなく、要件がよく書かれていて、完全で、曖昧さがなく、実装の準備ができているかどうかをテストしているのです。

**所有権とチェックボックスのライフサイクル**:

- このコマンドが生成するカスタムチェックリストは、レビュアーが所有する要件品質レビューの成果物です。
- `[x]` は、レビュアーが要件品質の基準が満たされていると判断したことを意味します。
- `[x]` は実装作業が完了したことを意味しません。
- このコマンドはチェックリスト項目を生成または追加しますが、生成した項目を `[x]` にマークしては**いけません**。
- エージェントが項目の評価を支援するのは、レビュアーから明示的に依頼された場合のみです。
- `checklists/requirements.md` は `/speckit-specify` と `/speckit-clarify` が管理する別のビルトインのspec品質チェックリストです。この例外がここで生成されるカスタムチェックリストにも適用されると考えないでください。

## User Input

```text
$ARGUMENTS
```

ユーザー入力がある場合は、それを検討してから進めなければなりません。

## Pre-Execution Checks（事前実行チェック）

**拡張フックの確認（チェックリスト生成の前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_checklist` キー配下のエントリを探す
- YAMLの解析に失敗する場合や不正な場合は、フックのチェックを黙ってスキップし、通常通り続行する
- `enabled` が明示的に `false` であるフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う
- 残りの各フックについて、フックの `condition` 式を解釈・評価しようとしては**いけない**:
  - フックに `condition` フィールドがない、またはそれが null/空である場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- フックコマンド名からコマンド呼び出しを構築する際は、ドット（`.`）をハイフン（`-`）に置き換える。例: `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに基づいて以下を出力する:
  - **オプションフック** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック** (`optional: false`):
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Execution Steps に進む前にフックコマンドの結果を待つこと。
    ```
    上のブロックを出力した後、実際にそのフックを呼び出し、完了を待ってから続行しなければなりません。このエージェント/セッションで自分自身がコマンドを実行するのと同じ方法で実行してください（呼び出し方法は上記の文字通りの `{command}` id とは異なる場合があります。例えばスキルモードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行されます）。上記のブロックを出力するだけではフックは実行されません。
- フックが登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## Execution Steps（実行手順）

1. **セットアップ**: リポジトリのルートから `.specify/scripts/powershell/check-prerequisites.ps1 -Json -Template checklist-template` を実行し、FEATURE_DIR、AVAILABLE_DOCS のリスト、TEMPLATE_CONTENT のJSONをパースする。
   - すべてのファイルパスは絶対パスでなければならない。
   - "I'm Groot" のような引数中のシングルクォートには、エスケープ構文を使用すること: 例 'I'\''m Groot'（可能であればダブルクォートを使用: "I'm Groot"）。

2. **存在する場合**: プロジェクトの原則とガバナンス制約について `.specify/memory/constitution.md` をロードする。

3. **意図の明確化（動的）**: 最大3つの初期コンテキスト明確化質問を導出する（あらかじめ用意されたカタログはない）。以下を満たさなければならない:
   - ユーザーの言い回し + spec/plan/tasksから抽出したシグナルから生成されること
   - チェックリストの内容を実質的に変える情報のみを尋ねること
   - `$ARGUMENTS` の中ですでに曖昧でない場合は個別にスキップされること
   - 網羅性より精度を優先すること

   生成アルゴリズム:
   1. シグナルを抽出する: フィーチャードメインのキーワード（例: auth、latency、UX、API）、リスク指標（"critical"、"must"、"compliance"）、ステークホルダーのヒント（"QA"、"review"、"security team"）、明示的な成果物（"a11y"、"rollback"、"contracts"）。
   2. シグナルを候補フォーカスエリア（最大4つ）にクラスタリングし、関連度順にランク付けする。
   3. 明示されていない場合、想定される対象読者とタイミング（作者、レビュアー、QA、リリース）を特定する。
   4. 欠けている次元を検出する: スコープの広さ、深さ/厳密さ、リスクの重点、除外境界、測定可能な受け入れ基準。
   5. 以下のアーキタイプから質問を組み立てる:
      - スコープの絞り込み（例: 「これにはXとYとの統合ポイントを含めるべきか、それともローカルモジュールの正しさに限定すべきか?」）
      - リスクの優先順位付け（例: 「これらの潜在的リスク領域のうち、どれに必須のゲーティングチェックを設けるべきか?」）
      - 深さの調整（例: 「これは軽量なプレコミットの健全性チェックリストか、それとも正式なリリースゲートか?」）
      - 対象読者のフレーミング（例: 「これは作者のみが使うのか、それともPRレビュー時に同僚も使うのか?」）
      - 境界の除外（例: 「今回はパフォーマンスチューニング項目を明示的に除外すべきか?」）
      - シナリオクラスのギャップ（例: 「リカバリーフローが検出されていない - ロールバック/部分的な失敗パスはスコープに含まれるか?」）

   質問フォーマットのルール:
   - 選択肢を提示する場合は、Option | Candidate | Why It Matters の列を持つコンパクトなテーブルを生成する
   - 選択肢はA〜Eまでに限定する。自由記述の方が明確な場合はテーブルを省略する
   - ユーザーがすでに言ったことを言い直させない
   - 憶測によるカテゴリを避ける（捏造しない）。不確かな場合は明示的に尋ねる: 「XがスコープにXが含まれるか確認してください」

   対話が不可能な場合のデフォルト:
   - 深さ: Standard
   - 対象読者: コード関連ならレビュアー（PR）、それ以外は作者
   - フォーカス: 関連度上位2クラスタ

   質問を出力する（Q1/Q2/Q3とラベル付け）。回答後: 2つ以上のシナリオクラス（Alternate / Exception / Recovery / Non-Functional ドメイン）が不明なままの場合、それぞれ一行の理由付き（例: 「未解決のリカバリーパスのリスク」）で、さらに2問（Q4/Q5）まで尋ねてもよい。合計5問を超えないこと。ユーザーが明示的にこれ以上の質問を拒否した場合はエスカレーションをスキップする。

4. **ユーザーの要求を理解する**: `$ARGUMENTS` + 明確化の回答を組み合わせる:
   - チェックリストのテーマを導出する（例: security、review、deploy、ux）
   - ユーザーが言及した明示的な必須項目を統合する
   - フォーカスの選択をカテゴリの骨組みにマッピングする
   - spec/plan/tasksから欠けているコンテキストを推測する（捏造しないこと）

5. **フィーチャーコンテキストのロード**: FEATURE_DIR から読み込む:
   - spec.md: フィーチャーの要件とスコープ
   - plan.md（存在する場合）: 技術的詳細、依存関係
   - tasks.md（存在する場合）: 実装タスク

   **コンテキストロード戦略**:
   - アクティブなフォーカスエリアに関連する必要な部分のみをロードする（ファイル全体のダンプを避ける）
   - 長いセクションを簡潔なシナリオ/要件の箇条書きに要約することを優先する
   - プログレッシブ・ディスクロージャーを使用する: ギャップが検出された場合にのみ追加の取得を行う
   - ソースドキュメントが大きい場合は、生テキストを埋め込む代わりに中間サマリー項目を生成する

6. **チェックリストの生成** - TEMPLATE_CONTENT を構造テンプレートとして使用し、「要件のためのユニットテスト」を作成する:
   - `FEATURE_DIR/checklists/` ディレクトリが存在しない場合は作成する
   - 一意のチェックリストファイル名を生成する:
     - ドメインに基づいた短く説明的な名前を使用する（例: `ux.md`、`api.md`、`security.md`）
     - 形式: `[domain].md`
   - ファイル処理の挙動:
     - ファイルが存在**しない**場合: 新規ファイルを作成し、CHK001から項目に番号を振る
     - ファイルが存在する場合: 既存ファイルに新しい項目を追加し、最後のCHK IDから続ける（例: 最後の項目がCHK015なら、新しい項目はCHK016から開始）
   - 既存のチェックリストの内容を削除・置換しない - 常に保持して追加する
   - 新しく生成した項目はすべて未チェック（`[ ]`）のままにする。チェックボックスの状態はレビュアーに属する

   **核となる原則 - 実装ではなく要件をテストする**:
   すべてのチェックリスト項目は、**要件そのもの**を以下の観点で評価しなければならない:
   - **完全性**: 必要な要件はすべて存在しているか?
   - **明確さ**: 要件は曖昧でなく具体的か?
   - **一貫性**: 要件は互いに整合しているか?
   - **測定可能性**: 要件は客観的に検証できるか?
   - **カバレッジ**: すべてのシナリオ/エッジケースに対応しているか?

   **カテゴリ構造** - 要件品質の次元ごとに項目をグループ化する:
   - **要件の完全性**（必要な要件はすべて文書化されているか?）
   - **要件の明確さ**（要件は具体的で曖昧でないか?）
   - **要件の一貫性**（要件は矛盾なく整合しているか?）
   - **受け入れ基準の品質**（成功基準は測定可能か?）
   - **シナリオカバレッジ**（すべてのフロー/ケースに対応しているか?）
   - **エッジケースカバレッジ**（境界条件は定義されているか?）
   - **非機能要件**（パフォーマンス、セキュリティ、アクセシビリティなど - それらは仕様化されているか?）
   - **依存関係と前提事項**（それらは文書化され、検証されているか?）
   - **曖昧さと矛盾**（何を明確にする必要があるか?）

   **チェックリスト項目の書き方 - 「英語のユニットテスト」**:

   ❌ **誤り**（実装をテストしている）:
   - 「ランディングページに3つのエピソードカードが表示されることを確認する」
   - 「デスクトップでホバー状態が機能することをテストする」
   - 「ロゴのクリックでホームに遷移することを確認する」

   ✅ **正しい**（要件品質をテストしている）:
   - 「注目エピソードの正確な数とレイアウトは仕様化されているか?」[完全性]
   - 「'目立つ表示' は具体的なサイズ/配置で定量化されているか?」[明確さ]
   - 「ホバー状態の要件はすべてのインタラクティブ要素間で一貫して定義されているか?」[一貫性]
   - 「すべてのインタラクティブUIについて、キーボードナビゲーションの要件は定義されているか?」[カバレッジ]
   - 「ロゴ画像の読み込みに失敗した場合のフォールバック挙動は仕様化されているか?」[エッジケース]
   - 「非同期のエピソードデータについて、ローディング状態は定義されているか?」[完全性]
   - 「競合するUI要素の視覚的階層をspecは定義しているか?」[明確さ]

   **項目の構造**:
   各項目は以下のパターンに従うべき:
   - 要件品質について尋ねる質問形式
   - spec/planに書かれている（あるいは書かれていない）ことに焦点を当てる
   - 品質の次元を角括弧で含める [Completeness/Clarity/Consistency/etc.]
   - 既存の要件を確認する場合はspecのセクション `[Spec §X.Y]` を参照する
   - 欠けている要件を確認する場合は `[Gap]` マーカーを使用する

   **品質の次元ごとの例**:

   完全性:
   - 「すべてのAPI失敗モードについてエラー処理の要件は定義されているか? [Gap]」
   - 「すべてのインタラクティブ要素についてアクセシビリティの要件は仕様化されているか? [Completeness]」
   - 「レスポンシブレイアウトについてモバイルのブレークポイント要件は定義されているか? [Gap]」

   明確さ:
   - 「'高速な読み込み' は具体的な時間のしきい値で定量化されているか? [Clarity, Spec §NFR-2]」
   - 「'関連エピソード'の選定基準は明示的に定義されているか? [Clarity, Spec §FR-5]」
   - 「'目立つ' は測定可能な視覚的プロパティで定義されているか? [Ambiguity, Spec §FR-4]」

   一貫性:
   - 「ナビゲーションの要件はすべてのページで整合しているか? [Consistency, Spec §FR-10]」
   - 「カードコンポーネントの要件はランディングページと詳細ページで一貫しているか? [Consistency]」

   カバレッジ:
   - 「ゼロ状態のシナリオ（エピソードなし）について要件は定義されているか? [Coverage, Edge Case]」
   - 「同時ユーザー操作のシナリオに対応しているか? [Coverage, Gap]」
   - 「部分的なデータ読み込み失敗について要件は仕様化されているか? [Coverage, Exception Flow]」

   測定可能性:
   - 「視覚的階層の要件は測定可能/テスト可能か? [Acceptance Criteria, Spec §FR-1]」
   - 「'バランスの取れた視覚的ウェイト' は客観的に検証できるか? [Measurability, Spec §FR-2]」

   **シナリオの分類とカバレッジ**（要件品質重視）:
   - 以下について要件が存在するか確認する: Primary、Alternate、Exception/Error、Recovery、Non-Functional のシナリオ
   - 各シナリオクラスについて尋ねる: 「[シナリオタイプ] の要件は完全で、明確で、一貫しているか?」
   - シナリオクラスが欠けている場合: 「[シナリオタイプ] の要件は意図的に除外されているのか、それとも欠落しているのか? [Gap]」
   - 状態変更が発生する場合はレジリエンス/ロールバックを含める: 「マイグレーション失敗のロールバック要件は定義されているか? [Gap]」

   **トレーサビリティの要件**:
   - 最低限: 項目の80%以上が少なくとも1つのトレーサビリティ参照を含まなければならない
   - 各項目はspecのセクション `[Spec §X.Y]`、または `[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]` のマーカーを参照するべき
   - IDシステムが存在しない場合: 「要件と受け入れ基準のIDスキームは確立されているか? [Traceability]」

   **問題の可視化と解決**（要件品質の問題）:
   要件自体について質問する:
   - 曖昧さ: 「'高速' という用語は具体的な指標で定量化されているか? [Ambiguity, Spec §NFR-1]」
   - 矛盾: 「§FR-10と§FR-10aの間でナビゲーション要件は矛盾していないか? [Conflict]」
   - 前提事項: 「'ポッドキャストAPIは常に利用可能' という前提は検証されているか? [Assumption]」
   - 依存関係: 「外部ポッドキャストAPIの要件は文書化されているか? [Dependency, Gap]」
   - 欠けている定義: 「'視覚的階層' は測定可能な基準で定義されているか? [Gap]」

   **内容の統合**:
   - ソフトキャップ: 生の候補項目が40件を超える場合、リスク/影響度で優先順位付けする
   - 同じ要件の側面をチェックしているほぼ重複項目を統合する
   - 影響度の低いエッジケースが5件を超える場合、1つの項目にまとめる: 「エッジケースX、Y、Zは要件に含まれているか? [Coverage]」

   **🚫 絶対禁止** - これらは要件テストではなく実装テストにしてしまう:
   - ❌ 「Verify」「Test」「Confirm」「Check」+ 実装の挙動で始まる項目
   - ❌ コード実行、ユーザー操作、システムの挙動への言及
   - ❌ 「正しく表示される」「正常に動作する」「期待通りに機能する」
   - ❌ 「クリックする」「遷移する」「描画する」「読み込む」「実行する」
   - ❌ テストケース、テストプラン、QA手順
   - ❌ 実装の詳細（フレームワーク、API、アルゴリズム）

   **✅ 必須パターン** - これらは要件品質をテストする:
   - ✅ 「[シナリオ] について [要件タイプ] は定義/仕様化/文書化されているか?」
   - ✅ 「[曖昧な用語] は具体的な基準で定量化/明確化されているか?」
   - ✅ 「[セクションA] と [セクションB] の間で要件は一貫しているか?」
   - ✅ 「[要件] は客観的に測定/検証できるか?」
   - ✅ 「[エッジケース/シナリオ] は要件に含まれているか?」
   - ✅ 「specは [欠けている側面] を定義しているか?」

7. **構造の参照**: タイトル、メタセクション、カテゴリ見出し、所有権の注記、Notesセクション、ID形式について、`.specify/templates/checklist-template.md` の正規テンプレートに従ってチェックリストを生成する。テンプレートが利用できない場合は以下を使用する: H1タイトル、目的/作成日のメタ行、`[x]` がレビュアーによる要件品質の承認を意味することを説明する所有権の注記、CHK001から始まるグローバルに増分するIDを持つ `- [ ] CHK### <requirement item>` 行を含む `##` カテゴリセクション、および `/speckit-implement` はチェックリストの状態を読み取るがマーカーは変更しないという注記。

8. **報告**: チェックリストファイルへのフルパス、項目数を出力し、この実行が新規ファイルを作成したか既存ファイルに追加したかを要約する。以下を要約する:
   - 選択されたフォーカスエリア
   - 深さのレベル
   - 対象読者/タイミング
   - 組み込まれた、ユーザーが明示的に指定した必須項目

**重要**: `/speckit-checklist` コマンドの各呼び出しは、短く説明的なチェックリストファイル名を使用し、新規ファイルを作成するか既存ファイルに追加します。これにより以下が可能になります:

- 異なる種類の複数のチェックリスト（例: `ux.md`、`test.md`、`security.md`）
- チェックリストの目的を示す、シンプルで覚えやすいファイル名
- `checklists/` フォルダ内での簡単な識別とナビゲーション

散らかりを避けるため、説明的な種類を使用し、完了した古いチェックリストは片付けてください。

## Anti-Examples: What NOT To Do（アンチパターン: やってはいけないこと）

**❌ 誤り - これらは要件ではなく実装をテストしている:**

```markdown
- [ ] CHK001 - ランディングページに3つのエピソードカードが表示されることを確認する [Spec §FR-001]
- [ ] CHK002 - デスクトップでホバー状態が正しく機能することをテストする [Spec §FR-003]
- [ ] CHK003 - ロゴのクリックでホームページに遷移することを確認する [Spec §FR-010]
- [ ] CHK004 - 関連エピソードセクションに3〜5件表示されることを確認する [Spec §FR-005]
```

**✅ 正しい - これらは要件品質をテストしている:**

```markdown
- [ ] CHK001 - 注目エピソードの数とレイアウトは明示的に仕様化されているか? [Completeness, Spec §FR-001]
- [ ] CHK002 - すべてのインタラクティブ要素についてホバー状態の要件は一貫して定義されているか? [Consistency, Spec §FR-003]
- [ ] CHK003 - すべてのクリック可能なブランド要素についてナビゲーション要件は明確か? [Clarity, Spec §FR-010]
- [ ] CHK004 - 関連エピソードの選定基準は文書化されているか? [Gap, Spec §FR-005]
- [ ] CHK005 - 非同期のエピソードデータについてローディング状態の要件は定義されているか? [Gap]
- [ ] CHK006 - 「視覚的階層」の要件は客観的に測定できるか? [Measurability, Spec §FR-001]
```

**主な違い:**

- 誤り: システムが正しく動作するかをテストする
- 正しい: 要件が正しく書かれているかをテストする
- 誤り: 挙動の検証
- 正しい: 要件品質の検証
- 誤り: 「それはXをするか?」
- 正しい: 「Xは明確に仕様化されているか?」

## Post-Execution Checks（事後実行チェック）

**拡張フックの確認（チェックリスト生成の後）**:
プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.after_checklist` キー配下のエントリを探す
- YAMLの解析に失敗する場合や不正な場合は、フックのチェックを黙ってスキップし、通常通り続行する
- `enabled` が明示的に `false` であるフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う
- 残りの各フックについて、フックの `condition` 式を解釈・評価しようとしては**いけない**:
  - フックに `condition` フィールドがない、またはそれが null/空である場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- フックコマンド名からコマンド呼び出しを構築する際は、ドット（`.`）をハイフン（`-`）に置き換える。例: `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに基づいて以下を出力する:
  - **オプションフック** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック** (`optional: false`):
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上のブロックを出力した後、実際にそのフックを呼び出し、完了を待ってから続行しなければなりません。このエージェント/セッションで自分自身がコマンドを実行するのと同じ方法で実行してください（呼び出し方法は上記の文字通りの `{command}` id とは異なる場合があります。例えばスキルモードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行されます）。上記のブロックを出力するだけではフックは実行されません。
- フックが登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする
