## User Input

```text
$ARGUMENTS
```

ユーザー入力がある場合は、それを検討してから進めなければなりません。

## Pre-Execution Checks（事前実行チェック）

**拡張フックの確認（明確化の前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_clarify` キー配下のエントリを探す
- YAMLの解析に失敗する場合や不正な場合は、フックのチェックを黙ってスキップし、通常通り続行する
- `enabled` が明示的に `false` であるフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う
- 残りの各フックについて、フックの `condition` 式を解釈・評価しようとしては**いけない**:
  - フックに `condition` フィールドがない、またはそれが null/空である場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- フックコマンド名からコマンド呼び出しを構築する際は、ドット（`.`）をハイフン（`-`）に置き換える。例: `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに基づいて以下を出力する:
  - **オプションフック** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック** (`optional: false`):
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Outline に進む前にフックコマンドの結果を待つこと。
    ```
    上のブロックを出力した後、実際にそのフックを呼び出し、完了を待ってから続行しなければなりません。このエージェント/セッションで自分自身がコマンドを実行するのと同じ方法で実行してください（呼び出し方法は上記の文字通りの `{command}` id とは異なる場合があります。例えばスキルモードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行されます）。上記のブロックを出力するだけではフックは実行されません。
- フックが登録されていない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする

## Outline

目的: アクティブな機能仕様における曖昧さや意思決定の抜けを検出・削減し、明確化の結果をspecファイルに直接記録する。

注記: この明確化ワークフローは `/speckit-plan` を呼び出す**前に**実行され、完了しているべきです。ユーザーが明確化を明示的にスキップすると述べた場合（例: 探索的なスパイク）、進めてもよいが、後続の手戻りリスクが高まることを警告しなければなりません。

実行手順:

1. リポジトリのルートから `.specify/scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly` を**一度だけ**実行する（`--json --paths-only` モード / `-Json -PathsOnly` を組み合わせたもの）。最小限のJSONペイロードフィールドをパースする:
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （任意で将来のチェーンフローのために `IMPL_PLAN`、`TASKS` を取得する。）
   - JSONのパースに失敗した場合は中止し、`/speckit-specify` を再実行するかフィーチャーブランチの環境を確認するようユーザーに指示する。
   - "I'm Groot" のような引数中のシングルクォートには、エスケープ構文を使用すること: 例 'I'\''m Groot'（可能であればダブルクォートを使用: "I'm Groot"）。

2. **存在する場合**: プロジェクトの原則とガバナンス制約について `.specify/memory/constitution.md` をロードする。

3. 現在のspecファイルをロードする。この分類法を使って構造化された曖昧さ・カバレッジのスキャンを行う。各カテゴリについて、状態をマークする: Clear（明確） / Partial（部分的） / Missing（欠落）。優先順位付けに使う内部カバレッジマップを作成する（質問がまったくない場合を除き、生のマップは出力しないこと）。

   機能スコープと挙動:
   - コアとなるユーザーの目標と成功基準
   - 明示的なスコープ外の宣言
   - ユーザーロール/ペルソナの区別

   ドメインとデータモデル:
   - エンティティ、属性、関係
   - 識別子と一意性のルール
   - ライフサイクル/状態遷移
   - データ量/スケールの前提

   インタラクションとUXフロー:
   - 重要なユーザージャーニー/シーケンス
   - エラー/空/読み込み中の状態
   - アクセシビリティやローカライゼーションの注記

   非機能的な品質属性:
   - パフォーマンス（レイテンシ、スループット目標）
   - スケーラビリティ（水平/垂直、限界）
   - 信頼性と可用性（稼働率、リカバリーへの期待）
   - オブザーバビリティ（ログ、メトリクス、トレーシングのシグナル）
   - セキュリティとプライバシー（認証/認可、データ保護、脅威の前提）
   - コンプライアンス/規制上の制約（あれば）

   統合と外部依存関係:
   - 外部サービス/APIと失敗モード
   - データのインポート/エクスポート形式
   - プロトコル/バージョニングの前提

   エッジケースと失敗処理:
   - ネガティブシナリオ
   - レート制限/スロットリング
   - 競合解決（例: 同時編集）

   制約とトレードオフ:
   - 技術的制約（言語、ストレージ、ホスティング）
   - 明示的なトレードオフや却下された代替案

   用語と一貫性:
   - 正規の用語集
   - 避けるべき同義語/非推奨の用語

   完了シグナル:
   - 受け入れ基準のテスト可能性
   - 測定可能な完了の定義（Definition of Done）スタイルの指標

   その他/プレースホルダー:
   - TODOマーカー/未解決の決定事項
   - 定量化を欠く曖昧な形容詞（"堅牢"、"直感的"）

   Partial または Missing の状態にあるカテゴリごとに、以下でない限り候補質問の機会を追加する:
   - 明確化しても実装や検証戦略が実質的に変わらない
   - 情報はプランニングフェーズに先送りする方が良い（内部的にメモする）

4. （内部的に）候補となる明確化質問の優先順位付きキューを生成する（最大5件）。一度にすべては出力しないこと。以下の制約を適用する:
    - セッション全体で合計最大5問。
    - 各質問は以下のいずれかで答えられなければならない:
       - 短い選択式の選択肢（2〜5個の相互排他的な選択肢）、または
       - 一言/短いフレーズの回答（明示的に制約する: 「5語以内で回答してください」）。
    - 回答がアーキテクチャ、データモデリング、タスク分解、テスト設計、UXの挙動、運用準備、コンプライアンス検証に実質的な影響を与える質問のみを含める。
    - カテゴリのカバレッジバランスを確保する: 影響度の最も高い未解決カテゴリを最初にカバーするようにする。1つの高影響領域（例: セキュリティ体制）が未解決なのに、低影響な質問を2つ尋ねることは避ける。
    - すでに答えられている質問、些細なスタイルの好み、またはplanレベルの実行詳細（正しさをブロックしない限り）は除外する。
    - 後続の手戻りリスクを減らす、または受け入れテストの不整合を防ぐ明確化を優先する。
    - 未解決のカテゴリが5を超える場合、（影響度 × 不確実性）のヒューリスティックで上位5つを選ぶ。

5. 逐次的な質問ループ（対話式）:
    - 一度に**ちょうど1問**を提示する。
    - **質問の書き方の品質（選択式・短答式を問わずすべての質問に適用）:**
       - `**Question:**` から始め、`?` で終わる完全な疑問文を続ける。`?` の前の質問文はそれ単体で意味が通らなければならない。
       - トピックラベル、見出し、要件IDをそのまま質問文として使っては**いけない**。例えば `Acceptance device/runtime matrix (FR-023)` は**無効**です - それは質問ではなくラベルです。
       - `?` の後に許される接尾辞は、括弧書きの要件/質問IDのみです。正確な形式: `**Question:** <疑問文>?` または `**Question:** <疑問文>? (FR-023)`。IDを `?` の前に置いてはいけません。またIDだけ（あるいはトピックラベルと合わせて）をプロンプト全体として使ってはいけません。
       - 質問行の直後、推奨案/選択肢の前に、平易な言葉で「なぜ重要か」という一文（受け入れや出荷にとって何が懸かっているか）を追加する。
       - 日常的な言葉遣いを使い、専門用語は同じ文の中で定義される場合のみ導入する。セルフチェック: Spec Kitを知らない読者が、質問行だけを見て答えられなければならない。簡潔なのは問題ないが、暗号のようなラベルは不可。
    - 選択式の質問の場合:
       - **すべての選択肢を分析**し、以下に基づいて**最も適切な選択肢**を判断する:
          - プロジェクトタイプに対するベストプラクティス
          - 類似実装における一般的なパターン
          - リスク低減（セキュリティ、パフォーマンス、保守性）
          - specに見える明示的なプロジェクトの目標や制約との整合性
       - **推奨する選択肢を明確な理由（なぜそれが最良の選択なのかを説明する1〜2文）とともに冒頭に目立つように提示する**。
       - 形式: `**Recommended:** Option [X] - <理由>`
       - その後、すべての選択肢をMarkdownテーブルとして表示する:

       | Option | Description |
       |--------|-------------|
       | A | <選択肢Aの説明> |
       | B | <選択肢Bの説明> |
       | C | <選択肢Cの説明>（必要に応じて最大5つまでD/Eを追加） |
       | Short | 別の短い回答を提供する（5語以内）（自由記述の代替が適切な場合のみ含める） |

       - テーブルの後に追加する: `選択肢の記号（例: "A"）で返信するか、"yes" または "recommended" と言って推奨案を承諾するか、独自の短い回答を提供できます。`
    - 短答式（意味のある離散的な選択肢がない）の場合:
       - ベストプラクティスとコンテキストに基づいた**提案する回答**を提示する。
       - 形式: `**Suggested:** <提案する回答> - <簡単な理由>`
       - その後、以下を出力する: `形式: 短い回答（5語以内）。"yes" または "suggested" と言って提案を承諾するか、独自の回答を提供できます。`
    - ユーザーが回答した後:
       - ユーザーが "yes"、"recommended"、"suggested" のいずれかで返信した場合、先に述べた推奨案/提案を回答として使用する。
       - それ以外の場合は、回答がいずれかの選択肢に対応するか、5語以内の制約に収まるかを検証する。
       - 曖昧な場合は、簡単な曖昧さ解消を求める（カウントは同じ質問のままとし、先には進めない）。
       - 満足のいく回答が得られたら、作業メモリに記録し（まだディスクには書き込まない）、キューの次の質問に進む。
    - 以下の場合、それ以上の質問を止める:
       - 重要な曖昧さがすべて早期に解決された（残りのキュー項目が不要になった）、または
       - ユーザーが完了を示す信号を出した（"done"、"good"、"no more"）、または
       - 5問尋ねた時点に達した。
    - キューにある今後の質問を事前に明かさない。
    - 開始時点で有効な質問が存在しない場合、直ちに重要な曖昧さがないことを報告する。

6. 承諾された各回答の後の統合（インクリメンタルな更新アプローチ）:
    - specのメモリ内表現（開始時に一度ロード）と生のファイル内容の両方を維持する。
    - このセッションで最初に統合する回答について:
       - `## Clarifications` セクションが存在することを確認する（存在しない場合は、specテンプレートに沿った最上位のコンテキスト/概要セクションの直後に作成する）。
       - その下に、まだ存在しなければ今日の日付の `### Session YYYY-MM-DD` サブ見出しを作成する。
    - 承諾直後に箇条書き行を追加する: `- Q: <question> → A: <final answer>`。
    - その後、直ちに最も適切なセクションに明確化を適用する:
       - 機能面の曖昧さ → Functional Requirements の箇条書きを更新または追加する。
       - ユーザーインタラクション/アクターの区別 → User Stories または Actors サブセクション（存在する場合）を、明確化されたロール、制約、シナリオで更新する。
       - データの形状/エンティティ → Data Model を更新する（フィールド、型、関係を追加）、順序は維持し、追加された制約は簡潔に記す。
       - 非機能的な制約 → Success Criteria > Measurable Outcomes に測定可能な基準を追加/修正する（曖昧な形容詞を指標や明示的な目標に変換する）。
       - エッジケース/ネガティブフロー → Edge Cases / Error Handling の下に新しい箇条書きを追加する（テンプレートにそのプレースホルダーがあればそのサブセクションを作成する）。
       - 用語の衝突 → spec全体で用語を正規化する。必要な場合のみ、一度だけ `(formerly referred to as "X")` を追加して元の用語を残す。
    - 明確化によって以前の曖昧な記述が無効になる場合、重複させるのではなくその記述を置き換える。矛盾する古いテキストを残さない。
    - コンテキスト喪失のリスクを最小化するため、統合ごとにspecファイルを保存する（アトミックな上書き）。
    - フォーマットを保持する: 無関係なセクションを並べ替えない。見出し階層はそのまま維持する。
    - 挿入する各明確化は最小限かつテスト可能に保つ（説明的な脱線を避ける）。

7. 検証（各書き込み後および最終パスの後に実施）:
   - Clarifications セッションには、承諾された回答1つにつき正確に1つの箇条書きが含まれている（重複なし）。
   - 尋ねた（承諾された）質問の合計は5問以下。
   - 更新されたセクションに、新しい回答が解決するはずだった曖昧なプレースホルダーが残っていない。
   - 矛盾する以前の記述が残っていない（今では無効な代替選択肢が削除されたことをスキャンする）。
   - Markdown構造が有効であること。許可される新しい見出しは `## Clarifications`、`### Session YYYY-MM-DD` のみ。
   - 用語の一貫性: 更新されたすべてのセクションで同じ正規の用語が使われている。

8. 更新されたspecを `FEATURE_SPEC` に書き戻す。

9. **Spec Quality Checklist の再検証**（存在する場合）:
   - `FEATURE_DIR/checklists/requirements.md` が存在するか確認する。
   - 存在**しない**場合は、このステップを黙ってスキップする。
   - 存在する場合:
     1. チェックリストファイルを読み込む。
     2. すべてのGitHubタスクリストのチェックボックス行を特定する — `- [ ]`、`- [x]`、`- [X]` に一致する行（大文字小文字を区別せず、ネストした項目の先頭空白は許容する）で、コードフェンスの外にあるもの。それ以外の内容（見出し、注記、チェックボックス以外の箇条書き、メタデータ）は無視する。
     3. 各チェックボックス行について、現在のマーカー状態（チェック済みか未チェックか）と項目テキストを、変更前のスナップショットリストに記録する。
     4. **更新後の**spec（ステップ7で保存したばかりのバージョン）に対して、各チェックボックス項目を再評価する。
     5. 各チェックボックス項目について、チェック済み/未チェックの状態が実際に変わった場合にのみ更新する:
        - 項目が今は合格していて、以前は未チェックだった場合: `[ ]` を `[x]` に変更する。
        - 項目が今は不合格で、以前はチェック済みだった場合: `[x]`/`[X]` を `[ ]` に変更する。
        - 状態が変わらない場合: マーカーはそのままにする（見た目上の差分を避けるため、既存の大文字小文字を維持する）。
     6. 更新されたチェックリストファイルを保存する。**状態が変化したチェックボックス行の `[ ]`/`[x]` マーカー部分のみを切り替えること。** それ以外のファイル内容 — 見出し、メタデータ、注記、行の順序、空白 — はノイズの多い差分を避けるため変更しないこと。
     7. 変更前のスナップショットと現在の状態を比較し、Completion Report 用に3つのリストを算出する:
        - **新たに合格したもの**: 未チェックからチェック済みに変わった項目。
        - **後退したもの**: チェック済みから未チェックに変わった項目。
        - **依然として未チェックのもの**: 未チェックのままの項目。
     8. 変更前/変更後の合格数を、チェック済み/合計のチェックボックス項目数として記録する（例: 「12/16 → 15/16 items passing」）。

挙動のルール:

- 意味のある曖昧さが見つからない場合（または想定されるすべての質問が低影響である場合）、次のように応答する: 「正式な明確化に値する重大な曖昧さは検出されませんでした。」そして進めることを提案する。
- specファイルが見つからない場合は、まず `/speckit-specify` を実行するようユーザーに指示する（ここで新しいspecを作成しないこと）。
- 尋ねた質問の合計が5問を絶対に超えないこと（1つの質問に対する明確化の再試行は新しい質問としてカウントしない）。
- 機能的な明確さをブロックしていない限り、憶測による技術スタックの質問は避ける。
- ユーザーの早期終了の合図（"stop"、"done"、"proceed"）を尊重する。
- カバレッジが完全なため質問が1つも出されなかった場合、コンパクトなカバレッジサマリー（すべてのカテゴリがClear）を出力し、その後前進することを提案する。
- 未解決の高影響カテゴリが残ったまま上限に達した場合、それらを理由とともにDeferredとして明示的にフラグする。

優先順位付けのためのコンテキスト: $ARGUMENTS

## Mandatory Post-Execution Hooks（必須の事後実行フック）

**ユーザーに完了を報告する前に、このセクションを完了しなければなりません。**

プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在しない場合、または `hooks.after_clarify` の下にフックが登録されていない場合は、Completion Report にスキップする。
- 存在する場合は読み込み、`hooks.after_clarify` キー配下のエントリを探す。
- YAMLの解析に失敗する場合や不正な場合は、フックのチェックを黙ってスキップし、Completion Report に進む。
- `enabled` が明示的に `false` であるフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残りの各フックについて、フックの `condition` 式を解釈・評価しようとしては**いけない**:
  - フックに `condition` フィールドがない、またはそれが null/空である場合、そのフックは実行可能として扱う
  - フックが空でない `condition` を定義している場合、そのフックはスキップし、条件の評価は HookExecutor の実装に委ねる
- フックコマンド名からコマンド呼び出しを構築する際は、ドット（`.`）をハイフン（`-`）に置き換える。例: `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに基づいて以下を出力する:
  - **必須フック** (`optional: false`) — **必須フックごとに `EXECUTE_COMMAND:` を出力しなければならない**:
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上のブロックを出力した後、実際にそのフックを呼び出し、完了を待ってから続行しなければなりません。このエージェント/セッションで自分自身がコマンドを実行するのと同じ方法で実行してください（呼び出し方法は上記の文字通りの `{command}` id とは異なる場合があります。例えばスキルモードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行されます）。上記のブロックを出力するだけではフックは実行されません。
  - **オプションフック** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
