# prompt_editor_speckit Constitution

## Core Principles（基本原則）

### I. Spec Kit ワークフロー厳守
機能開発は必ず `/speckit-constitution` → `/speckit-specify` → `/speckit-clarify` → `/speckit-plan`
→ `/speckit-tasks` → `/speckit-analyze` / `/speckit-checklist` → `/speckit-implement` の順序で進めなければ
ならない（MUST）。いずれかの段階を飛ばして直接コード実装やビルドに進んではならない。各段階の成果物
（spec.md、plan.md、tasks.md 等）は次段階が読み込む前提の情報源であり、勝手に省略・改変してはならない。
この列挙は**必須の順序**を定めるものであり、使用可能なコマンドの全集合ではない。`/speckit-implement` の
後に残作業を洗い出す `/speckit-converge`、タスクを課題として起票する `/speckit-taskstoissues` なども
必要に応じて用いてよい。`.specify/extensions.yml` にフックが定義されている場合は、各スキルの
Pre/Post-Execution Checks に従って必ず確認しなければならない。

`/speckit-analyze` と `/speckit-checklist` は「/」で並記されているが選択制であり、両方の実施を義務づける
ものではない。機能001〜016はいずれも `/speckit-analyze`（spec/plan/tasksの整合性チェック）と
`/speckit-specify` が自動生成する `checklists/requirements.md` を検証手段として用いており、
`/speckit-checklist`（レビュアー用のカスタムチェックリスト生成）は使用していない。本プロジェクトの規模
では `/speckit-analyze` と組み込みのrequirements.mdチェックリストで十分と判断したためであり、意図的な
省略である。より詳細なレビュー観点（例: セキュリティ、アクセシビリティ）が必要になった場合は
`/speckit-checklist` を追加で用いてよい。
**理由**: 段階を飛ばすと仕様と実装が乖離し、後工程（tasks/implement）が前提とする情報が欠落する。

### II. 日本語での一貫性
リポジトリ内のドキュメント（CLAUDE.md、spec/plan/tasks 等の Spec Kit 成果物）、UI文字列、コメントは
日本語で統一しなければならない（MUST）。既存の `MFCApplication1` の日本語UI・日本語コメントの慣習を
新規追加コードでも踏襲すること。技術用語・識別子（変数名、関数名、コマンド名等）は英語のままでよいが、
説明文・コメント・ドキュメントは日本語を用いる。
**理由**: 既存コードベースとドキュメントが日本語で統一されており、混在は可読性と保守性を損なう。

### III. シンプルさ優先（YAGNI）
`MFCApplication1` はダイアログベースの小規模MFCデスクトップアプリケーションである。現時点で必要とされて
いない抽象化・共通化・将来を見越した拡張ポイントを導入してはならない（MUST NOT）。3行程度の重複コードは、
時期尚早な共通化より許容される。新しい依存関係やレイヤーを追加する場合は、既存の `tasks.md` / `plan.md`
に明記された要求に基づくものでなければならない。

新しい状態・分岐・依存関係を追加する前に、既存の仕組みの意味論を読み解けば同じ要求を満たせないかを確認
しなければならない（MUST）。既存の意味論をそのまま転用できる場合は、新設より転用を優先する。
**理由**: 小規模なデスクトップアプリの規模に対して過剰設計は保守コストを増大させるだけで便益がない。
016（リポジトリ登録トグル）では、既存の依存関係チェック（`StepResult::Skipped` を依存充足として扱う
仕組み）をそのまま読み解いて再利用することで、依存関係グラフ自体の再設計を避けられた。

### IV. 変更の追跡可能性
`MFCApplication1` に対するすべての機能追加・変更は、対応する `specs/<NNN>-<short-name>/spec.md` に遡れ
なければならない（MUST）。spec/plan/tasks を経由しないアドホックな変更は、緊急のバグ修正など明確な例外
理由がない限り行ってはならない。現時点でテストスイートは存在しないため、`tasks.md` と `spec.md` の対応
関係がその代替として変更の妥当性を担保する一次情報源となる。

**FR番号の採番規則**: 機能要件（FR）番号は `FR-<機能番号><連番2桁>` の形式とし、各機能に専用の百番台
（例: 8番目の機能なら FR-801〜FR-899、16番目の機能なら FR-1601〜FR-1699）を割り当てなければならない
（MUST）。機能008以降はこの規則が機能番号とそのまま一致する。機能001〜007は初期に手探りで採番したため
百番台と機能番号が厳密に一致しない箇所がある（例: 006が百番台5と6の両方を使ったため、007は百番台7から
始まる）が、既存specの番号は振り直さない。既存の要件に後から項目を追加する場合は、新しい番号を割り当てる
のではなく `FR-504a` のように英字の接尾辞を付ける（006 FR-504a・FR-505a・FR-507aの前例）。
**理由**: テストによる裏付けがない状態では、仕様との対応関係だけが変更意図を将来検証する手段になる。
採番規則が暗黙のままだと、新しい機能のspecを書くたびに過去のspecを逆引きして推測する必要があり、
機能番号と百番台がずれている001〜007を参照すると誤った採番をしかねない。

### V. 検証は実測に基づく
要件の充足判定・寸法・外部コマンドの挙動・環境の前提は、目視や推測ではなく実測に基づいて判断しなければ
ならない（MUST）。

- 画面表示の判定は、目視ではなく機械的に取得した値（ピクセル・列幅・行数）で行う。
- 「設定ファイルに記述が無い」ことから「その機能が無い」と結論づけてはならない。ビルド済みの成果物や
  実行中のプロセスを確認すること。
- 別の機能で得た測定値を、測定の基準（対象範囲・除外条件）を確かめずに転用してはならない。
- 検査そのものが正しく動くことを確かめなければならない。実装前に実行して意図どおり不合格になること、
  または既に正しい状態に対して合格することを確認する。
- 測れないものは安全側に見積もり、見積もりであることを明記する。検査と実装が同じ見積もりを共有する
  場合は、誤差を吸収する余裕を別枠で確保しなければならない。
- UIコントロールの配置・余白など、数値化はできても「見た目として妥当か」は設計時の見積もりだけでは
  判断しきれない場合がある。この種の判断は、実際にビルドして動かした状態を見て確定してよい（MUST NOT
  ではない）。その結果、設計時に決めた寸法・配置等を実装後に修正することは仕様の手戻りではなく本原則の
  実践であり、変更内容を spec/plan/research 等の該当箇所へ反映することを条件に許容される。

**理由**: 自動テストスイートが存在しないため、検査手順そのものが唯一の品質保証手段である。その検査が
誤っていれば「合格した」という事実は何も保証しない。実際に 001〜014 の開発を通じて、目視判断の誤り・
検査の自己破綻（検査が自身のコメントを拾って不合格になる）・測定基準の取り違え（別機能の値の無検証な
転用）が繰り返し発生した。016では、処理中のラジオボタン無効化やコントロールの余白幅について、計画時の
見積もりでは気づけなかった「実機で見ると過大」という判断を、実際に動かした利用者による確認で修正した。
これは実測に基づく判断がspecそのものより優先されるべき場面であり、頻繁な手戻りを推奨するものではないが、
実機確認の結果を理由に spec/plan を実装後に修正すること自体は本原則が想定する正常な進行である。

## 技術的制約

- `MFCApplication1` は Visual Studio 専用のMFCプロジェクトであり、CMake/Makefile等の代替ビルドシステム
  を導入してはならない（MUST NOT）。ビルドは `msbuild MFCApplication1/MFCApplication1.sln
  -p:Configuration=<Debug|Release> -p:Platform=<x64|x86>` を用いる。`.sln` に渡すプラットフォーム名は
  `x86` であり、`Win32` を渡すと `error MSB4126` で失敗する（2026-09-14 に実測で確認）。`Win32` は
  `.vcxproj` を直接ビルドする場合の名前である。
- Spec Kit 側のスクリプトは PowerShell（`.specify/scripts/powershell/`）のみをサポートする。bash版スクリ
  プトを新規追加してはならない。Windows環境では `.ps1` の実行にBashツールではなくPowerShellツールを使用
  すること。
- 現状このリポジトリには自動テストスイートおよびlint設定が存在しない。導入する場合は、その必要性を対応
  する `spec.md`/`plan.md` に明記すること。

## 所有権・スレッドモデル

この節は、メモリの所有権とスレッドの扱いについて、すべてのコード（人が書くものも AI が書くものも）が守るルールを定める。

### 所有権

**O-1. 生の new / delete は使わない**
- オブジェクトは `std::make_unique` で作る。共有の所有者が必要な場合だけ `std::make_shared` を使う。
- 例外は次の2つに限る。例外を使う場所には、**誰が所有者かをコメントに書く**こと。
  - MFC のモードレスダイアログ（`PostNcDestroy` で `delete this` する型）
  - O-3 のパターンで、PostMessage を通して所有権を渡すとき
- 理由：所有者が型で読めるようにし、delete し忘れ（リーク）と二重 delete を防ぐため。

**O-2. 引数の `T*` / `T&` は借用である**
- 受け取った側は、絶対に delete してはならない。
- 借用したポインタ・参照を、関数を抜けた後まで保存してはならない。スレッドに渡す場合は、渡した側がそのスレッドの終了を待つこと。
- 理由：借用先が先に消えると、ダングリング（消えたものへのアクセス）になるため。

**O-3. スレッド間で所有権を渡すときは unique_ptr と release を使う**
- 送る側：`std::make_unique` で作り、`PostMessage` が**成功した場合のみ** `release()` する。失敗した場合は unique_ptr のまま自動で破棄させる。
- 受ける側：`lParam` から受け取ったポインタは、**すぐに `std::unique_ptr` で受け取り直す**。
- 理由：送信失敗時のリークと、受信側の delete し忘れを防ぐため。

### スレッド

**T-1. UI の部品は UI スレッドだけが触る**
- ワーカースレッドから画面を更新するときは、`PostMessage(HWND, ...)` で UI スレッドに依頼する。
- ワーカースレッドから `SendMessage` を使ってはならない。
- 理由：UI の部品はスレッド親和性を持つため。SendMessage は、UI スレッドがワーカーの終了を待っている場合にデッドロックするため。

**T-2. ワーカースレッドの実行中は、ダイアログを閉じない**
- ワーカースレッドの処理の終了を確認してから、ダイアログを閉じること。
- 例：実行中フラグ（`m_running`）を立て、`OnOK` / `OnCancel` で実行中は閉じないようにする。
- 理由：ワーカーがダイアログ（`this`）を使っている間にダイアログが破棄されると、ダングリングになるため。

**T-3. 2つのスレッドが同じ変数を触るときは保護する**
- 小さい値（フラグ・カウンター）は `std::atomic` を使う。
- 大きいデータ（文字列・コンテナなど）は、優先して共有しない設計を検討する（PostMessage で渡すなど）。共有が必要な場合は `std::mutex` でデータを守る。
- 理由：保護なしの同時アクセスは、データ競合（未定義動作）になるため。

**T-4. ハンドルは、使っているすべてのスレッドが終了してから閉じる**
- `WaitForSingleObject` などで、そのハンドルを使うスレッドの終了を確認してから `CloseHandle` すること。
- 特に `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 付きのジョブは、閉じた瞬間に中のプロセスが強制終了されることに注意する。
- 理由：ハンドルもポインタと同じく借用であり、先に閉じると無効なハンドルへのアクセスになるため。

## 開発ワークフロー

- 新機能は必ず `/speckit-specify` によって作成された `specs/<NNN>-<short-name>/` 配下から開始する。
  機能ディレクトリを手動で作成してはならない。
- `checklists/*.md` は読み取り専用のゲートとして扱う。`/speckit-implement` はチェック未了の項目があれば
  進行前にユーザーへ確認しなければならず、チェックリスト自体を編集してはならない。
- `.specify/memory/constitution.md` の変更は本コマンド（`/speckit-constitution`）経由でのみ行う。他の
  Spec Kit コマンドの実行中に憲法ファイルを書き換えてはならない。
- `spec.md` 冒頭の `**Status**` フィールドは、次の2値のいずれかでなければならない（MUST）:
  - **Draft**: `/speckit-specify` 実行直後から、`/speckit-implement` が完了するまでの状態。
  - **Implemented**: `tasks.md` の**必須タスク**がすべて `[X]` になった状態。「必須タスク」とは、タスクの
    説明文中で「任意」「必須ではない」「利用者の判断に委ねる」等と明記されていない、通常のタスクを指す。
    フォルダ選択ダイアログの自動操作ができないこと（CLAUDE.md記載の既知の制限）に起因して環境依存の
    手動実機確認が「任意」として`tasks.md`に明記されているタスクは、未実施（`[ ]`）のままでもStatusを
    `Implemented`とすることを妨げない。ただしタスク自体のチェック状態を実施していないのに`[X]`へ書き換え
    てはならない（MUST NOT） — 原則V（検証は実測に基づく）に反するため。未実施の任意タスクは`[ ]`のまま
    残し、いつでも実施状況を追跡できるようにする。
  `/speckit-implement` の完了報告時に、この値を `Implemented` へ更新することを次の実装から徹底する。

## Governance（ガバナンス）

本憲法はこのリポジトリにおける他のすべての開発慣行・ガイダンスに優先する。CLAUDE.md や各 `SKILL.md` の
記述が本憲法と矛盾する場合は、本憲法を優先し、矛盾箇所は発見次第修正しなければならない。ただし本憲法の
記述自体が事実と異なることが実測で判明した場合は、原則Vに従い、本憲法の側を訂正する。

- **改訂手続き**: 憲法の変更は `/speckit-constitution` を通じてのみ行う。変更内容は必ずファイル冒頭の
  Sync Impact Report に記録する。
- **バージョニングポリシー**: セマンティックバージョニングに従う。
  - MAJOR: 既存原則の後方互換性のない削除・再定義。
  - MINOR: 新しい原則・セクションの追加、ガイダンスの実質的拡張。
  - PATCH: 文言の明確化・誤字修正・非意味論的な改善。
- **コンプライアンスレビュー**: `/speckit-plan` の憲法ゲートおよび `/speckit-analyze` の整合性チェックに
  おいて、本憲法の原則との矛盾がないかを確認しなければならない（MUST）。矛盾が見つかった場合は、実装を
  進める前に spec/plan を修正するか、本憲法の改訂を検討する。
