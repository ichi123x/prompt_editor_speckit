# Phase 0 Research: 完了案内にCLAUDE.mdのコミット手順を追加する

**Feature**: [spec.md](./spec.md) | **Date**: 2026-09-13

## R-1201: 挿入位置と文言

**現状の確認**: `MFCApplication1Dlg.cpp`の`ShowCompletionGuide()`（[MFCApplication1Dlg.cpp:585](../../MFCApplication1/MFCApplication1Dlg.cpp#L585)）の成功時の案内は次のとおり。

```text
Spec Kit の導入が完了しました。次の手順は Claude Code との対話が必要です。
 1. VS Code で %s を開く（.specify と .claude が直下に見えるフォルダ）
 2. Claude パネルで /init を実行し、CLAUDE.md を生成する
 3. テスト方針を決め、/speckit-constitution で憲章を制定する
 4. /init を再実行し、憲章を反映した CLAUDE.md に更新する
```

利用者提供の導入手順書（SpecKitVSCodesetup.pdf）の手順08は、`/init`実行の直後に次を行うとしている。

```text
git add -A
git commit -m "CLAUDE.md を追加"
```

**Decision**: 現行の手順2（`/init`実行）と手順3（テスト方針決定）の間に、次の手順を追加し、以降の
番号を1つずつ繰り下げる。

```text
Spec Kit の導入が完了しました。次の手順は Claude Code との対話が必要です。
 1. VS Code で %s を開く（.specify と .claude が直下に見えるフォルダ）
 2. Claude パネルで /init を実行し、CLAUDE.md を生成する
 3. 生成された CLAUDE.md をコミットする（git add -A / git commit -m "CLAUDE.md を追加"）
 4. テスト方針を決め、/speckit-constitution で憲章を制定する
 5. /init を再実行し、憲章を反映した CLAUDE.md に更新する
```

**Rationale**:
- 挿入位置は導入手順書の順序（手順08の直後）とそのまま一致させる。案内文の手順番号と実際に
  行うべき作業の順序を一致させることが目的であり、番号を振り直すこと自体に副作用はない
- コミットコマンドの表記（`git add -A` / `git commit -m "..."`）は、導入手順書の表記、および本アプリ
  自身の結果一覧に表示される既存のGit操作の説明（`SetupRunner.cpp`の`RunInitGit`が使う`git add -A`・
  `git commit -m "Spec Kit 導入"`という表記）と一貫性を保つ（FR-1204）
- 既存の手順1・2・4・5（振り直し後）の文言は一切変更しない。挿入は1行追加するだけであり、
  `guide.Format`の引数（`m_workerPath`）の埋め込み方法にも影響しない

**Alternatives considered**:
- コミット手順を独立した注記として末尾に追加する（番号を振り直さない）: 導入手順書の時系列
  （`/init`の直後にコミットする）と案内文中の見た目の順序が一致しなくなり、ユーザーが読み違える
  リスクがある。番号を振り直す方が実際の作業順序に忠実であるため採用しない理由がない
- コミットメッセージの文言を独自に考案する: 導入手順書がすでに具体的な文言（`"CLAUDE.md を追加"`）
  を示しており、それに倣うのが最も一貫性が高く、新たな検討コストもかからない

## R-1202: 案内欄の高さ調整（`/speckit-analyze`での指摘を受けて追加）

**発見の経緯**: `/speckit-analyze`が、006（起動直後のまま結果と案内が読める）のFR-507aを次のように
引用して指摘した。「案内欄の表示行数 | 完了案内5行+折り返し1回=6行 | 6行（クライアント87px）| **余裕0行**」
「メッセージを1文字でも長くする、あるいは**案内を1行増やす変更は、そのままでは表示が切れる**。
文言を足す前にこの表を確認すること。」本フィーチャーは完了案内を5行（見出し+手順4）から6行
（見出し+手順5）に増やすため、`.rc`側の調整なしに文字列だけを変更すると、006が保証したFR-504
（5行すべてが同時に見える）が壊れ、追加した新しい手順自体が見切れる可能性が高いことが判明した。

**Decision**: `MFCApplication1.rc`の`IDC_STATIC_GUIDE`（現行 高さ52 DLU）を**61 DLU**に拡張する。
これに伴い、006 R-507の前例（案内欄の高さの差分がそのままダイアログの高さに乗る）に従い、
`IDOK`・`IDCANCEL`のY座標を203→212に、ダイアログ全体の高さを224→233 DLUに変更する。

**算出根拠**:

1. 006 FR-507aの実測値により、現在の案内欄はクライアント高さ87 pxで6行（見出し+手順4行+折り返し1回）を
   表示しており、1行あたり **87 ÷ 6 = 14.5 px**
2. 本フィーチャーで必要な行数は7行（見出し+手順5行+折り返し1回）。必要なクライアント高さは
   `14.5 × 7 = 101.5px`。7行目が欠けないよう切り上げて **102 px**
3. 現在のコントロール高さ（52 DLU）は、CLAUDE.mdの換算式（1 DLU = 1.75px、四捨五入、実測115 DPI）で
   `52 × 1.75 = 91px`。クライアント87 pxとの差である**4px**が、エディットコントロールの枠・内部余白
   （実測できないため見積もり、006 R-505と同じ性質の推定値）
4. 必要なコントロール高さ: `102 + 4 = 106px`。DLUへの変換は最小限必要な値を保証するため**切り上げ**で
   `106 ÷ 1.75 = 60.57 → 61 DLU`
5. **交差検証**: 006自身が「案内欄を28→52 DLU」（研究文書 R-507）に拡張した際の増分は24 DLUで、
   これは3行相当の増加に対応する。24 ÷ 3 ≈ 8 DLU/行であり、本フィーチャーで算出した増分
   `61 - 52 = 9 DLU`（1行分）とほぼ整合する。独立した2つの算出方法が近い値を示しており、
   61 DLUという見積もりの妥当性を裏付ける

**この数値は見積もりであり、実装後に実機で確認する必要がある**（コントロールの内部余白が実測でき
ないという006 R-505と同じ制約による）。[quickstart.md](./quickstart.md) のDT-1201で、実際に7行すべて
がスクロールなしで表示されることを目視確認する。

**Rationale**:
- 006が確立した「1行あたりの表示高さ」という実測値を再利用することで、フォントを再計測する
  手間を省きつつ、同じ精度の算出根拠を維持できる
- 差分（9 DLU）をダイアログ全体の高さとボタンのY座標にそのまま反映する方法は、006 R-507で
  既に採用され検証済みの手法であり、新しい計算方法を考案する必要がない
- 006 FR-506（1024x768の作業領域に収まること）への影響は軽微。006時点でウィンドウ高さ437 pxに
  対し余裕291 pxがあり、本フィーチャーによる増加分（9 DLU ≈ 16px）を加えても大幅な余裕が残る

**Alternatives considered**:
- 新しい手順を独立した行にせず、既存の行（例: 手順2の`/init`実行の説明）に追記して行数を増やさない:
  1行の文字数が大きく伸び、006 FR-504aが警告する「折り返しが2回以上必要になるほど極端に長い」
  状態に近づくリスクがあり、かつ「`/init`実行」と「コミット」という異なる操作を1行に混在させると
  可読性が下がる。原則III（YAGNI）よりも006が優先したユーザー体験（FR-501「利用者が何もしなくても
  読める」の精神）を優先し、新しい行として追加する方針を採る
- 案内欄の高さを変えず、フォントサイズを縮小する: 006 Assumptions「文字の大きさは変更しない」と
  正面から矛盾するため却下
- 正確な行送り高さをGDIで再計測する: 006と同じ環境・同じフォント（MS UI Gothic 9pt）であり、
  既存の実測値（87px/6行）を再利用する方が、再計測の手間なく同等の精度を得られる。ただし本フィーチャー
  の算出値はあくまで見積もりであるため、実装後の実機確認（DT-1201）を必須とする
