## Phase 3: User Story 1 - 結果の説明を最後まで読む (Priority: P1) 🎯 MVP

**独立したテスト**: アプリを起動し、ウィンドウのサイズも列幅も変えずに、3列の幅がそれぞれの最長文字列 + 余白 20 px + 余裕 8 px 以上であることを計測して確認する

- [ ] T004 [US1] `MFCApplication1/MFCApplication1Dlg.cpp` の `kColumnRatio` のコメントに、変更の根拠を記載する（FR-513）。**`.rc` にはコメントを書けないため、寸法変更の根拠もここに集約する** — 対応する FR 番号（FR-501、FR-502、FR-504、FR-506、FR-509）と、比率を変えずに幅だけ広げる案が成立しない理由（40/20/40 のままでは一覧幅が 1430 px 必要になり FR-506 の 1024 px 制約を超える）を書く。**旧比率 `{ 40, 20, 40 }` をコメント中に書かないこと** — ST-502 が旧比率の残存を検出する検査であり、コメントに書くと誤検出する（005 の ST-402 で同じ失敗をした）。T003 に依存

### User Story 1 の検証

- [ ] T005 [US1] [quickstart.md](./quickstart.md) 手順2の **ST-501**（`.rc` の寸法）と **ST-502**（列幅の比率）を実施する。ST-501 は7項目すべて一致し**コントロール行数が 8**（FR-510）、ST-502 は新比率が1件・旧比率が0件・**定義箇所が1つだけ**・参照が **5件** であること。**ST-501 の照合は空白の数に依存しない正規表現で行う** — 実際の `.rc` は `DIALOGEX` の後に空白が2つあり、完全一致では正しい実装でも落ちる（analyze B1）。T004 に依存

## Dependencies & Execution Order（依存関係と実行順序）

### Phase Dependencies（フェーズの依存関係）

- **Setup (Phase 1)**: **T001 は実装を始める前に必ず実施する** — 実装後では 004・005 のベースラインが取れなくなる
- **Foundational (Phase 2)**: T001 の後。US1・US2 の両方をブロックする
- **User Story 1 (Phase 3)**: Foundational の後
- **User Story 2 (Phase 4)**: Foundational の後。T008 は T002 と同一ファイル（`.rc`）のため逐次に行う
- **Polish (Phase 5)**: 両ストーリーの完了後

### 重要な順序

| タスク | 依存 | 理由 |
|---|---|---|
| T001（ベースライン取得） | — | **実装前でなければ意味がない** |
| T008（`.rc` の縦方向） | T002 | 同一ファイルの別箇所。同時に編集すると競合する |
| T010（ST-503） | T001 | T001 で控えた値と突き合わせる |
| T013（DT-505） | T009、T012 | 新しい初期サイズが確定してから回帰を測る |
| T016（通し確認） | T010〜T015 | 全検証が揃った状態で実施する |

### Parallel Opportunities（並行実行の機会）

- **Phase 2・4**: T002 と T008 は同一ファイルのため**並行不可**
- **Phase 3**: T005・T006 は互いに独立（T004 の後）

## Implementation Strategy（実装戦略）

### MVP First（User Story 1 のみ）

1. Phase 1: T001（**実装前のベースライン取得**）
2. Phase 2: T002（`.rc` の幅）
3. Phase 3: T003〜T007（比率の変更と検証）
4. **停止して検証**: T007（列幅 ≧ 必要幅）を必ず通すこと

### 実装順序に関する注意

- **T001 を飛ばさない。** 実装後に 004・005 のカウントを取っても「元からその値だったか」が分からず、ST-503 が意味を失う
- **T002 と T008 を1つのタスクにまとめない。** どちらも `.rc` を触るが、幅は両ストーリーの前提、高さは US2 固有である。分けておくと、US1 だけを先に完成させて検証できる
- **T004 のコメントに旧比率を書かない。** ST-502 が `{ 40, 20, 40 }` の残存を検出する検査であり、コメントに書くと自分で自分を落とす
- **T007 で `LVM_GETSTRINGWIDTH` を使わない。** アプリが異常終了する。R-503 に失敗の記録がある
- **T007 の余裕 8 px を削らない。** 余白 20 px は見積もりであり、検査と実装が同じ値を使うため、余裕が無いと見積もり誤りを検出できない
- **T005 の ST-501 を文字列の完全一致で書かない。** `.rc` は `DIALOGEX` の後に空白が2つある
- **T013 で 004 の期待値を流用しない。** 初期サイズが変わったため、004 の実測値（578 x 395 など）はもう正しくない

### Incremental Delivery（段階的な提供）

1. Setup + Foundational → ダイアログが広がる
2. User Story 1 → 結果の内容が全文読める（**MVP**）
3. User Story 2 → 完了案内が5行とも見える
4. Phase 5 → 004・005 の回帰確認、コード分析、通し確認
