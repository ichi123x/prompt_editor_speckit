# Implementation Plan: 起動直後のまま結果と案内が読める

## Summary（概要）

ダイアログを **320 x 200 → 545 x 216 DLU**（ウィンドウ 578 x 395 → **971 x 423 px**）に広げ、結果一覧の列幅比率を **40/20/40 → 20/17/63** に変える。これにより、起動直後の大きさのまま「内容」欄の全メッセージ（最長 552 px）が読め、完了案内の5行が折り返しもスクロールもなしに表示される。

**コードの変更は `kColumnRatio` の1行のみ**で、残りは `.rc` の座標である。004 は初期矩形を実行時に読み、最小サイズも実行時のウィンドウサイズから取る設計のため、**004・005 のコードには一切手を入れない**。

比率の見直しが要点である。現行の 40/20/40 は「項目」列に必要（173 px）の 2 倍以上を割り当てており、比率を変えずに幅だけ広げると一覧幅が 1430 px 必要になって 1024 px の制約を満たせない。

## 実装方針の要点

1. **`.rc` は UTF-16LE BOM 付き**である。PowerShell で編集する場合は `[System.Text.Encoding]::Unicode` で読み書きする（CLAUDE.md 既出）。エンコーディングを壊すとリソースコンパイルが通らない

2. **隙間の値を保つ。** 左右余白 7 DLU、パス欄と参照の 6 DLU、OK とキャンセルの 4 DLU、案内欄下端とボタンの 4 DLU、ボタン下端とダイアログ下端の 7 DLU。[data-model.md](./data-model.md) 3章に検算を載せてある

3. **`kColumnRatio` の定義は1箇所のままにする。** 004 FR-308 の契約であり、初期化時と再配置時の両方がこれを参照する。値を変えるだけで両方に効く。ST-502 が定義箇所が1つであることを検査する

4. **004・005 のコードに触らない。** 触る必要が無いことを R-509 で確認済みである。ST-503 が 004・005 のキーワード11件の出現数を実装前後で突き合わせる

5. **メッセージの文言を短くして解決しない**（FR-511）。「読める幅を確保する」のが本フィーチャーであり、文言を削るのは別の判断である

6. **列幅の検査でコメント行を除外する。** 経緯として旧比率 `{40,20,40}` に言及するコメントを書くと、検査がそれを拾って誤検出する。005 の ST-402 で実際に起きた

## 見落としやすい点（Phase 0 で判明したもの）

| 事実 | 影響 |
|---|---|
| **「内容」欄の最長は失敗時ではなく完了時のメッセージ**（552 px） | 単独の文字列リテラルを測るだけでは最長を見落とす。`Git初期化はスキップ。` が前に連結される（[research.md](./research.md) R-504） |
| **案内欄はスクロールバーが常に 20 px を占める** | 文字が使える幅はウィンドウ幅 − 24 px。幅の計算で忘れやすい（R-502） |
| **現在の案内欄では折り返しが起きている** | 初期案内は論理2行だが表示3行。幅を広げると折り返しが消え、高さの計算が単純になる（R-507） |
| **`LVM_GETSTRINGWIDTH` は使えない** | クロスプロセスではアプリが異常終了し、自プロセスでも ASCII 混在で過小な値を返す。`TextRenderer.MeasureText` を使う（R-503） |

## 未解決のリスク

**列の内部余白を実測できていない。** `LVM_GETSTRINGWIDTH` が使えず（R-503）、描画結果から余白だけを分離する手段も見つからなかったため、**20 px という見積もり**を置いている。

**この見積もりは検査と実装の両方が共有する。** したがって見積もりが誤っていても DT-503 は通ってしまい、「テストは合格したのに画面では切れている」という状態になりうる。`/speckit-analyze` の B3 で指摘された、本フィーチャーで最も気づきにくい失敗の形である。

**対策として 8 px 以上の余裕を要求している**（実際の余裕は 12 / 11 / 10 px）。実際の余白が 20 px を超えていても 28 px までは吸収できる。それでも足りない場合は T016 の通し確認で目に見える形で現れる。

これ以外に未解決の項目は無い。すべての数値が実測から確定している。
