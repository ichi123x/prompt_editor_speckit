# Feature Specification: 準備状況の診断機能の廃止

**Feature Branch**: `ver.0.2`

**Created**: 2026-09-08

**Status**: Implemented

**Input**: User description: "準備状況のボタンと機能は不要です。"

## 背景と、001・002 との関係

フィーチャー 001（[SDDプロジェクトのベース作成ツール](../001-sdd-project-bootstrap/spec.md)）では、「準備状況を診断」ボタンと、準備完了チェックリスト7項目の判定機能を実装した。本フィーチャーはこれを**廃止**する。

判定した7項目のうち、機械的に断定できたのは3項目（足場の有無、コミット件数、憲章のプレースホルダー）にとどまり、残る4項目は「判定不能」または時刻に基づく参考判定であった。本ツールの中心的な価値は「配置済みプロジェクトをSDD化すること」であり、その後の準備状況を評価することは役割の外にある。憲章の制定状況や CLAUDE.md の妥当性は、`/speckit-constitution` や `/init` を実行する Claude Code 自身が判断できる。

本フィーチャーが廃止する 001 の要件は次のとおり。

| 001 の要件 | 内容 | 本フィーチャーでの扱い |
|---|---|---|
| FR-017 | 診断ボタンの提供 | **廃止** |
| FR-018 | 7項目の判定 | **廃止** |
| FR-019 | 未達項目への次の行動の表示 | **廃止** |
| FR-020 | 診断は読み取り専用 | **廃止**（診断そのものが無くなるため） |
| FR-021 | 判定不能を未達と区別する | **廃止**（同上） |
| FR-022 | 自動実行できない工程の手順案内 | **廃止**（診断結果を入力とするため成立しない） |

**廃止しない機能**: SDD化の5手順の実行と結果表示、べき等性、入れ子リポジトリの警告、書き込み権限の確認、実行中のコントロール無効化、未コミット変更を巻き込まないステージング、そして**「生成」完了後に表示される定型の完了案内**。完了案内は診断結果に依存せず、002 の FR-110〜112 で読みやすさとコピー可能性を確保したばかりであり、SDD化の次に何をすべきかを伝える唯一の手段として残す。

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - SDD化だけに専念した画面で操作する (Priority: P1)

開発者がツールを開くと、画面には「対象フォルダの選択」と「生成」しかない。診断ボタンも準備状況の一覧も存在しない。フォルダを選んで「生成」を押すという一本道だけが提示されるため、何をすべきか迷う余地がない。

**Why this priority（この優先度である理由）**: 本フィーチャーの目的そのものである。ツールの役割を「配置済みプロジェクトをSDD化する」一点に絞り、それ以外の機能を画面から消す。

**Independent Test（独立したテスト方法）**: アプリを起動して画面上に診断ボタンが存在しないことを確認し、`C:\work\test\test01` を選んで「生成」を押してSDD化が完走することを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） ダイアログが表示されている、**When**（動作） ユーザーが画面を確認する、**Then**（結果） 準備状況を診断するボタンやその他の診断手段が画面上に存在しない。
2. **Given**（前提） プロジェクトが配置済みのフォルダを選択している、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 5手順が実行され、結果が一覧表示される。診断機能の廃止によって影響を受けない。
3. **Given**（前提） フォルダが選択されていない、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 先にフォルダを選択するよう促すメッセージが表示され、いかなるファイルも作成・変更されない。
4. **Given**（前提） 診断ボタンを削除した後の画面である、**When**（動作） ユーザーが画面を見る、**Then**（結果） 削除によって生じた空白がそのまま残っておらず、レイアウトが崩れていない。

---

### User Story 2 - 生成後の案内は引き続き表示される (Priority: P2)

「生成」が完了すると、開発者は次に何をすべきか（VS Code でフォルダを開き、`/init` を実行し、`/speckit-constitution` で憲章を制定する）を画面下の案内欄で読める。この案内は診断機能の廃止後も変わらず表示され、選択してコピーできる。

**Why this priority（この優先度である理由）**: 診断機能を消す作業の巻き添えで、完了案内まで失われる危険がある。完了案内は診断結果に依存せず、SDD化の次に何をすべきかを伝える唯一の手段であり、002 で読みやすさとコピー可能性を確保したばかりである。失ってはならない。

**Independent Test（独立したテスト方法）**: 「生成」を実行した後、案内欄に5行の定型メッセージが表示され、末尾まで読めてコピーできることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） SDD化が完了した、**When**（動作） ユーザーが案内欄を見る、**Then**（結果） VS Code でフォルダを開き `/init` を実行する手順が表示されている。
2. **Given**（前提） 案内が表示されている、**When**（動作） ユーザーが案内文をドラッグ選択してコピーする、**Then**（結果） 表示どおりの内容がコピーされる。
3. **Given**（前提） アプリを起動した直後である、**When**（動作） ユーザーが案内欄を見る、**Then**（結果） フォルダを選んで「生成」を押すよう促す初期案内が表示されている。診断への言及が含まれていない。

---

### Edge Cases（エッジケース）

- 診断ボタンの削除によって生じた空白をそのまま残してはならない。未完成に見えるため、残るコントロールの配置を調整する。
- 実行中に無効化するコントロールの一覧から診断ボタンを取り除く際、**生成ボタンと参照ボタンを巻き添えで外してはならない**。参照ボタンの無効化は 001 の analyze で HIGH として指摘し追加した項目である。
- 結果一覧は診断結果と手順結果の双方が共用していた。診断が無くなっても、手順結果の表示は変わってはならない。
- 診断のためだけに存在していた処理（憲章ファイルの読み取り、CLAUDE.md の更新時刻の比較など）が、参照されないまま残ってはならない。

### テスト方針

001・002 と同じく、静的テスト（アプリケーションを実行せずに行う検査）と動的テスト（ダイアログを操作して行う検査）の2層で検証する。本フィーチャーは 002 と同様に**削除**が中心であり、**回帰の検出**に重点を置く。

#### 静的テスト

- **ST-201 UIリソースの検査**: ダイアログのリソース定義から診断ボタンが削除されていること。残るコントロールのIDとタブ順序が整合していること。
- **ST-202 未使用コードの検査**: 診断のためだけに存在していた定義・関数・ファイル・メッセージ文字列が残っていないこと。参照されないコードを残さない。
- **ST-203 コンパイラ警告の検査**: 全構成のビルドが、本変更に起因する警告（未使用変数・未使用関数など）を出さずに完了すること。
- **ST-204 完了案内の残存検査**: 完了時の定型案内を生成する処理と、その文字列が**削除されていない**ことを確認する。
- **ST-205 仕様と実装の対応の検査**: 本フィーチャーで変更した各箇所が、どの機能要件に対応するかをコード上で追跡できること。
- **ST-206 コミット判定文字列の検査**: コミットの結果判定に用いる文字列が、Git が実際に出力する文言と一致していることを確認する。実際の出力を採取して突き合わせ、推測に基づく文字列が残っていないことを検査する（FR-210、FR-211）。

#### 動的テスト

対象フォルダは `C:\work\test\test01` を用いる。

| No. | 検証内容 | 対応する受け入れシナリオ |
|---|---|---|
| DT-201 | 画面に診断ボタンが存在しない | US1-1 |
| DT-202 | 削除による空白が残っておらず、レイアウトが崩れていない | US1-4 |
| DT-203 | SDD化が完走する（回帰確認） | US1-2 |
| DT-204 | フォルダ未選択で「生成」を押下する（回帰確認） | US1-3 |
| DT-205 | 完了後の案内が5行すべて読め、コピーできる（回帰確認） | US2-1, US2-2 |
| DT-206 | 初期案内に診断への言及が無い | US2-3 |
| DT-207 | 実行中に生成ボタンと参照ボタンが無効化される（回帰確認） | Edge Case |
| DT-208 | 再実行で全手順が「スキップ」になる（回帰確認） | 001 FR-013 |
| DT-209 | コミット対象が無いとき Git 手順が「スキップ」と表示される | FR-210 |

**回帰確認が5件を占める理由**: 本フィーチャーは既存の実装からコードとコントロールを取り除く作業であり、削除の巻き添えで既存機能が壊れる危険が主リスクである。特に DT-207 は、無効化するコントロールの一覧から診断ボタンを取り除く際に、生成ボタンや参照ボタンまで巻き添えで外してしまう誤りを検出する。DT-205 は、002 で修正したばかりの完了案内が失われていないことを確認する。

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

- **FR-201**: システムはダイアログから準備状況を診断するボタンを削除しなければならない。画面上に準備状況を診断する手段が存在してはならない。
- **FR-202**: システムは準備完了チェックリスト7項目の判定機能を削除しなければならない。判定結果を表す状態、項目の定義、判定処理のいずれも残してはならない。
- **FR-203**: システムは診断結果に基づく手順案内（自動実行できない工程を完了状況付きで提示する機能）を削除しなければならない。
- **FR-204**: システムは、診断のためだけに存在していたコード・ファイル・メッセージ文字列を残してはならない。憲章ファイルの読み取り、CLAUDE.md の更新時刻の比較、プレースホルダーの検出など、診断以外から参照されない処理を含む。
- **FR-205**: システムは「生成」完了後の定型の完了案内を**引き続き表示しなければならない**。この案内は診断結果に依存せず、内容も 001 から変更しない。
- **FR-206**: システムは初期表示の案内から、診断への言及があればこれを取り除かなければならない。
- **FR-207**: システムは、以下の機能の動作を変更してはならない — 5手順の実行と結果表示、べき等性、入れ子リポジトリの警告、書き込み権限の確認、未選択時のガード、実行中のコントロール無効化、未コミット変更を巻き込まないステージング、`.gitignore` の生成と追記。
- **FR-208**: 診断ボタンを削除した後、残るコントロールの配置に不自然な空白が残ってはならない。ラベルとコントロールの対応関係、およびタブ順序が正しく保たれなければならない。
- **FR-209**: システムは実行中に無効化するコントロールから診断ボタンを取り除かなければならない。**生成ボタンと参照ボタンは引き続き無効化の対象として残さなければならない。**

**コミット対象が無いときの結果表示の修正（002 の手動テストで発見）**

- **FR-210**: Git 手順において、コミットすべき変更が存在しないためにコミットが行われなかった場合、システムはその手順を**「失敗」ではなく「スキップ」として表示**しなければならない。データは何も壊れておらず、ユーザーが対処すべきことも無いため、失敗として示すのは誤りである。
- **FR-211**: システムがコミットの結果を判定する際に用いる文字列は、Git が実際に出力する文言と一致していなければならない。推測に基づく部分文字列を用いてはならない。

### Key Entities（主要エンティティ）

- **準備完了チェック項目**: 001 で定義した7項目の判定結果を表す構造。本フィーチャーで**完全に削除する**。項目名・完了条件・判定結果・次に取るべき行動のいずれも保持しない。
- **対象プロジェクトフォルダ**: 001・002 で定義した構造。診断が参照していた情報（足場の有無、コミット件数）は SDD化の手順判定でも使うため、**構造そのものは変更しない**。

## Success Criteria（成功基準） *(必須)*

### Measurable Outcomes（測定可能な成果）

- **SC-201**: 画面上の操作可能なコントロールが、フォルダ選択・参照・生成の**3つだけ**になる（OK / キャンセルを除く）。
- **SC-202**: ユーザーが「このツールで何ができるか」を判断するために読む必要のある画面要素が減り、SDD化という単一の目的が一目で分かる。
- **SC-203**: 診断機能の廃止後も、001・002 で合格していた検証項目が100%再現する（SDD化の完走、べき等性、未選択ガード、実行中の無効化、完了案内の可読性とコピー可能性）。
- **SC-204**: 診断のためだけに存在していたソースファイルが1件も残らない。

## Assumptions（前提事項）

- 本フィーチャーは 001・002 の実装に対する変更であり、新規の別アプリは作らない。
- **診断（001 FR-017〜FR-021）と手順案内（001 FR-022）はまとめて廃止する。** 手順案内は診断結果を入力として完了状況を [済]/[未] で示す機能であり、診断が無くなると判定材料を失う。案内だけを残しても定型文となり、FR-205 で残す完了案内と重複する。したがって両者を分離して片方だけ残す選択は採らない。
- 準備状況の把握が必要になった場合は、VS Code の Claude Code パネルで直接尋ねればよい。憲章の制定状況や CLAUDE.md の妥当性は、リポジトリを読める Claude Code のほうが本ツールより正確に判断できる。
- 結果一覧（`.gitignore` 生成などの手順結果を表示する領域）は SDD化の結果表示に引き続き使うため、削除しない。診断と共用していたが、共用をやめるだけである。
- 001 の User Story 2（診断）と User Story 3（手順案内）は本フィーチャーにより無効となる。001 の検証タスクのうち、これらに対応するものは実施不要となる。
- 002 の検証タスクのうち、診断の回帰確認にあたるもの（DT-106）も同様に実施不要となる。
- 本フィーチャーの検証には、001・002 と同じく `C:\work\test\test01` を用いる。

### コミット対象が無いときの結果表示について（FR-210、FR-211）

**発見の経緯**: 002 の手動テスト中、`test01` に対する「生成」で Git 手順が「失敗」と表示され、内容欄に `On branch main Untracked files:...` が出た。データは何も壊れておらず（コミット1件、追記ブロック各1回のまま）、表示だけが誤っていた。

**原因**: 実装はコミットの結果判定に `nothing to commit` という文字列を探していたが、Git が実際に出力するのは `nothing added to commit but untracked files present` である。前者は後者の部分文字列ではないため判定が外れ、「スキップ」とすべきところが「失敗」になっていた。001 の実装時に Git の出力を実測せず推測で書いた箇所である。

**発生条件**: 次の4つが揃ったときに起こる。

1. 既にコミット済みのリポジトリである
2. `.gitignore` が削除されるなどして、ツールが再作成する（内部的に「変更あり」と判定される）
3. しかし再作成された内容がコミット済みのものと同一で、Git 視点では差分がゼロ
4. `git add` しても何もステージされず、`git commit` が上記メッセージを出して非0終了する

**方針**: Git が実際に出力する文言を採取したうえで判定条件を修正する。推測に基づく文字列を残さない（FR-211）。実測した出力は次のとおり。

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	package.json

nothing added to commit but untracked files present (use "git add" to track)
```

**本フィーチャーに含める理由**: 発見は 002 の検証中だが、原因は 001 の実装にある。002 は検証がほぼ完了しており蒸し返す形になる。003 はまだ実装未着手であり、`SetupRunner.cpp` は診断削除では触らないファイルのため、修正が他の削除作業と干渉しない。実装と検証を1回にまとめられる。
