# Phase 0 Research: 失敗理由が装飾バナーに埋もれて見えなくなる問題を解消する

**Feature**: [spec.md](./spec.md) | **Date**: 2026-09-13

## R-1101: 問題の実機再現と原因の特定

**事実確認（実機）**: 対象フォルダで`specify init . --integration claude --script ps --force --non-interactive`
を実際に実行し、以下の出力（要約）を確認した。

```text
             ███████╗██████╗ ███████╗ ██████╗██╗███████╗██╗   ██╗
             ██╔════╝██╔══██╗██╔════╝██╔════╝██║██╔════╝╚██╗ ██╔╝
             （中略、ロゴが続く）
               GitHub Spec Kit - Spec-Driven Development Toolkit

Warning: Current directory is not empty (23 items)
（中略）
┌─────────────────────────────────────────────────────────────────────────────┐
│  Specify Project Setup ...                                                  │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────── Agent Detection Error ───────────────────────────┐
│  claude not found                                                            │
│  Install from: https://docs.anthropic.com/en/docs/claude-code/setup         │
│  Claude Code is required to continue with this project type.                │
│  Tip: Use --ignore-agent-tools to skip this check                           │
└─────────────────────────────────────────────────────────────────────────────┘
```

冒頭のロゴだけで500文字を超える。既存の`Brief()`（[SetupRunner.cpp:25](../../MFCApplication1/SetupRunner.cpp#L25)）
は出力の先頭160文字を単純に切り詰めるため、結果一覧には常にロゴの断片だけが表示され、実際の失敗原因
（`claude not found`）が一切現れない。

**Decision**: この事実確認をもって、原因は「先頭からの単純な文字数切り詰め」であると特定する。以降の
決定はこの原因に対する修正方針である。

## R-1102: 修正方針 — 段落単位への分割と、最後の段落を先頭優先で切り詰め

**Decision**: `Brief()`を次の手順に変更する。

1. 出力を改行（`\r\n`・`\n`）で行に分割する
2. 各行からUnicodeの罫線描画文字（Box Drawing、U+2500〜U+257F）とブロック要素（Block Elements、
   U+2580〜U+259F）を除去してTrimし、可視文字が残るかどうかで「内容行」と「空行」に分類する
3. 内容行を「段落」にまとめる。**空行が1行だけの場合は区切りとみなさず**（罫線ボックス内部の余白
   行として無視する）、内容行として扱ってそのまま連結を続ける。**空行が2行以上連続した場合にのみ**
   そこまでの内容行をひとつの段落として確定し、次の段落を開始する
4. 得られた段落のうち**最後の段落**を採用する。その段落内の行は半角スペースで連結する
5. 採用した段落が`maxLength`以下ならそのまま返す。超える場合は**その段落の先頭から**`maxLength`
   文字を切り詰めて返す（既存と同じ`Left()`方向、ただし対象が段落単位に絞り込まれている点が異なる）
6. 内容行が1つも無かった場合（出力全体が装飾のみだった場合）は、元の出力を改行・タブのみ正規化した
   ものを対象に、既存どおり先頭から`maxLength`文字を切り詰めて返す（FR-1103のフォールバック）

**実機データでの検証（`/speckit-analyze`による指摘を受けて実施）**: R-1101で取得した実際の
`specify init`出力（装飾除去前2236文字）に対して上記アルゴリズムを実行したところ、3つの段落
（(1) ロゴ・警告文の251文字、(2) Specify Project Setupボックスの99文字、(3) Agent Detection Error
ボックスの214文字）に分割され、最後の段落(3)が採用された。段落(3)を先頭から160文字に切り詰めた
結果は次のとおりであり、**「claude not found」を含む**ことを実測で確認した。

```text
Agent Detection Error claude not found Install from: https://docs.anthropic.com/en/docs/claude-code/setup Claude Code is required to continue with this project ...
```

**Rationale**:
- R-1101で確認したとおり、`specify`のロゴ・枠線はいずれもBox Drawing / Block Elementsの範囲の文字で
  構成されている。この範囲を除去するだけで、ロゴ行は（可視文字が残らないため）実質的に消える
- **単純な「除去＋末尾優先」だけでは不十分だった**: 当初は除去後のテキスト全体をひとつながりの
  文字列として末尾`maxLength`文字を採用する設計を検討したが、実機データで検証したところ
  「claude not found」の後に続く説明文（URL・案内文・Tip、合計約190文字）だけで予算を使い切り、
  肝心の見出し行が末尾ウィンドウから押し出されてしまうことが判明した（最初の`/speckit-analyze`で
  指摘、実測で確認）。単純な位置（先頭/末尾）だけでは、見出しとその説明文が合わせて`maxLength`を
  超える現実のケースに対応できない
- **段落単位への分割が有効な理由**: `specify`のボックス描画は、ボックスの外枠だけでなく**ボックス
  内部にも余白としての空行**を挟む（例: タイトル行と本文行の間に1行の空行がある）。この内部余白を
  「段落の区切り」と誤認しないよう、**空行1行は無視し、2行以上連続した場合のみ区切りとみなす**
  ことで、1つのエラーボックスの内容（タイトル＋見出し＋説明文＋Tip）を1つの段落としてまとめて
  扱える。ボックス間（無関係な情報ボックスとエラーボックスの間）には十分な数の空行・枠線が
  存在するため、正しく別の段落として分離される
- **最後の段落を「先頭から」切り詰める理由**: 段落単位に絞り込むことで既に無関係な先行ボックス
  （「GitHub Spec Kit」のタグライン、「Specify Project Setup」ボックス等）は除外できているため、
  最後の段落自体は「見出し（例: Agent Detection Error → claude not found）が先頭に、詳細な説明が
  後に続く」という自然な書き方になっていることが多い。したがって段落を採用した後は、（全体を
  末尾優先にするのではなく）**その段落自体を先頭から**切り詰める方が、見出しを含めた診断情報を
  最大化できる
- **既存の短い失敗メッセージに影響しない理由（SC-1102）**: 装飾も空行もない短い出力は、内容行が
  すべて1つの段落にまとまり、かつその長さは`maxLength`以下であることが通常であるため、そのまま
  返され既存の表示と完全に一致する（実機データではなく合成データで再検証済み、[quickstart.md](./quickstart.md) DT-1101ケースB）

**Alternatives considered**:
- 特定のキーワード（"Error"、"error"、"エラー"等）を含む行を検索して優先表示する: `specify`の
  実例には効くが、キーワードに一致しない失敗メッセージには効かず、キーワードの網羅性を保守し
  続ける必要が生じる。段落分割という構造ベースのヒューリスティックの方が、キーワード辞書を
  持たずに済み、既存の除去処理（R-1103）とも自然に組み合わさる
- 出力全体を新しいUIやログファイルに保存し、詳細を別途参照できるようにする: spec.md Assumptionsで
  明示的にスコープ外とした（新しい永続化・UIを追加しない、原則III YAGNI）
- 除去後のテキスト全体（段落分割なし）の末尾`maxLength`文字を採用する: 当初の設計。上記のとおり
  実機データで「claude not found」が失われることを確認したため却下（本R-1102の履歴として記録）
- 空行を1行でも区切りとみなす（ボックス内部の余白を考慮しない）: 実機データのボックス内部余白により
  1つのエラーボックスが複数の小さな段落に分断され、「最後の段落」が本文の一部（例:「Tip: ...」の
  1行のみ）になってしまい、見出しを含む段落が選ばれない。却下

## R-1103: 除去対象の文字範囲の選定

**Decision**: Unicode の **Box Drawing（U+2500〜U+257F）** と **Block Elements（U+2580〜U+259F）** の
2ブロックを除去対象とする。

**Rationale**:
- 実機で確認した`specify`のロゴ・枠線は、フルブロック（█ U+2588）、罫線（═ U+2550、║ U+2551、
  ╗ U+2557、╝ U+255D、╚ U+255A、╔ U+2554 等）、通常の枠線（┌ U+250C、┐ U+2510、└ U+2514、
  ┘ U+2518、─ U+2500、│ U+2502 等）で構成されており、いずれもこの2ブロックに収まる
- 対象を2つの連続したUnicodeブロックに限定することで、除去処理は単純な範囲比較（コードポイントが
  2つの区間に入るかどうか）で実装でき、個別の文字を列挙する保守コストが生じない
- 日本語の文章（ひらがな・カタカナ・漢字）やラテン文字はこの範囲に含まれないため、誤って通常の
  エラーメッセージを消してしまうリスクは低い（spec.md Edge Cases: 日本語・英語混在時も正しく表示）

**Alternatives considered**:
- ASCII文字以外をすべて除去する: 日本語のエラーメッセージ（例: 「git のユーザー設定が必要です」）
  まで消えてしまい、要件に反する。却下
- 罫線文字を1文字ずつ列挙してリスト管理する: Unicodeブロックでの範囲指定と比べて保守性が低く、
  将来別のツールが使う罫線文字を見落とすリスクがある。却下
