# Feature Specification: ダイアログのリサイズ追従

**Feature Branch**: `ver.0.2`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "ダイアログボックスを右に引っ張ったときと、下に引っ張ったときの動作です。右に引っ張ったときに、表の表示エリアも連動して変化してほしい。また、下に引っ張ったときに、案内欄と OK・キャンセルのエリアが連動して移動してほしい。どちらも、縮めたときは反対の動作をします。"

## 背景

ダイアログは `WS_THICKFRAME` を持つため、ユーザーはマウスでサイズを変更できる。しかし**サイズ変更に追従する処理が一切実装されていない**。ウィザードが生成した状態のまま、001〜003 のどのフィーチャーもこの点に触れてこなかった。

その結果、ウィンドウを広げると各コントロールは元の大きさ・位置のまま取り残され、右側と下側に大きな空白が生じる。せっかく画面を広げても、結果一覧に表示できる行数も列幅も増えない。逆に縮めると、コントロールがウィンドウの外へはみ出して操作できなくなる。

本フィーチャーは、ウィンドウのサイズ変更に**各コントロールが追従する**ようにする。

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - ウィンドウを広げて結果を見やすくする (Priority: P1)

開発者は、SDD化の実行結果や `.gitignore` の生成理由が長くて読みきれないとき、ウィンドウの右端をドラッグして横に広げる。すると**結果一覧の幅も一緒に広がり**、「内容」列に表示される文字が増えて読めるようになる。下端をドラッグして縦に広げると、**結果一覧の高さが伸びて**より多くの行が一度に見える。

広げすぎたと感じて元に戻すと、コントロールも**縮小に追従して**元の見え方に戻る。ウィンドウの外へはみ出したり、重なったりしない。

**Why this priority（この優先度である理由）**: 本フィーチャーの目的そのものである。結果一覧の「内容」列には手順の失敗理由や `.gitignore` の状況が入り、既定のウィンドウ幅では末尾が切れることがある。ウィンドウを広げれば読めるようにすることが、最も直接的な価値になる。

**Independent Test（独立したテスト方法）**: アプリを起動してウィンドウの右下をドラッグで広げ、結果一覧の幅と高さが追従することを確認し、続いて元のサイズまで縮めて追従して戻ることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） ダイアログが既定のサイズで表示されている、**When**（動作） ユーザーが右端をドラッグして横に広げる、**Then**（結果） パス表示欄と結果一覧と案内欄の**幅が広がり**、右側に不自然な空白が残らない。
2. **Given**（前提） ダイアログが既定のサイズで表示されている、**When**（動作） ユーザーが下端をドラッグして縦に広げる、**Then**（結果） 結果一覧の**高さが伸び**、案内欄と OK・キャンセルボタンが**下へ移動**して、下側に不自然な空白が残らない。
3. **Given**（前提） ダイアログを広げた状態である、**When**（動作） ユーザーがウィンドウを縮める、**Then**（結果） 各コントロールが**縮小に追従**し、ウィンドウの外へはみ出さず、互いに重ならない。
4. **Given**（前提） ウィンドウのサイズを変更した、**When**（動作） ユーザーが「参照...」「生成」ボタンを見る、**Then**（結果） 参照ボタンは**右端との距離を保ったまま**移動し、生成ボタンは**左端との距離を保ったまま**その場に留まる。ボタンの大きさは変わらない。
5. **Given**（前提） ウィンドウを縦横に大きく広げた、**When**（動作） ユーザーが OK・キャンセルボタンを見る、**Then**（結果） 2つのボタンは**右下の隅との距離を保ったまま**移動している。

---

### User Story 2 - 小さくしすぎても操作不能にならない (Priority: P2)

開発者がウィンドウを極端に小さくしようとしても、一定の大きさより小さくはならない。すべてのコントロールが見えていて操作できる状態が保たれ、ボタンが隠れて押せなくなったり、結果一覧が潰れて何も読めなくなったりしない。

**Why this priority（この優先度である理由）**: 追従処理を入れると、縮小時にコントロールの幅や高さが負の値になりうる。制限が無いと表示が破綻し、最悪の場合ボタンが押せずアプリを終了するしかなくなる。User Story 1 の価値を安全に成立させるための土台である。

**Independent Test（独立したテスト方法）**: ウィンドウの右下をつまんで可能な限り小さくドラッグし、それ以上小さくならない下限が存在すること、その状態でもすべてのコントロールが見えて操作できることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） ダイアログが表示されている、**When**（動作） ユーザーがウィンドウを可能な限り小さくしようとする、**Then**（結果） 既定のサイズより小さくはならず、そこで下限に達する。
2. **Given**（前提） ウィンドウが下限のサイズである、**When**（動作） ユーザーが画面を見る、**Then**（結果） すべてのコントロールが見えており、ボタンはクリックでき、結果一覧には少なくとも数行が表示できる高さがある。

---

### Edge Cases（エッジケース）

- ウィンドウを最大化した場合も、通常のリサイズと同じ追従が行われる。
- ウィンドウを最小化してから元に戻した場合、コントロールの配置が崩れない。
- 導入処理の実行中にウィンドウのサイズを変更しても、処理は中断されず、結果一覧への行の追加も正しく続く。
- 結果一覧の列幅は、一覧そのものの幅が変わったときに追従する。列の合計幅が一覧の幅と大きく食い違って、右側に無駄な余白ができたり横スクロールバーが不要に出たりしない。
- 案内欄は縦スクロール可能なため、高さが変わってもテキストが失われない。

### テスト方針

001〜003 と同じく、静的テスト（アプリケーションを実行せずに行う検査）と動的テスト（ダイアログを操作して行う検査）の2層で検証する。

本フィーチャーは**画面の見た目と操作感が成果物**であり、その大部分は実際にウィンドウをドラッグしないと確認できない。静的テストで確認できるのは実装の構造（追従処理と下限設定が存在すること、各コントロールの追従方針が定義されていること）に限られ、**動的テストの比重が 001〜003 より大きくなる**。

#### 静的テスト

- **ST-301 追従処理の存在検査**: ウィンドウのサイズ変更を受け取る処理と、各コントロールを再配置する処理が実装されていることを確認する。
- **ST-302 下限設定の存在検査**: ウィンドウの最小サイズを制限する処理が実装されていることを確認する（FR-306）。
- **ST-303 追従方針の網羅検査**: 画面上のすべてのコントロールについて、サイズ変更時の追従方針（位置を保つ／幅が伸びる／端に貼り付く等）が定義されており、方針が未定義のまま取り残されたコントロールが無いことを確認する。
- **ST-304 コンパイラ警告の検査**: 全構成のビルドが、本変更に起因する警告を出さずに完了すること。
- **ST-305 仕様と実装の対応の検査**: 本フィーチャーで追加した各箇所が、どの機能要件に対応するかをコード上で追跡できること。

#### 動的テスト

| No. | 検証内容 | 対応する受け入れシナリオ |
|---|---|---|
| DT-301 | 横に広げると一覧・パス欄・案内欄の幅が広がる | US1-1 |
| DT-302 | 縦に広げると一覧の高さが伸び、案内欄とボタンが下へ移動する | US1-2 |
| DT-303 | 縮めると追従して元に戻り、はみ出しも重なりも起きない | US1-3 |
| DT-304 | 参照ボタンは右端、生成ボタンは左端との距離を保つ | US1-4 |
| DT-305 | OK・キャンセルは右下の隅との距離を保つ | US1-5 |
| DT-306 | 既定サイズより小さくできない | US2-1 |
| DT-307 | 下限サイズでもすべてのコントロールが操作できる | US2-2 |
| DT-308 | 結果一覧の列幅が一覧の幅に追従する | Edge Case |
| DT-309 | 最大化・最小化からの復帰で配置が崩れない | Edge Case |
| DT-310 | 導入処理の実行中にサイズを変更しても処理が続く（回帰確認） | Edge Case |

**DT-310 を含める理由**: サイズ変更の処理はワーカースレッドの動作中にも起こりうる。結果一覧への行追加とコントロールの再配置が同時に発生しても破綻しないことを確認する。001〜003 で積み上げた実行中の挙動を壊していないかの回帰確認にあたる。

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

- **FR-301**: システムはウィンドウのサイズが変更されたとき、画面上のすべてのコントロールを新しいサイズに合わせて再配置しなければならない。拡大時と縮小時の双方で追従しなければならない。
- **FR-302**: システムは横方向のサイズ変更に対し、**パス表示欄・結果一覧・案内欄の幅**を変化量に応じて増減させなければならない。
- **FR-303**: システムは縦方向のサイズ変更に対し、**結果一覧の高さ**を変化量に応じて増減させ、**案内欄と OK・キャンセルボタンを**変化量に応じて上下に移動させなければならない。
- **FR-304**: システムは、右端に配置されたコントロール（参照ボタン、OK・キャンセルボタン）について、**ウィンドウの右端との距離を一定に保った**まま移動させなければならない。ボタンの大きさは変えてはならない。
- **FR-305**: システムは、左端に配置されたコントロール（対象フォルダのラベル、生成ボタン）について、**ウィンドウの左端との距離を一定に保った**まま、位置も大きさも変えてはならない。
- **FR-306**: システムはウィンドウの最小サイズを制限しなければならない。下限は**既定のサイズ**とし、それより小さくできてはならない。
- **FR-307**: 下限のサイズにおいて、すべてのコントロールが表示され、操作可能でなければならない。コントロールがウィンドウの外へはみ出したり、互いに重なったりしてはならない。
- **FR-308**: システムは結果一覧の列幅を、一覧そのものの幅の変化に追従させなければならない。列の合計幅と一覧の幅が食い違って、不要な余白や横スクロールバーが生じてはならない。
- **FR-309**: システムは、導入処理の実行中にウィンドウのサイズが変更されても、処理を中断してはならない。結果一覧への行の追加も正しく続かなければならない。
- **FR-310**: システムは、ウィンドウの最大化・最小化からの復帰においても、通常のサイズ変更と同じ追従を行わなければならない。

### Key Entities（主要エンティティ）

- **コントロールの追従方針**: 画面上の各コントロールが、ウィンドウのサイズ変更に対してどう振る舞うかの定義。「位置も大きさも変えない」「幅だけ変える」「右端との距離を保って移動する」「下端との距離を保って移動する」「幅と高さの両方を変える」といった種類を持つ。**画面上のすべてのコントロールがいずれか1つの方針を持たなければならない**（ST-303）。
- **ウィンドウの最小サイズ**: 縮小の下限。既定のダイアログサイズと同じ値を持つ。

## Success Criteria（成功基準） *(必須)*

### Measurable Outcomes（測定可能な成果）

- **SC-301**: ウィンドウを横に広げたとき、結果一覧の「内容」列で読める文字数が増える。
- **SC-302**: ウィンドウを縦に広げたとき、結果一覧にスクロールなしで表示できる行数が増える。
- **SC-303**: ウィンドウをどのサイズに変更しても、コントロールがウィンドウの外へはみ出す状態が発生しない。
- **SC-304**: ウィンドウを拡大してから元のサイズへ戻したとき、各コントロールの位置と大きさが**変更前と一致する**。
- **SC-305**: 001〜003 で合格していた検証項目が100%再現する（SDD化の完走、べき等性、未選択ガード、実行中のコントロール無効化、完了案内の可読性とコピー可能性）。

## Assumptions（前提事項）

- 本機能は既存の `MFCApplication1` のダイアログに追加する。
- ダイアログは既に `WS_THICKFRAME` を持ちサイズ変更可能である。この属性は変更しない。
- 対象となるコントロールは 003 完了時点の5つ（パス表示欄・参照ボタン・生成ボタン・結果一覧・案内欄）と、ラベル・OK・キャンセルである。003 で診断ボタンが廃止されたため、本フィーチャーが扱う対象は確定している。
- ウィンドウの最小サイズは既定のダイアログサイズとする。既定サイズは 001 の設計時点で全コントロールが収まるよう決めたものであり、それより小さくする理由が無い。
- 縦方向のサイズ変更で高さが伸びるのは結果一覧のみとする。案内欄は 002 で縦スクロール可能にしてあり、高さを変えなくても全文を読めるため。
- リサイズ時のちらつき（再描画のたらつき）については、目立つ場合にのみ対処する。本フィーチャーの主目的は追従そのものであり、描画品質の最適化は含めない。
- 本フィーチャーの検証には、001〜003 と同じく `C:\work\test\test01` を用いる。
