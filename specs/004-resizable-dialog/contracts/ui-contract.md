## 2. ラベルのID（**新規に割り当てる**）

現在、ラベル「対象フォルダ:」は `IDC_STATIC` として定義されている。

```
LTEXT  "対象フォルダ:",IDC_STATIC,7,10,45,8
```

`IDC_STATIC` は `-1` であり、複数のコントロールが共有しうる特別な値である。`GetDlgItem(-1)` で個別のコントロールを取得することはできない。

**Decision**: ラベルに専用のID `IDC_STATIC_TARGET_LABEL`（1008）を割り当てる。`_APS_NEXT_CONTROL_VALUE` を 1009 へ更新する。

**Rationale**: ラベルの追従方針は `Fixed`（位置も大きさも変えない）であり、**再配置の処理としては何もしない**。したがって技術的にはIDが無くても動作する。それでもIDを与えるのは、**ST-303（追従方針の網羅検査）を成立させるため**である。

`Fixed` のコントロールを追従テーブルから除外する設計にすると、「意図的に固定したもの」と「定義を忘れたもの」が区別できなくなる。定義漏れの検出こそが ST-303 の目的であり、それが働かなくなる。テーブルに全コントロールを載せ、`Fixed` も明示的に1行を持たせることで、**テーブルの行数と画面上のコントロール数を突き合わせるだけで漏れが分かる**。

憲章の原則III（YAGNI）に照らすと「何もしないコントロールにIDを与える」のは一見過剰だが、これは将来のための拡張ポイントではなく、**いま必要な検査を成立させるための手当て**である。

**契約**: ID を割り当てるのはラベル1件のみ。他のコントロールのIDは変更しない。

## 3. 追従方針の契約

各コントロールは、ウィンドウのサイズ変更に対して次のとおり振る舞わなければならない。

| コントロール | 方針 | 横に広げたとき | 縦に広げたとき |
|---|---|---|---|
| ラベル | `Fixed` | 変化なし | 変化なし |
| `IDC_EDIT_TARGET_PATH` | `StretchH` | **幅が広がる** | 変化なし |
| `IDC_BUTTON_BROWSE` | `AnchorRight` | **右へ移動**（大きさ不変） | 変化なし |
| `IDC_BUTTON_GENERATE` | `Fixed` | 変化なし | 変化なし |
| `IDC_LIST_RESULT` | `StretchBoth` | **幅が広がる** | **高さが伸びる** |
| `IDC_STATIC_GUIDE` | `AnchorBottomStretchH` | **幅が広がる** | **下へ移動** |
| `IDOK` | `AnchorBottomRight` | **右へ移動** | **下へ移動** |
| `IDCANCEL` | `AnchorBottomRight` | **右へ移動** | **下へ移動** |

**縮めたときは、いずれも上表の逆方向に動く**（FR-301）。

**契約**:
- 再配置は**初期サイズからの差分**で計算する。前回サイズからの相対計算をしてはならない。丸め誤差が累積し、拡大と縮小を繰り返すと位置がずれる（[research.md](./research.md) R-303）
- 上表のとおり、**縦に伸びるのは結果一覧のみ**である。案内欄は 002 で縦スクロール可能にしてあり、高さを変えなくても全文を読める。増えた高さをすべて一覧に振ることで、読める行数が最大になる（SC-302）
- ボタン類（参照・OK・キャンセル・生成）の**大きさは変えない**。ボタンが伸縮すると、ウィンドウサイズによって押しやすさが変わり操作感が安定しない

## 4. 最小サイズの契約

**Decision**: ウィンドウの最小トラッキングサイズを**初期のウィンドウサイズ**に設定する。

**契約**:
- 下限は初期サイズと**同一**とする。それより小さくできてはならない（FR-306）
- 設定する値は**クライアント領域ではなくウィンドウ全体のサイズ**である。`ptMinTrackSize` はウィンドウ全体の寸法を指すため、クライアントサイズを渡すと枠とタイトルバーの分だけ小さい下限になる（[research.md](./research.md) R-304）
- 下限のサイズにおいて、すべてのコントロールが表示され操作可能でなければならない（FR-307）。初期サイズは 001 の設計時点で全コントロールが収まるよう決めたものなので、これは自動的に満たされる

---

## 5. 初期化との順序の契約

`OnSize` は**ダイアログの初期化中にも呼ばれる**。その時点ではコントロールが未生成で `GetDlgItem` が `nullptr` を返す。

**契約**:
- 初期化完了フラグを持ち、**フラグが立つまで `OnSize` は何もしない**。これを怠るとアクセス違反になる
- フラグは `OnInitDialog` の**最後**に立てる。追従テーブルへの初期矩形の記録と、初期クライアントサイズ・最小ウィンドウサイズの記録が済んだ後でなければならない
- 初期矩形は `GetWindowRect` + `ScreenToClient` でダイアログのクライアント座標として記録する

---

## 6. 結果一覧の列幅の契約

`InitResultList()` は列幅を一覧のクライアント幅の **40% / 20% / 40%** で設定している。

**契約（FR-308）**:
- リサイズによって一覧の幅が変わったとき、**同じ比率で列幅を再計算する**。放置すると一覧だけ広がって列が元幅のまま残り、右側に余白ができる
- 比率は**1箇所にまとめて定義し**、初期化時と再配置時の両方から参照する。別々に持つと、列を追加したり比率を変えたりしたときに片方だけ直す誤りが起きる（[research.md](./research.md) R-305(2)）

## 7. 既存機能への影響（**変更してはならないもの**）

以下は本フィーチャーで一切変更しない。

| 機能 | 根拠 |
|---|---|
| 5手順の実行、検証チェーンの5段階とその順序 | 003 FR-207 を継承 |
| 実行中のコントロール無効化（生成・参照の2つ）と、完了時に有効へ戻す契約 | 003 FR-209 を継承 |
| 完了案内の内容・可読性・コピー可能性 | 002 FR-110〜112、003 FR-205 を継承 |
| `.gitignore` の生成と追記、べき等性 | 002 FR-106〜106b を継承 |
| ワーカースレッドとの通信方式（`PostMessage`） | 001 research.md R-002 |

**ワーカースレッド実行中のリサイズについて（FR-309 / DT-310）**: ワーカーはコントロールを直接操作せず `PostMessage` で結果を送るだけである。`OnSize` は UI スレッドで動くため、再配置と行追加が競合しない。**追加の排他制御は不要**であり、導入してはならない。不要なロックは処理の停止を招く。

ただし `AppendResultRow` は `EnsureVisible` を呼ぶため、リサイズ直後にスクロール位置が動くことがある。これは新しい行を見せる正しい動作であり、対処しない。
