# Tasks: ダイアログのリサイズ追従

**Input**: `/specs/004-resizable-dialog/` からの設計ドキュメント

**Prerequisites（前提条件）**: [plan.md](./plan.md)、[spec.md](./spec.md)、[research.md](./research.md)、[data-model.md](./data-model.md)、[contracts/ui-contract.md](./contracts/ui-contract.md)、[quickstart.md](./quickstart.md)

**Tests（テスト）**: 仕様の「テスト方針」がテストを明示的に要求している。静的テスト（ST-301〜305）と動的テスト（DT-301〜310）を検証タスクとして含める。自動テストランナーは導入しないため、これらはコードではなく**実施手順**として遂行するタスクである。

**Organization（構成）**: タスクはユーザーストーリーごとにグループ化される。追従の仕組み（列挙・構造・テーブル・再配置処理）は両ストーリーが依存する共通基盤のため Phase 2 に置く。

**⚠️ 本フィーチャー固有の注意**: 001〜003 は削除中心で「消し過ぎ」が主リスクだったが、**004 は初めての機能追加**であり主リスクが変わる。次の2点に注意する。

- **定義漏れ** — コントロールを1つ追従テーブルに載せ忘れると、そのコントロールだけ元の位置に取り残される（T009、ST-303 が検出）
- **計算方式の誤り** — 前回サイズからの相対計算は丸め誤差が累積し、拡大縮小を繰り返すと位置がずれる（T010、SC-304 が検出）

- **[P]**: 並行実行可能（異なるファイル、依存関係なし）
- **[Story]**: このタスクがどのユーザーストーリーに属するか（US1、US2）
- 説明には正確なファイルパスを含める

- [ ] T007 `MFCApplication1/MFCApplication1Dlg.h` に `OnSize` と `OnGetMinMaxInfo` の宣言、および再配置処理のヘルパー関数の宣言を追加する。T006 に依存

## Implementation Strategy（実装戦略）

### MVP First（User Story 1 のみ）

1. Phase 1: Setup を完了する（T001〜T003）
2. Phase 2: Foundational を完了する（T004〜T014）
3. Phase 3: User Story 1 を検証する（T015〜T020）
4. **停止して検証**: T015（ST-303 定義漏れ）と T018（SC-304 位置のずれ）を実施する

### 実装順序に関する注意

- **T009 で8コントロールすべてを登録する。** `Fixed` のラベルと生成ボタンも省略しない。除外すると ST-303 が「意図的に固定」と「定義を忘れた」を区別できなくなる
- **T010 は必ず初期矩形からの差分で計算する。** 前回サイズからの相対計算は丸め誤差が累積し、SC-304 を満たせない。この誤りは拡大縮小を何度か繰り返さないと表面化しない
- **T011 で `m_layoutReady` の早期リターンを省略しない。** `OnSize` は初期化中にも呼ばれ、コントロール未生成の状態で `GetDlgItem` が `nullptr` を返す
- **T012 で渡すのはウィンドウ全体のサイズ。** クライアントサイズを渡すと下限が枠とタイトルバーの分だけ小さくなる
- **T013 で比率を2箇所に分けて持たない。** 初期化と再配置で別々に持つと、片方だけ直す誤りが起きる
- **T025 で排他制御を追加しない。** ワーカーは `PostMessage` で結果を送るだけなので競合しない。不要なロックは処理の停止を招く

### Incremental Delivery（段階的な提供）

1. Setup + Foundational → 追従の仕組みが揃う
2. User Story 1 → ウィンドウを広げて結果が読みやすくなる（**MVP**）
3. User Story 2 → 縮めすぎても操作不能にならない
4. Phase 5 → 既存機能の回帰確認と、002・003 を含めた通し実行

## Notes（注記）

- [P] タスク = 異なるファイル、依存関係なし

- 検証タスク（T015〜T027）はコードを書くタスクではなく、[quickstart.md](./quickstart.md) の手順を実施して結果を確認するタスクである
- 番号体系が 001〜003 と並存する。本書で既存フィーチャーの要件を参照する場合は「003 FR-209」のように接頭辞を付けている。接頭辞の無い `FR-3xx` はすべて 004 の要件である
- **本フィーチャーは動的テストの比重が大きい。** 画面の見た目と操作感が成果物であり、その大部分はウィンドウを実際にドラッグしないと確認できない。静的テストで確認できるのは実装の構造に限られる
- `C:\work\test\test01` は検証で破壊的に変更される。リセット手順は [quickstart.md](./quickstart.md) の付録を参照
- 各タスクまたは論理的なまとまりごとにコミットする。ただし T008〜T012 はリンクエラーを避けるため1つのまとまりとして扱う
