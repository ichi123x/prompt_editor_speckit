# Phase 0 リサーチ: ダイアログのリサイズ追従

**Feature**: 004-resizable-dialog
**Date**: 2026-09-09
**前提**: 001〜003 の research.md は引き続き有効。本書はその差分のみを扱う。

本フィーチャーは既存実装への**追加**である。001〜003 が削除中心だったのに対し、初めて機能を足すことになる。

---

## R-301: 追従処理の実現方式

**Decision**: `WM_SIZE`（`OnSize`）を受け取り、**コントロールごとに定めた追従方針に従って `SetWindowPos` で再配置する**方式を採る。追従方針はテーブルで宣言的に持つ。

**Rationale**:
- MFC には `CResizableDialog` のような標準クラスが**存在しない**。MFC Feature Pack にも汎用のアンカー機構は含まれない。自前で書くのが素直な選択になる。
- 追従方針をテーブルで持つことで、コントロールを1つ追加したときに「テーブルに1行足す」だけで済む。処理本体に `if` を積み重ねる形にすると、コントロールが増えるたびに分岐が伸び、定義漏れも見つけにくくなる。
- ST-303（追従方針の網羅検査）は、テーブルの行数と画面上のコントロール数を突き合わせることで機械的に実施できる。処理本体に分岐を散らす方式ではこの検査が成立しない。

**Alternatives considered**:
- *外部のリサイズ用ライブラリを導入する*: 憲章の技術的制約は新規依存の追加を禁じてはいないが、原則III（YAGNI）に照らして、8コントロールの再配置のために外部依存を増やすのは過剰である。却下。
- *`DeferWindowPos` でまとめて再配置する*: 複数ウィンドウの位置を一括更新でき、ちらつきが減る。ただし 8 コントロールでは体感差がほとんどなく、コードは複雑になる。Assumptions で「描画品質の最適化は含めない」としているため、まず `SetWindowPos` で実装する。ちらつきが目立つ場合の代替として記録しておく。

**実装上の注意**: `OnSize` はダイアログの初期化中（`OnInitDialog` の完了前）にも呼ばれる。この時点ではコントロールがまだ生成されておらず `GetDlgItem` が `nullptr` を返すため、**初期化完了フラグを見て早期リターンする**必要がある。これを怠るとアクセス違反になる。

## R-302: 各コントロールの追従方針

**Decision**: 5種類の方針を定義し、8つのコントロールすべてに割り当てる。

現在の配置（003 完了時点、ダイアログは 320 x 200 DLU）:

| コントロール | 位置 (x, y, w, h) | 追従方針 |
|---|---|---|
| ラベル「対象フォルダ:」 | 7, 10, 45, 8 | **固定**（左上に留まる） |
| `IDC_EDIT_TARGET_PATH` | 54, 7, 205, 14 | **横に伸びる**（左上固定・幅のみ増減） |
| `IDC_BUTTON_BROWSE` | 265, 7, 48, 14 | **右に貼り付く**（右端との距離を保つ・大きさ不変） |
| `IDC_BUTTON_GENERATE` | 7, 30, 70, 18 | **固定** |
| `IDC_LIST_RESULT` | 7, 52, 306, 90 | **縦横に伸びる**（幅と高さの両方が増減） |
| `IDC_STATIC_GUIDE` | 7, 147, 306, 28 | **下に貼り付いて横に伸びる**（下端との距離を保ち、幅は増減） |
| `IDOK` | 209, 179, 50, 14 | **右下に貼り付く**（右端・下端との距離を保つ・大きさ不変） |
| `IDCANCEL` | 263, 179, 50, 14 | **右下に貼り付く** |

方針の種類は次の5つ。

| 方針 | 意味 | 該当 |
|---|---|---|
| `Fixed` | 位置も大きさも変えない | ラベル、生成ボタン |
| `StretchH` | 左上固定、幅だけ増減 | パス表示欄 |
| `AnchorRight` | 右端との距離を保って移動、大きさ不変 | 参照ボタン |
| `StretchBoth` | 幅と高さの両方が増減 | 結果一覧 |
| `AnchorBottomStretchH` | 下端との距離を保って移動し、幅は増減 | 案内欄 |
| `AnchorBottomRight` | 右端・下端との距離を保って移動、大きさ不変 | OK、キャンセル |

**Rationale**（仕様の FR との対応）:
- FR-302（横方向でパス欄・一覧・案内欄の幅が増減） → `StretchH`・`StretchBoth`・`AnchorBottomStretchH`
- FR-303（縦方向で一覧の高さが増減し、案内欄とボタンが移動） → `StretchBoth`・`AnchorBottomStretchH`・`AnchorBottomRight`
- FR-304（右端のコントロールは右端との距離を保つ） → `AnchorRight`・`AnchorBottomRight`
- FR-305（左端のコントロールは位置も大きさも変えない） → `Fixed`

**縦方向に伸びるのは結果一覧のみ**とした。案内欄は 002 で縦スクロール可能にしてあり、高さを変えなくても全文を読める（Assumptions に記載）。一覧だけが伸びることで、増えた高さがすべて「読める行数」に変換される。

**Alternatives considered**:
- *案内欄も縦に伸ばし、一覧と高さを按分する*: 一覧の伸びが半減し、SC-302（表示できる行数が増える）の効果が薄れる。案内欄はスクロールで足りる。却下。

## R-303: 再配置の計算方法

**Decision**: **初期サイズからの差分**を基準に計算する。`OnInitDialog` の時点で各コントロールの初期位置と初期サイズ、およびダイアログの初期クライアントサイズを記録し、リサイズのたびに「現在のクライアントサイズ − 初期クライアントサイズ」を各コントロールへ適用する。

```
dx = 現在の幅 - 初期の幅
dy = 現在の高さ - 初期の高さ

Fixed                 : 変更なし
StretchH              : w += dx
AnchorRight           : x += dx
StretchBoth           : w += dx, h += dy
AnchorBottomStretchH  : y += dy, w += dx
AnchorBottomRight     : x += dx, y += dy
```

**Rationale**:
- **前回サイズからの相対計算にしない。** 相対計算は丸め誤差が累積し、拡大と縮小を繰り返すとコントロールの位置がじわじわずれていく。初期値からの絶対差分なら、どんな経路でリサイズしても同じサイズには同じ配置が対応する。
- これにより SC-304（拡大してから元のサイズへ戻すと、位置と大きさが変更前と一致する）が構造的に保証される。テストで確認するまでもなく成立する性質にできる。

**Alternatives considered**:
- *前回の `OnSize` からの差分を積算する*: 実装は短いが上記の累積誤差を招く。SC-304 を満たせない。却下。

## R-304: 最小サイズの制限

**Decision**: `WM_GETMINMAXINFO`（`OnGetMinMaxInfo`）で最小トラッキングサイズを**初期のウィンドウサイズ**に設定する。

**Rationale**:
- FR-306 が「下限は既定のサイズ」と定めている。初期サイズは 001 の設計時点で全コントロールが収まるよう決めたものなので、それを下限にすれば FR-307（下限でもすべて操作可能）が自動的に満たされる。
- `OnSize` 側で幅や高さを下限に丸める方法もあるが、ウィンドウ枠だけが小さくなってコントロールがはみ出す見た目になる。ウィンドウ自体を縮ませないほうが挙動として自然である。

**実装上の注意**: 記録するのは**クライアント領域ではなくウィンドウ全体のサイズ**である。`OnGetMinMaxInfo` が扱う `ptMinTrackSize` はウィンドウ全体の寸法を指すため、クライアントサイズを渡すと枠とタイトルバーの分だけ小さい下限になってしまう。

## R-305: 既存機能への影響（回帰の注意点）

**(1) ワーカースレッド実行中のリサイズ**（FR-309 / DT-310）

`OnSize` は UI スレッドで動く。ワーカースレッドは `PostMessage` で結果を送るだけで、コントロールを直接操作しない（001 research.md R-002）。したがって再配置と行追加が競合することはない。**この設計のおかげで追加の排他制御は不要である。**

ただし `AppendResultRow` が `EnsureVisible` を呼ぶため、リサイズ直後にスクロール位置が動く可能性はある。動作としては正しい（新しい行を見せる）ため対処しない。

**(2) 結果一覧の列幅**（FR-308 / DT-308）

`InitResultList()` は一覧の**クライアント幅の 40% / 20% / 40%** で列幅を決めている。リサイズ後もこの比率を保つには、再配置のたびに列幅を再計算する必要がある。放置すると一覧だけ広がって列が元幅のまま残り、右側に余白ができる。

再計算は `InitResultList()` の列幅設定部分と同じ比率で行う。**列の追加や比率の変更があったときに2箇所を直す必要が生じる**ため、比率を1箇所にまとめて両方から使う。

**(3) `OnInitDialog` 完了前の `OnSize`**

R-301 に記載のとおり、初期化完了フラグで早期リターンする。フラグは `OnInitDialog` の最後に立てる。

**(4) 002 で入れた案内欄のスクロール**

案内欄は `ES_AUTOVSCROLL | WS_VSCROLL` を持つ複数行エディットである。幅が変わると折り返し位置が変わるが、スクロール可能なため内容は失われない。002 の FR-110（行数によらず全文が読める）は維持される。
