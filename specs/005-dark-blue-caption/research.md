# Phase 0 リサーチ: タイトルバーを濃い青にする

**Feature**: 005-dark-blue-caption
**Date**: 2026-09-09

本書の結論は、すべて**この開発機での実測**に基づく。推測で書いた項目には「未測定」と明記する。

**測定環境**: Windows 11 Pro 10.0.26200（25H2）／Windows SDK 10.0.26100.0／`AppsUseLightTheme=1`・`SystemUsesLightTheme=0`・`ColorPrevalence=0`（タイトルバーへのアクセントカラー適用は無効）

---

## R-401: 着色の手段

**Decision**: `DwmSetWindowAttribute` に `DWMWA_CAPTION_COLOR` を渡す。

**測定**: 起動中のダイアログのウィンドウハンドルに対して属性35を設定したところ `S_OK`（0x00000000）が返り、**画面から採取したタイトルバーのピクセルが `#1F3864` ちょうど**になった。

**Rationale**: OS 標準の仕組みであり、キャプションボタン・角丸・スナップレイアウトの吹き出しなど Windows 11 が描く要素はすべて DWM 側が面倒を見る。こちらは色を1つ渡すだけで済む。

**Alternatives considered**:

- **`WM_NCPAINT` を自前で描く** — 却下。非クライアント領域を自前描画すると、閉じる／最小化／最大化ボタン、角丸、フォーカス枠、スナップレイアウトのホバー UI をすべて自分で再現する羽目になる。FR-410（既存機能を変えない）を守るのが極めて難しく、憲章 原則III（YAGNI）にも反する
- **Windows のアクセントカラー設定を変更する** — 却下。システム全体のすべてのウィンドウが変わってしまい、利用者の環境を書き換えることになる
- **`WS_EX_LAYERED` や独自フレーム（`DwmExtendFrameIntoClientArea`）** — 却下。クライアント領域の扱いが変わり、004 のリサイズ追従に影響する

---

## R-402: 属性の値と COLORREF のバイト順

**測定**: SDK の `dwmapi.h`（10.0.26100.0）の `DWMWINDOWATTRIBUTE` 列挙を実際に読んだ。

```
DWMWA_WINDOW_CORNER_PREFERENCE = 33
DWMWA_BORDER_COLOR             = 34
DWMWA_CAPTION_COLOR            = 35
DWMWA_TEXT_COLOR               = 36
```

`WINVER` / `NTDDI_VERSION` によるガードは**掛かっていない**。したがって定数を自前で `#define` する必要はなく、`<dwmapi.h>` を include すればそのまま使える。

**COLORREF のバイト順は `0x00BBGGRR`**（RGB とは逆順）。`#1F3864` は R=0x1F・G=0x38・B=0x64 なので **`0x0064381F`** となる。

**Rationale**: ここは取り違えやすい。`0x001F3864` と書くと R と B が入れ替わり、濃い青のつもりが**茶色寄りの色**になる。実測で `0x0064381F` を渡して `#1F3864` が出ることを確認済み。

---

## R-403: タイトル文字の色

**Decision**: `DWMWA_TEXT_COLOR`（36）に白 `0x00FFFFFF` を設定する。

**測定**: 設定して `S_OK` が返った。

**Rationale**: 背景 `#1F3864` の相対輝度は約 0.041 で、白とのコントラスト比は **約 11.5:1**。SC-402 の下限 4.5:1 を大きく上回る。設定しない場合、利用者がライトモードのときは文字が濃い色で描かれ、濃紺の背景に埋もれて読めなくなる（FR-403 違反）。

---

## R-404: どこで呼ぶか（FR-404 のちらつき対策）

**Decision**: `CMFCApplication1Dlg::OnInitDialog()` の中で呼ぶ。

**Rationale**: `OnInitDialog` は `m_hWnd` が有効になっている最初の地点であり、かつ**ダイアログが画面に出る前**である。ダイアログテンプレートが `WS_VISIBLE` を持っていても、ダイアログマネージャがウィンドウを表示するのは `WM_INITDIALOG` の処理が返った後なので、既定色が一瞬見えてから塗り替わる、という見え方にはならない。

`OnInitDialog` 内での位置は、004 の追従テーブル初期化（`InitAnchors()` と `m_layoutReady`）とは**互いに無関係**なのでどちらが先でもよい。本設計では見た目に関する処理として先頭付近に置く。

**Alternatives considered**:

- **`OnPaint` や `OnSize` で毎回設定する** — 却下。R-407 のとおり DWM が属性を保持するため不要であり、毎回の再設定は 004 の `OnSize` に無関係な処理を混ぜることになる
- **`InitInstance` で設定する** — 却下。この時点ではまだウィンドウが存在しない

---

## R-405: 着色できない環境での振る舞い（FR-408・FR-409）

**Decision**: `DwmSetWindowAttribute` の戻り値 `HRESULT` を**意図的に無視する**。呼び出しを `if` で囲んだり、失敗時に何かを表示したりしない。

**測定**: 存在しない属性番号（999）を渡したところ、**例外も異常終了も起きず `E_INVALIDARG`（0x80070057）が返るだけ**だった。Windows 10 や Windows 11 のビルド 22000 未満で属性35を渡した場合も、同じく `E_INVALIDARG` が返る（属性が未知であるという点で 999 と同じ扱いになる）。

**Rationale**: 戻り値を無視すれば、着色できない環境では「何も起こらなかった」のと同じになり、FR-408 をそのまま満たす。

**`GetProcAddress` による動的解決は行わない**。`dwmapi.dll` は Windows Vista 以降のすべての Windows に存在し、`DwmSetWindowAttribute` のエクスポートも Vista 以降ある。存在しない可能性があるのは**属性番号のほう**であって関数ではないため、動的解決しても得られるものが無い。憲章 原則III（YAGNI）に照らして採用しない。

---

## R-406: dwmapi.lib のリンク方法

**Decision**: 実装する `.cpp` の中に `#pragma comment(lib, "dwmapi.lib")` を書く。`.vcxproj` は変更しない。

**測定**: `.vcxproj` には `AdditionalDependencies` の上書きが無く、既定のライブラリ一覧が使われている。SDK 10.0.26100.0 には **x64・x86 の両方**に `dwmapi.lib` が存在することを確認した。

**Rationale**: `.vcxproj` に書くと Debug／Release × x64／Win32 の**4構成すべて**に同じ記述を足すことになり、1箇所でも書き漏らすと特定構成だけリンクエラーになる（ST-404 が4構成をビルドするのはこの種の漏れを拾うため）。`#pragma` なら1行で全構成に効く。

---

## R-407: 状態が変わっても色が保たれるか（FR-406）

**Decision**: **一度設定すれば再設定は不要**。`OnSize` などで塗り直す処理は入れない。

**測定**: 属性を設定した後、再設定を一切せずに「最大化 → 元に戻す → 最小化 → 復帰」を行い、そのあとで画面からタイトルバーのピクセルを採取したところ **`#1F3864` のままだった**。DWM がウィンドウの属性として保持していることが確認できた。

**Rationale**: これにより 004 の `OnSize` / `OnGetMinMaxInfo` に一切手を入れずに済み、FR-410 を構造的に満たせる。

---

## R-408: 非アクティブ時の色（FR-405）

**測定**: 別のウィンドウを前面に出して本ツールを非アクティブにした状態でピクセルを採取したところ、**`#1F3864` のまま**だった。

> 測定時はメモ帳を起動して相手役にしたが、Windows 11 のメモ帳はストアアプリで、`Start-Process` が返すプロセスIDと実際にウィンドウを持つプロセスが別のため `Stop-Process` で閉じきれず、利用者の画面にメモ帳が残ってしまった。[quickstart.md](./quickstart.md) の手順3では**タスクバー（`Shell_TrayWnd`）にフォーカスを移す**方式に改めてある。アプリを起動しないので後片付けが要らない。

Windows の標準的なウィンドウは非アクティブになるとタイトルバーが淡くなるが、`DWMWA_CAPTION_COLOR` を明示した場合はアクティブ・非アクティブの区別なく同じ色が使われる。spec の前提事項「非アクティブ時も同じ濃い青」はそのまま満たされ、**追加の実装は不要**。

---

## R-409: 検証をどう行うか

**Decision**: **画面のピクセルを採取して色を突き合わせる**。

**測定**: `DwmGetWindowAttribute` に属性35を渡すと `E_INVALIDARG` が返る。`DWMWA_CAPTION_COLOR` は `[set]` 専用であり、**設定した色をプログラムから読み戻すことはできない**。

そのため検証は画面のキャプチャから1ピクセルを取り出して行う。採取位置は**タイトル文字とキャプションボタンの両方を避ける**必要があるため、ウィンドウ矩形の右端から 200 ピクセル左・上端から 15 ピクセル下とする。

- ウィンドウ幅は既定 578 ピクセル。右側のキャプションボタン3つはおよそ 140 ピクセル分を占めるため、右端から 200 の位置はボタンより左に入る
- タイトル文字「SDDプロジェクトのベース作成ツール」は左端から 250 ピクセル程度で終わるため、右端から 200（＝左端から約 378）は文字にも掛からない

この方法は 004 のリサイズ検証と同じく、GUI を目視せずに機械的な合否判定ができる。CLAUDE.md に記録した「フォルダ選択ダイアログは自動操作できない」という制約とは無関係で、本フィーチャーの動的テストは**ほぼ全自動で回せる**。

---

## R-410: アクセントカラー設定との優先関係（**未測定**）

Windows の設定「タイトル バーとウィンドウの境界線にアクセント カラーを表示する」（レジストリ `HKCU\Software\Microsoft\Windows\DWM\ColorPrevalence`）が有効なとき、本ツールの指定色とどちらが優先されるか。

**現環境は `ColorPrevalence=0`（無効）であり、有効時の挙動は測定していない。** 利用者の環境設定を書き換えることになるため、開発側では切り替えずに DT-405 として利用者の手で確認する。

**予想**: `DwmSetWindowAttribute` はウィンドウ単位の明示指定であり、システム既定であるアクセントカラーより優先されるはずである。ただしこれは予想であり、DT-405 で覆る可能性がある。**覆った場合は spec の FR-401 を「アクセントカラー設定が無効な場合に濃い青とする」へ弱めるか、別の手段を検討する**必要がある。
