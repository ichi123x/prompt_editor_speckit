# Feature Specification: 導入処理の実行中はダイアログを閉じられないようにする

**Feature Branch**: `018-block-close-while-running`

**Created**: 2026-11-02

**Status**: Implemented

**Input**: User description: "導入処理の実行中はダイアログを閉じられないようにする（T_CHECK_BUG_01 の正式化）。コミット1d49765で #ifdef T_CHECK_BUG_01 として実験的に入れた修正（CMFCApplication1Dlg の OnOK / OnCancel をオーバーライドし、m_running が true の間は OK・キャンセル・✖ でダイアログを閉じない）を、憲章 v1.5.0 の T-2「ワーカースレッドの実行中は、ダイアログを閉じない」に基づく正式な機能として仕様化する。実装時は #ifdef / #define T_CHECK_BUG_01 の囲みを外し、FR番号コメントを付け、CLAUDE.md の既存機能の表に 018 を追加し、憲章の説明（「4つの原則」）を最新化する。"

## 背景と、001・憲章 T-2 との関係

001 は FR-014 で「処理の実行中、二重実行を防止しなければならない」と定め、実行中は「生成」「参照...」ボタンを無効化している。しかし、ダイアログを**閉じる**操作（「OK」「キャンセル」ボタン、タイトルバーの ✖、Esc キー等）は実行中も有効なままだった。

導入処理（手順1〜6）はダイアログとは別の処理の流れで動いており、各手順の結果をダイアログへ通知しながら進む。実行中にダイアログを閉じると、次の問題が起きる。

- 処理がまだダイアログへ結果を通知しようとしているのに、通知先のダイアログが先に消える（憲章 T-2 の理由に挙げられた状態）。
- アプリケーションの終了に伴い、実行中の外部コマンド（winget・uv・specify・git・claude）が途中で強制終了される。対象フォルダには、Spec Kit の足場や Git リポジトリが中途半端な状態で残りうる。

この不具合は学習中の動作確認で発見され、コミット `1d49765` で `T_CHECK_BUG_01` という実験用の目印で囲んだ修正として先行して取り込まれた。Spec Kit を経由していないため、憲章 原則I・原則IV から外れた状態にある。その後、憲章 v1.5.0 で「所有権・スレッドモデル」節が追加され、T-2「ワーカースレッドの実行中は、ダイアログを閉じない」が明文化された。本フィーチャーは、この先行修正を T-2 に基づく正式な要件として定め直すものである。

| 既存の要件・ルール | 本フィーチャーでの扱い |
|---|---|
| 001 FR-014（実行中の二重実行防止） | **維持**。本フィーチャーは「閉じる」操作への防止を追加するもので、FR-014 の対象（生成・参照ボタン）は変えない |
| 憲章 v1.5.0 T-2（ワーカー実行中はダイアログを閉じない） | 本フィーチャーで**充足**する |
| コミット `1d49765` の実験用修正（`T_CHECK_BUG_01`） | 本フィーチャーの要件として**正式化**し、実験用の目印は取り除く |
| 憲章 v1.5.0 O-1・O-3（生の new / delete の禁止、スレッド間の所有権の渡し方） | 手順の結果をダイアログへ通知する箇所について、本フィーチャーで**充足**する（FR-1806・FR-1807） |

手順の結果の通知については、もう1つ問題がある。各手順の結果は、通知のたびに新しく確保したメモリに入れてダイアログへ送られ、ダイアログ側が受け取って解放する。しかし、送り先のダイアログが既に消えていると送信は失敗し、確保したメモリは誰にも解放されずに残る（メモリリーク）。送信が失敗する代表的な場面は「実行中にダイアログが閉じられた」ときであり、本フィーチャーが防ぐ状況と同じ場面から生じる問題であるため、同じフィーチャーで扱う（`/speckit-specify` 時の利用者の選択による）。

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - 実行中に誤って閉じても処理が守られる (Priority: P1)

開発者は「生成」をクリックして導入処理を始めた後、処理の完了を待たずに「OK」「キャンセル」、またはタイトルバーの ✖ を押してしまう。システムはダイアログを閉じず、「導入処理の実行中は閉じられません。完了までお待ちください。」という案内を表示する。案内を閉じると、ダイアログはそのまま表示され、導入処理は中断されずに最後まで進む。

**Why this priority（この優先度である理由）**: 本フィーチャーの目的そのものである。実行中に閉じられると、外部コマンドが途中で強制終了され、対象フォルダが中途半端な状態で残る。

**Independent Test（独立したテスト方法）**: `C:\work\claude\test\test01` を対象フォルダとして「生成」をクリックし、結果一覧に手順が並び始めた（まだ完了していない）時点で「キャンセル」を押す。案内が表示されてダイアログが閉じないこと、案内を閉じた後も手順が最後まで進むことを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 導入処理の実行中、**When**（動作） 「OK」ボタンを押す、**Then**（結果） ダイアログは閉じず、実行中のため閉じられない旨の案内が表示される。
2. **Given**（前提） 導入処理の実行中、**When**（動作） 「キャンセル」ボタンを押す、**Then**（結果） ダイアログは閉じず、同じ案内が表示される。
3. **Given**（前提） 導入処理の実行中、**When**（動作） タイトルバーの ✖ を押す、**Then**（結果） ダイアログは閉じず、同じ案内が表示される。
4. **Given**（前提） 上記いずれかの案内が表示された、**When**（動作） 案内を閉じる、**Then**（結果） ダイアログは表示されたままで、導入処理は中断されずに完了まで進み、結果一覧と完了案内がこれまでどおり表示される。

---

### User Story 2 - 処理が終わればこれまでどおり閉じられる (Priority: P2)

開発者は導入処理が完了した後（成功・失敗・中止のいずれでも）、または一度も「生成」を押していない状態で、「OK」「キャンセル」、✖ のいずれかを押す。システムはこれまでどおり、案内を出さずにダイアログを閉じる。

**Why this priority（この優先度である理由）**: 閉じる操作を止めるのは実行中に限る必要がある。止める条件を誤ると、アプリケーションを終了できなくなる回帰が起きる。

**Independent Test（独立したテスト方法）**: アプリケーションを起動した直後に「キャンセル」を押してダイアログが閉じることを確認する。また、導入処理を完了まで実行した後に ✖ を押してダイアログが閉じることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） アプリケーションの起動直後で、導入処理を一度も実行していない、**When**（動作） 「OK」「キャンセル」、✖ のいずれかを押す、**Then**（結果） 案内は表示されず、ダイアログが閉じる。
2. **Given**（前提） 導入処理が完了した（成功・失敗・途中の手順の失敗による中止のいずれでも）、**When**（動作） 「OK」「キャンセル」、✖ のいずれかを押す、**Then**（結果） 案内は表示されず、ダイアログが閉じる。
3. **Given**（前提） 「生成」を押したが、検証（フォルダ未選択・書き込み権限・マーカー等）で処理が開始されずに中止された、**When**（動作） 「キャンセル」を押す、**Then**（結果） 案内は表示されず、ダイアログが閉じる。

---

### Edge Cases（エッジケース）

- 実行中に Esc キー・Alt+F4・タイトルバーのシステムメニューの「閉じる」・タスクバーのウィンドウ一覧からの「ウィンドウを閉じる」で閉じようとした場合も、ボタンや ✖ と同じく閉じずに案内を表示しなければならない。
- 実行中に Enter キーを押した場合（既定のボタンである「OK」が押されたとみなされる場合）も、閉じずに案内を表示しなければならない。
- 案内を表示している間に導入処理が完了した場合、案内を閉じた後は、結果一覧と完了案内がこれまでどおり表示され、その後は閉じる操作がそのまま受け付けられなければならない。
- 実行中に閉じる操作を何度繰り返しても、そのたびに案内が表示されるだけで、ダイアログが閉じたり導入処理が中断されたりしてはならない。
- 利用者が画面のどこもクリックしないまま、キーボードだけで操作する場合（「生成」を押した直後に Esc・Enter を押す、完了後にそのまま Esc を押す）も、Esc・Enter は上記のとおり働かなければならない（FR-1808）。

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

- **FR-1801**: システムは、導入処理の実行中（「生成」で処理が開始されてから、全手順の完了が通知されるまで）、ダイアログを閉じるすべての操作（「OK」ボタン、「キャンセル」ボタン、タイトルバーの ✖、およびこれらと同じ扱いになる Enter・Esc・Alt+F4・システムメニューの「閉じる」等）に対して、ダイアログを閉じてはならない。
- **FR-1802**: システムは、FR-1801 によって閉じる操作を受け付けなかったとき、「導入処理の実行中は閉じられません。完了までお待ちください。」という日本語の案内を表示しなければならない。
- **FR-1803**: システムは、FR-1801 によって閉じる操作を受け付けなかった場合でも、導入処理を中断・取り消ししてはならず、処理は最後まで継続しなければならない。
- **FR-1804**: システムは、導入処理を実行していないとき（起動直後、処理の完了後、検証による中止後）は、閉じる操作をこれまでどおり受け付け、案内を表示せずにダイアログを閉じなければならない。
- **FR-1805**: 本フィーチャーの動作は常に有効でなければならない。実験用の目印（`T_CHECK_BUG_01`）による有効・無効の切り替えは残してはならない。
- **FR-1806**: システムは、導入処理が各手順の結果をダイアログへ通知する際、通知の送信に失敗した場合でも、その結果を保持するために確保したメモリを確実に解放しなければならない（憲章 v1.5.0 O-1・O-3）。
- **FR-1807**: システムは、ダイアログが手順の結果の通知を受け取った場合、結果の表示が終わった時点で、その結果を保持するメモリを確実に解放しなければならない。受け取った結果の所有者（解放の責任を持つ側）は、コード上で明示されていなければならない（憲章 v1.5.0 O-1・O-3）。
- **FR-1808**: システムは、導入処理を開始した時点で、キーボードの入力先（フォーカス）をダイアログ内の操作可能な部品へ移さなければならない。実行中に無効化する「生成」ボタンにフォーカスが残ると、フォーカスがどこにも無い状態になり、Esc・Enter がダイアログに届かず、FR-1801・FR-1802 の案内も、完了後の FR-1804 の「閉じる」も働かなくなるためである（実装後の実機確認 DT-1801 で発見。憲章 原則V）。

## Success Criteria（成功基準） *(必須)*

### Measurable Outcomes（測定可能な成果）

- **SC-1801**: 導入処理の実行中に、閉じる操作（「OK」「キャンセル」、✖、Esc、Alt+F4）を試みた場合、100% のケースでダイアログが閉じず、導入処理が最後まで完了する。
- **SC-1802**: 導入処理を実行していないときに閉じる操作を行った場合、100% のケースで、追加の確認や案内なしに1回の操作でダイアログが閉じる（本フィーチャー導入前と同じ操作回数）。
- **SC-1803**: 実行中に閉じる操作を試みたことが原因で、対象フォルダが中途半端な状態（外部コマンドの途中終了による不完全な足場・リポジトリ）で残るケースが 0 件になる。
- **SC-1804**: 手順の結果の通知に関わるコードのうち、所有者が明示されないメモリの確保・解放（憲章 O-1 の例外として所有者がコメントで示された箇所を除く）が 0 箇所になる。

## Assumptions（前提事項）

- 実行中に閉じる操作を受け付けなかったことを利用者へ伝える手段は、実験用修正で利用者自身が確認済みの「メッセージボックスによる案内」を踏襲する。「OK」「キャンセル」ボタンを実行中に無効化する方式は採らない（✖ やキーボード操作は無効化だけでは防げず、結局同じ防止処理が必要になるため。憲章 原則III）。
- 実行中に処理を途中で取り消す機能（中止ボタン等）は本フィーチャーの対象外とする。外部コマンドを安全に途中終了させる設計が別途必要になるためである。
- 憲章 O-1 に反する箇所のうち、手順の結果の通知以外のもの（例: アプリケーション起動時にウィザードが生成したシェルマネージャーの確保・解放）は本フィーチャーの対象外とする。018 の目的（実行中のダイアログの寿命と、処理からの通知の安全性）と関係しないためである。
- FR-1806 の「送信に失敗した場合」は、本フィーチャー適用後は実行中にダイアログが閉じられなくなるため、画面操作では再現できない。この要件の充足は、動的テストではなくコードの検査（静的テスト）で確認する。
- Windows のシャットダウン・サインアウトによる強制終了は本フィーチャーの対象外とする。OS がアプリケーションの終了を強制する場面であり、利用者の誤操作を防ぐという本フィーチャーの目的とは異なる。
- FR-1808 は、実装後の実機確認（DT-1801、2026-11-03）で、実行中の Esc・Enter が無反応になることが判明して追加した。OK・キャンセル・✖・Alt+F4 は合格していた。原因は 001 から存在した「無効化したボタンにフォーカスが残る」問題であり、画面をクリックしてから Esc を押すと閉じることを利用者が実機で確認して、原因を確定した。利用者の選択（案A: 018 の中で直す）により本フィーチャーに含める。
- 実装時の付帯作業として、次を行う（憲章 原則IV・Governance に基づく）。
  - 先行修正の実験用の目印（`#ifdef` / `#define T_CHECK_BUG_01`）とその説明コメントを取り除き、変更箇所に本フィーチャーの FR 番号をコメントで記載する。
  - CLAUDE.md の「既存機能」の表に 018 を追加する。
  - CLAUDE.md の憲章の説明（「4つの原則」）を、憲章 v1.5.0 の内容（原則 I〜V と「所有権・スレッドモデル」節）に合わせて更新する。
