# Feature Specification: サブフォルダ内のウィザードプロジェクトを検出できるようにする

**Feature Branch**: `017-detect-nested-project`

**Created**: 2026-09-21

**Status**: Implemented

**Input**: User description: "指定したフォルダのサブフォルダにウィザードプロジェクトがあるときも、動作するように修正してください。"

## 背景と、002 との関係

002（[プロジェクト種別選択の廃止](../002-remove-kind-selection/spec.md)）は FR-103 で「対象フォルダ配下に、認識可能なプロジェクトマーカーが1つ以上存在するかを、種別を区別せずに確認しなければならない」と定めた。しかし実装（`TargetFolderState::Read`）は対象フォルダの**直下**しか調べておらず、「配下」という文言が意図していたはずのサブフォルダの探索を行っていなかった。

Visual Studio のプロジェクトウィザードは、ユーザーが選んだ場所の直下ではなく、ソリューション名と同名のサブフォルダを新規作成してその中にプロジェクト一式（`.sln` を含む）を配置することがある（本リポジトリ自身の `MFCApplication1/` フォルダがまさにこの構造）。利用者が「対象フォルダ」としてこの一つ上の階層（プロジェクトの親フォルダ、将来 Spec Kit の足場や `.git` を置く場所）を選んだ場合、現状ではマーカーが直下に無いため「対象のプロジェクトが見つかりません」と誤って中止される。

本フィーチャーが置き換える 002 の要件は次のとおり。

| 002 の要件 | 本フィーチャーでの扱い |
|---|---|
| FR-103（対象フォルダ配下のマーカー確認） | **拡張**。「直下」に加え、対象フォルダの配下にあるサブフォルダも探索対象に含める |

上記以外の 001・002 の要件（マーカーの種別を区別しない、複数種類の共存を警告しない、検証チェーンの順序、診断は対象フォルダに書き込まない、等）はすべてそのまま有効である。マーカーが見つかった**後**の一連の処理（`.gitignore` の配置、Git 初期化、Spec Kit 足場の配置など）は、これまでどおり利用者が選んだ対象フォルダそのものに対して行われる。マーカーが実際にはサブフォルダにあったとしても、対象フォルダを差し替えることはしない。

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - プロジェクトの親フォルダを選んでもSDD化できる (Priority: P1)

開発者は、Visual Studio のウィザードで新規プロジェクトを作成した際にできた「プロジェクト名と同じ名前のサブフォルダ」を含む親フォルダを対象フォルダとして選び、「生成」ボタンをクリックする。ウィザードが作成した `.sln`/`.vcxproj` 等が対象フォルダの直下ではなくサブフォルダにあっても、システムはプロジェクトを検出し、これまでどおり手順1〜6（または016のリポジトリ登録：NG選択時は手順1〜4と手順6の生成部分）を実行する。

**Why this priority（この優先度である理由）**: 本フィーチャーの目的そのものである。これが動かないと、Visual Studio の標準的なプロジェクト作成結果に対して本ツールがそのまま使えない。

**Independent Test（独立したテスト方法）**: `C:\work\test\test01` のようにサブフォルダ（例: `test01\MFCApplication1\`）に `.sln` を配置したフォルダを対象フォルダとして選び、「生成」をクリックして、「対象のプロジェクトが見つかりません」で中止されずに手順が進行することを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 対象フォルダの直下にはプロジェクトファイルが無く、1階層下のサブフォルダに `.sln` がある、**When**（動作） 対象フォルダを選んで「生成」をクリックする、**Then**（結果） 「対象のプロジェクトが見つかりません」で中止されず、後続の手順が実行される。
2. **Given**（前提） 対象フォルダの直下に `.sln` がある（従来どおりの構成）、**When**（動作） 対象フォルダを選んで「生成」をクリックする、**Then**（結果） これまでどおり検出され、後続の手順が実行される（既存動作に回帰がない）。

---

### User Story 2 - 無関係なフォルダは引き続き未検出として扱われる (Priority: P2)

開発者が、プロジェクトを一切含まない空のフォルダ（例: `empty01`）を対象フォルダとして選んだ場合、サブフォルダの探索を導入した後も、システムは引き続き「対象のプロジェクトが見つかりません」で中止する。

**Why this priority（この優先度である理由）**: サブフォルダを探索するように広げたことで、無関係なフォルダまで誤って「プロジェクトあり」と判定してしまう回帰を防ぐ必要がある。

**Independent Test（独立したテスト方法）**: `empty01` を対象フォルダとして選び、「生成」をクリックして、これまでどおり「対象のプロジェクトが見つかりません」で中止されることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 対象フォルダにもそのサブフォルダのどこにもプロジェクトマーカーが無い、**When**（動作） 対象フォルダを選んで「生成」をクリックする、**Then**（結果） 「対象のプロジェクトが見つかりません」で中止される。

---

### Edge Cases（エッジケース）

- 対象フォルダの配下に `.git` フォルダが既に存在する場合（例: 別のプロジェクトを一度Git管理した後の再実行）、その内部（`.git/` 配下）にたまたま `.sln` に類似したファイルがあっても、それをプロジェクトマーカーとして誤検出してはならない。
- 対象フォルダの配下に複数のサブフォルダがあり、そのうち1つだけにプロジェクトマーカーがある場合（他は無関係なフォルダ）でも、検出できなければならない。
- サブフォルダの階層がさらに深い場合（孫フォルダ、ひ孫フォルダ）でも検出できなければならない。
- 対象フォルダの配下に大量のファイル・フォルダがある場合（例: 既存の `.git` 履歴や依存ライブラリの復元済みフォルダを含む）でも、生成ボタンを押してから応答が返るまでの体感が損なわれてはならない。

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

- **FR-1701**: システムは、プロジェクトマーカー（`*.sln`・`*.vcxproj`・`*.csproj`・`package.json`）の存在確認を、対象フォルダの直下だけでなく、その配下のすべてのサブフォルダ（階層数を問わない）に対しても行わなければならない。
- **FR-1702**: システムは、対象フォルダ自身とその配下のいずれか1箇所でもマーカーが見つかれば、種別やその位置を区別せず「プロジェクトが検出された」として扱わなければならない（002 FR-103・FR-105 の「種別を区別しない」「複数種類の共存を警告しない」という方針を、探索範囲の拡大後も維持する）。
- **FR-1703**: システムは、マーカー検出のためのサブフォルダ探索において、`.git` フォルダの内部を探索対象から除外しなければならない（Git 自身の内部ファイルによる誤検出を避けるため）。
- **FR-1704**: マーカーがどのサブフォルダで見つかったかに関わらず、システムは以降の全ての処理（`.gitignore` の配置、Git 初期化、Spec Kit 足場の配置、`.claude` の展開、CLAUDE.md の生成など）を、利用者が選択した対象フォルダそのものに対して行わなければならない（対象フォルダをマーカーの場所へ差し替えない）。
- **FR-1705**: システムは、対象フォルダの配下にプロジェクトマーカーが一つも見つからない場合、これまでどおり「対象のプロジェクトが見つかりません」のメッセージで処理を中止しなければならない。

## Success Criteria（成功基準） *(必須)*

### Measurable Outcomes（測定可能な成果）

- **SC-1701**: Visual Studio のウィザードがプロジェクト名と同じサブフォルダを作ってプロジェクト一式を配置した場合、利用者はその一つ上のフォルダを選ぶだけで、これまでと同じ操作感でSDD化を完了できる。
- **SC-1702**: プロジェクトを含まない空のフォルダを選んだ場合、これまでどおり誤りなく「対象のプロジェクトが見つかりません」で中止される（誤検出が発生しない）。
- **SC-1703**: サブフォルダの探索を追加したことによる処理時間の増加が、通常の開発フォルダ規模（数百〜数千ファイル程度）において体感できるほどの遅延（数秒以上の待たされ感）を生まない。

## Assumptions（前提事項）

- 対象フォルダの配下に存在しうるサブフォルダの階層数・ファイル数は、通常のソフトウェア開発プロジェクトの規模（数百〜数千ファイル程度）を想定する。ドライブ全体のような桁違いに巨大なフォルダを対象フォルダとして選ぶ運用は想定しない。
- `.git` フォルダの内部を除外する以外に、探索対象から除外すべき特別なフォルダ（`node_modules`・`bin`・`obj` 等のビルド生成物）は、現時点では設けない。これらの内部にたまたまプロジェクトマーカーに類似したファイルが存在するケースは稀であり、YAGNI の原則により対応を見送る。将来問題が顕在化した場合に別フィーチャーで対応する。
- マーカーが複数のサブフォルダに分散して存在する場合（モノレポ的な構成）でも、いずれか1つが見つかった時点で「検出された」と判定してよく、すべてを列挙する必要はない（002 FR-105 の方針を踏襲）。
