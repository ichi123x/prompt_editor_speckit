## Notes

- 全16項目が合格。`/speckit-clarify` または `/speckit-plan` に進める状態。
- **スコープ確定の経緯**: 初版では「プロジェクト雛形の生成」を User Story 4（P3）として含め、その実現方式に `[NEEDS CLARIFICATION]` を付けていた。ユーザーの回答により、**雛形生成はスコープ外**と確定した。対象となるMFCアプリ／Webアプリはユーザーが任意のフォルダへ配置しておき、本ツールは種別を選択して「生成」を押すことで、その配置済みプロジェクトをSDD化する（＝SDDの土台を作る）役割に限定される。
  - これに伴い User Story 4 を削除し、代わりに「プロジェクト種別の選択」を User Story 1 の入力として組み込んだ（FR-003、FR-006〜FR-008、FR-010）。
  - さらにユーザーより「ひな形は使用しない。ターゲットプロジェクトは VS2022 などを使用してユーザーがウィザードで生成するのを条件とする」との確定を得た。これを受けて、FR-007 に「本ツールはプロジェクトの雛形を保持してはならず、いかなる方法でも雛形を生成してはならない」という否定形の要件を明記し、Assumptions に「ウィザードでの生成」を**前提条件**として記載した。
  - 否定形の要件として書いているのは、後工程（`/speckit-plan`・`/speckit-implement`）が善意で雛形生成機能を追加してしまうことを仕様上で禁じるためである。
- **テスト対象**: `C:\work\test\test01`（VS2022 のウィザードで生成された MFC ダイアログアプリ、SDD化前の状態）をユーザーが用意済み。Assumptions に記載し、User Story 1・2 の Independent Test から参照している。
  - 注意: このフォルダはソリューション一式が直下にあるため、SDD化後は `.specify`・`.claude` が `.sln` と同階層に並ぶ。手順書が推奨する「プロジェクトフォルダ ＞ ソリューションフォルダ」の2階層構成とは異なるが、Spec Kit の動作要件（開くフォルダに `.claude` があること）は満たす。この配置差を本ツールが区別しない点を Assumptions に明記した。
  - このフォルダは**破壊的に変更される**（`.git` 初期化と初回コミットが作られる）。べき等性（SC-002）の検証には初回実行後の状態をそのまま再利用できるが、初回実行前の状態を再現するには `.git`・`.gitignore`・`.specify`・`.claude` の削除が必要になる。
- **テスト方針**: ユーザーの指示により、「User Scenarios & Testing」配下に「テスト方針」節を追加した。静的テスト（ST-001〜ST-007、アプリを実行せず検査）と動的テスト（DT-001〜DT-009、ダイアログを操作して検査）の2層構成。
  - 静的テストを設けた理由は、本フィーチャーの処理が外部コマンド実行とファイルシステム変更を伴い、動的テストの実行コストと環境依存が大きいため。動的テストでしか確認できない項目を絞り込むことで再現性を高める。
  - ST-001（コンパイラ警告）・ST-002（コード解析）は MSBuild と Visual Studio の既存機能で実施でき、新たな依存関係を追加しない。憲法の技術的制約「自動テストスイートおよびlint設定が存在しない」に抵触しないよう、テストランナーの新規導入はスコープ外と Assumptions に明記した。
  - ST-003（仕様と実装の対応の追跡）は、憲法の原則IV「変更の追跡可能性」が定める「テストがない以上、spec と tasks の対応関係が変更妥当性を担保する一次情報源」という位置づけを、検査項目として具体化したもの。
- **フォルダ未選択時の「生成」押下**: ユーザーの指示により、独立した受け入れシナリオ（US1-4）と動的テストケース（DT-003）として明示した。
  - 初版では「フォルダまたは種別のいずれかが未選択」と1シナリオにまとめていたが、フォルダ未選択と種別未選択は表示すべきメッセージも検出タイミングも異なるため分割した（US1-4 / US1-5）。
  - 併せて、フォルダ選択後にキャンセルした場合に選択済みパスが保持されること（US1-6 / DT-005）を追加した。「未選択」の境界条件として、キャンセルが選択状態を消してしまう誤実装を検出するため。
  - DT-003 には確認項目(a)〜(e)を列挙した具体的手順を記載。特に (d)「メッセージを閉じた後も生成ボタンが無効化されたままにならない」は、FR-014 の二重実行防止（実行中のボタン無効化）と組み合わさったときに起きやすい不具合を狙っている。
- 準備完了チェックリストのうち機械的に断定できない項目（テスト方針、ビルド成否、CLAUDE.md と憲法の内容整合）は、「未達」ではなく「判定不能」として扱う方針を Assumptions に明記済み。
