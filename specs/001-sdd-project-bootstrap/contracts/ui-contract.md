**Feature**: 001-sdd-project-bootstrap
**Date**: 2026-09-08

**`IDC_LIST_RESULT` の列定義**（データモデルの ResultRow に対応）:

|---|---|---|
| 0 | 項目 | 40% |
| 1 | 結果 | 20% |
| 2 | 内容 | 40% |

## 2. ボタンの有効・無効の契約

`IDC_BUTTON_GENERATE` の有効・無効は、以下の規則に厳密に従う。DT-003 の確認項目(d)が検証する箇所である。

| タイミング | 状態 |
|---|---|
| ダイアログ初期化直後 | **有効** |
| 未選択エラーで早期リターンしたとき | **有効のまま**（無効化してはならない） |
| ワーカースレッド起動の直前 | 無効 |
| ワーカースレッドの完了通知を受信したとき | **有効に戻す**（成功・失敗・中断のいずれでも） |

**根拠**: FR-014（二重実行防止）はワーカースレッドが動作している間のみ適用される。未選択エラーは処理を開始しないため、ボタンを無効化する理由がない。ここを取り違えると、ユーザーがフォルダを選択してもボタンが押せなくなり、アプリケーションの再起動が必要になる。

**同様に `IDC_BUTTON_DIAGNOSE` も、導入処理の実行中は無効とする。** 診断は読み取り専用だが、導入処理中のフォルダを読むと途中経過を表示してしまい、SC-004 の「追加調査なしに判断できる」を損なうためである。

### 実行中に無効化するコントロール（全4種）

ワーカースレッドの動作中は、以下の**4つ**を無効化し、完了通知の受信時にすべて有効へ戻す。

| コントロールID | 無効化する理由 |
|---|---|
| `IDC_BUTTON_GENERATE` | 二重実行の防止（FR-014） |
| `IDC_BUTTON_DIAGNOSE` | 処理途中のフォルダを読んで中間状態を表示するのを防ぐ |
| `IDC_BUTTON_BROWSE` | **処理中に対象フォルダを変更されると、ワーカースレッドが処理しているフォルダと画面表示が食い違う** |
| `IDC_RADIO_KIND_MFC` / `IDC_RADIO_KIND_WEB` | **処理中に種別を変更されると、実行中の判定・`.gitignore` の選択と画面表示が食い違う** |

**根拠**: 仕様のエッジケース「処理の実行中にユーザーが別のフォルダを選び直したり、種別を変更したり、ボタンを連打したりしても、二重実行や不整合な状態が起きない」は、ボタンの連打（生成ボタン）だけでなく**フォルダの選び直しと種別の変更**を明示的に挙げている。生成・診断ボタンの無効化だけではこの要求を満たさない。

ワーカースレッドは起動時に対象フォルダパスと種別のコピーを受け取り、実行中はダイアログのメンバ変数を参照しない。無効化はこれと合わせた二重の防御であり、片方だけでは不足する（無効化のみでは将来の改修で漏れうる。コピーのみでは画面表示と実際の処理対象が食い違って見える）。

## 3. 操作フローの契約

### 3.1 「参照...」ボタン（FR-001, FR-002）

```
押下
 ├─ CFolderPickerDialog を表示
 ├─ [IDOK]     → IDC_EDIT_TARGET_PATH に選択された完全パスを設定
 └─ [IDCANCEL] → IDC_EDIT_TARGET_PATH を変更しない（US1-6）
```

**契約**: キャンセル時に表示中のパスを消去してはならない。一度選択したフォルダは、次に別のフォルダを選択して確定するまで保持される。

### 3.2 「生成」ボタン（FR-004〜FR-016）

検証は以下の順序で行う。いずれかで中止した場合、**ファイルシステムへの変更は一切行われない**。

```
押下
 │
 ├─ 1. フォルダ未選択？        → 「対象フォルダを選択してください。」で中止   [US1-4]
 ├─ 2. 種別未選択？            → 「プロジェクトの種別を選択してください。」で中止 [US1-5]
 ├─ 3. 書き込み権限なし？      → 権限不足の案内で中止                         [FR-015]
 ├─ 4. 選択種別のマーカーなし？
 │      ├─ 他方の種別のマーカーあり → 不一致の警告。[いいえ]なら中止          [FR-008]
 │      └─ どの種別のマーカーもなし → ウィザードでの生成を促して中止          [US1-7]
 ├─ 5. .specify と .claude の一方だけ存在？ → 警告して手動確認を促し中止       [Edge Case]
 ├─ 6. GitState = NestedUnderParent？ → 入れ子リポジトリの警告。[いいえ]なら中止 [FR-016]
 │
 ├─ 生成・診断・参照ボタンとラジオボタンを無効化（上記「実行中に無効化するコントロール」の4種）
 ├─ 対象フォルダパスと種別をワーカースレッドへコピーして渡す
 ├─ ワーカースレッドを起動し、5手順を順に実行
 │    各手順の完了ごとに PostMessage で1行を IDC_LIST_RESULT に追加
 └─ 完了通知の受信
      ├─ ボタンを有効に戻す
      └─ IDC_STATIC_GUIDE に次の手順の案内を表示                              [FR-022]
```

**契約**: 検証1〜6はすべて読み取りのみで行う。ワーカースレッドを起動するまで、対象フォルダに書き込みを発生させてはならない。

### 3.3 「準備状況を診断」ボタン（FR-017〜FR-021）

```
押下
 ├─ フォルダ未選択？ → 「対象フォルダを選択してください。」で中止
 ├─ 7項目を判定（すべて読み取り専用）
 ├─ IDC_LIST_RESULT に7行を表示
 └─ IDC_STATIC_GUIDE に未達項目に対する案内を表示
```

**契約**: 診断は対象フォルダに一切の書き込みを行わない（FR-020 / SC-005 / DT-008）。一時ファイルの作成も含めて禁止する。書き込み権限の確認（`TargetFolderState.IsWritable`）は一時ファイルの作成を伴うため、**診断では実施しない**。

## 4. メッセージ文字列の契約（ST-005）

ユーザーに表示するすべての文字列は日本語とする（憲法 原則II）。以下は最低限定義されなければならないメッセージである。

| 用途 | メッセージ | 対応 |
|---|---|---|
| フォルダ未選択 | 対象フォルダを選択してください。 | US1-4 / DT-003 |
| 種別未選択 | プロジェクトの種別を選択してください。 | US1-5 / DT-004 |
| 書き込み権限なし | 対象フォルダに書き込みできません。フォルダの権限を確認してください。 | FR-015 |
| マーカー不在 | 対象のプロジェクトが見つかりません。Visual Studio 2022 などのウィザードでプロジェクトを作成し、このフォルダに配置してから再実行してください。 | US1-7 |
| 種別の不一致 | 選択された種別と、フォルダ内のプロジェクトが一致しません。このまま続行しますか？ | FR-008 |
| 足場が中途半端 | `.specify` と `.claude` の一方だけが存在します。手動で確認してください。 | Edge Case |
| 入れ子リポジトリ | 親フォルダが既に Git リポジトリです。このまま初期化すると入れ子のリポジトリになります。続行しますか？ | FR-016 |
| コマンド不在 | `{コマンド名}` が見つかりません。インストールして PATH を通してから再実行してください。 | Edge Case |
| Git ユーザー未設定 | Git のユーザー設定（user.name / user.email）が必要です。 | R-006 |

**手順名と結果の表示文字列**（FR-011）:

| 内部値 | 表示 |
|---|---|
| `InstallUv` | uv の導入 |
| `InstallSpecify` | specify CLI の導入 |
| `InstallVsCodeExt` | VS Code 拡張の導入 |
| `InitSpecKit` | Spec Kit 足場の配置 |
| `InitGit` | Git 初期化と初回コミット |
| `Success` | 成功 |
| `Skipped` | スキップ |
| `SkippedUnmetDependency` | スキップ（前提未達） |
| `Failed` | 失敗 |

**判定結果の表示文字列**（FR-019）: `Met` → `達成`、`NotMet` → `未達`、`Indeterminate` → `判定不能`

### 完了時の案内（FR-022）

導入処理がすべて完了した後、`IDC_STATIC_GUIDE` に以下を表示する。

```
Spec Kit の導入が完了しました。次の手順は Claude Code との対話が必要です。
 1. VS Code で {対象フォルダ} を開く（.specify と .claude が直下に見えるフォルダ）
 2. Claude パネルで /init を実行し、CLAUDE.md を生成する
 3. テスト方針を決め、/speckit-constitution で憲章を制定する
 4. /init を再実行し、憲章を反映した CLAUDE.md に更新する
```

## 5. 外部コマンドのコントラクト

本ツールが起動する外部プロセスの一覧。すべて `CreateProcess` に標準出力・標準エラーのパイプを接続して実行する（R-001）。

| 目的 | コマンドライン | 成功の判定 | 作業ディレクトリ |
|---|---|---|---|
| uv の検出 | `uv --version` | 終了コード 0 | 任意 |
| uv の導入 | `winget install --id=astral-sh.uv -e` | 終了コード 0 | 任意 |
| specify の検出 | `specify version` | 終了コード 0 | 任意 |
| specify の導入 | `uv tool install specify-cli` | 終了コード 0 | 任意 |
| 拡張の検出 | `cmd.exe /c code --list-extensions` | 標準出力に `anthropic.claude-code` の行を含む | 任意 |
| 拡張の導入 | `cmd.exe /c code --install-extension anthropic.claude-code` | 終了コード 0 | 任意 |
| Spec Kit 足場 | `specify init . --integration claude --script ps --force --non-interactive` | 終了コード 0 | **対象フォルダ** |
| Git 状態 | `git rev-parse --is-inside-work-tree` | 終了コード 0 ならリポジトリ内 | **対象フォルダ** |
| Git ルート | `git rev-parse --show-toplevel` | 終了コード 0。出力をパスとして使う | **対象フォルダ** |
| コミット数 | `git rev-list --count HEAD` | 終了コード 0。出力を整数として使う | **対象フォルダ** |
| Git 初期化 | `git init` | 終了コード 0 | **対象フォルダ** |
| ステージング | `git add -A` | 終了コード 0 | **対象フォルダ** |
| 初回コミット | `git commit -m "Spec Kit 導入"` | 終了コード 0 | **対象フォルダ** |

**契約**:
- 作業ディレクトリの指定は `CreateProcess` の `lpCurrentDirectory` で行う。プロセス全体のカレントディレクトリ（`SetCurrentDirectory`）を変更してはならない。
- `specify init` には `--non-interactive` を必ず付ける。省略するとパイプ接続時にプロンプト待ちでハングする（R-005）。
- `specify init` には `--integration claude` を必ず付ける。省略すると非対話セッションでは Copilot が既定として選ばれる（R-005）。
- `specify init` には `--force` を必ず付ける。対象フォルダにはプロジェクトが配置済みで非空だからである（R-005）。
- すべての子プロセスは `CREATE_NO_WINDOW` で起動し、コンソールウィンドウを表示しない。
- 子プロセスの出力を読み出しながら終了を待つ。読み出さずに待つとパイプバッファが埋まってデッドロックする（R-001）。

## 6. 生成されるファイルのコントラクト（ST-006）

`.gitignore` は、選択された種別に応じた本体（埋め込みリソース）の末尾に、以下の2ブロックを追記した内容とする。

```
# ---- Spec Kit ----
# feature.json は作業中の機能を指すマシンローカルな状態。
# 複数PCで同じ機能を続けるなら、除外せずコミットする選択もある
# .specify/feature.json

# ---- このプロジェクト固有 ----
*.pdf
```

**契約**:
- 既存の `.gitignore` がある場合、本体は書き換えず、上記2ブロックのうち**未記載のものだけ**を末尾に追記する（FR-010）。
- 記載済みかどうかは、目印行 `# ---- Spec Kit ----` および `# ---- このプロジェクト固有 ----` の有無で判定する。
- 同じ操作を繰り返しても、ブロックが重複してはならない（FR-013 / ST-006）。
