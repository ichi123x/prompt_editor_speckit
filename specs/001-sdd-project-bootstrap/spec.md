# Feature Specification: SDDプロジェクトのベース作成ツール

**Feature Branch**: `ver.0.2`

**Created**: 2026-09-08

**Status**: Implemented

**Input**: User description: "既存の MFCApplication1 のダイアログを拡張し、「SDDプロジェクトのベース作成ツール」にする。ひな形は使用しない。ターゲットプロジェクト（MFCアプリまたはWebアプリ）は、ユーザーが VS2022 などのプロジェクトウィザードで生成し、任意のフォルダに配置しておくことを条件とする。本ツールではまず対象となる種別（Web か MFC か）を選択し、生成ボタンを押下すると、その配置済みプロジェクトをSDD化する。あくまでSDDの土台を作るツールである。対象範囲は (1) Spec Kit 導入と Git 初期化、(2) 準備完了チェックリストの判定、(3) 憲法・CLAUDE.md までの準備支援 の3つ。"

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - 配置済みプロジェクトを選んでSDD化する (Priority: P1)

開発者は、Visual Studio 2022 等のプロジェクトウィザードであらかじめ生成し、任意のフォルダに配置しておいたプロジェクト（MFCアプリまたはWebアプリ）に対して、本ツールで「参照」ボタンからそのフォルダをGUI選択し、対象の種別（MFCアプリ／Webアプリ）を選び、「生成」ボタンをクリックする。それだけで、uv・specify CLI・VS Code の Claude Code 拡張の導入確認とインストール、対象フォルダ直下への Spec Kit 足場（`.specify` / `.claude`）の配置、Gitリポジトリの初期化、選択した種別に応じた `.gitignore` の配置、初回コミットの作成までが連続して完了し、そのプロジェクトがSDDの土台を持った状態になる。各手順の結果は「成功」「スキップ」「失敗」として画面上で確認できる。

**Why this priority（この優先度である理由）**: 手順書で最も手数が多く、コマンドの打ち間違いや実行順序の誤りが起きやすい区間であり、これを自動化することが本フィーチャーの中心的価値である。このストーリー単独で「配置済みプロジェクトをSDD化する」という目的が完結し、他のストーリーが無くても実用的な価値を提供できる。

**Independent Test（独立したテスト方法）**: テスト対象フォルダ `C:\work\test\test01`（VS2022 のウィザードで生成された MFC ダイアログアプリ。Spec Kit も Git も未導入）を選択し、種別に「MFCアプリ」を選んで「生成」をクリックし、実行後にそのフォルダ直下へ `.specify`・`.claude`・`.git`・`.gitignore` が並び、コミットが1件以上作成されていることを確認するだけで、完全にテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 対象フォルダにMFCアプリのソリューションが配置済みで、uv・specify CLI・VS Code拡張・Spec Kit足場・Gitリポジトリのいずれも未導入である、**When**（動作） ユーザーがそのフォルダを選択し、種別に「MFCアプリ」を選んで「生成」をクリックする、**Then**（結果） 5つの手順がすべて実行され、対象フォルダ直下に `.specify`・`.claude`・`.git`・`.gitignore` が配置され、初回コミットが作成され、各手順が「成功」として一覧表示される。
2. **Given**（前提） 対象フォルダにWebアプリのプロジェクトが配置済みである、**When**（動作） ユーザーが種別に「Webアプリ」を選んで「生成」をクリックする、**Then**（結果） 同様に5つの手順が実行され、Webアプリに適した内容の `.gitignore` が配置される。
3. **Given**（前提） 一部の手順（例: uv と specify CLI の導入）が既に完了しているフォルダである、**When**（動作） ユーザーが同じフォルダと種別で再度「生成」をクリックする、**Then**（結果） 完了済みの手順は「スキップ」として表示され、未完了の手順のみが実行され、既存の環境は一切変更されない。
4. **Given**（前提） アプリケーション起動直後で、フォルダが一度も選択されておらずパス表示欄が空である、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 先にフォルダを選択するよう促すメッセージが表示され、導入手順は1つも実行されず、いかなるファイルも作成・変更されない。メッセージを閉じた後もダイアログは操作可能な状態を保ち、「生成」ボタンは無効化されたままにならない。
5. **Given**（前提） フォルダは選択済みだが種別が選択されていない、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 先に種別を選択するよう促すメッセージが表示され、導入手順は1つも実行されず、いかなるファイルも作成・変更されない。
6. **Given**（前提） 「参照」でフォルダを選択した後、フォルダ選択ダイアログを再度開いてキャンセルした、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 直前に選択済みのフォルダが対象として扱われ、未選択エラーにはならない。
7. **Given**（前提） 選択した種別に対応するプロジェクトが対象フォルダに存在しない、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） Visual Studio 2022 等のウィザードで対象プロジェクトを先に生成し、そのフォルダへ配置するよう促すメッセージが表示され、導入手順は実行されず、雛形も生成されない。
8. **Given**（前提） specify CLI のインストールがネットワーク不通により失敗する、**When**（動作） 導入処理が進行する、**Then**（結果） 当該手順が「失敗」として理由とともに表示され、それに依存する後続手順（Spec Kit 足場の配置）は実行されず「スキップ（前提未達）」として表示され、依存しない手順は続行される。

### User Story 2 - 準備完了チェックリストの達成状況を診断する (Priority: P2)

開発者は、対象フォルダを選択して「準備状況を診断」ボタンをクリックすると、SDDを開始するために揃っているべき7項目（ビルドが通る雛形がある／`.git`・`.gitignore`・`.specify`・`.claude` が同じ階層に並んでいる／コミットが1件以上ある／テスト方針が決まっている／憲法がある／CLAUDE.md が憲法を反映している／技術スタックが記録されている）について、それぞれ達成・未達・判定不能のいずれであるかと、未達項目に対して次に取るべき行動が一覧表示される。

**Why this priority（この優先度である理由）**: 導入手順を終えただけでは仕様駆動開発は回らず、残作業の把握が最初の `/speckit-specify` に踏み出せない主要因になる。対象フォルダを読むだけの副作用のない機能であり、User Story 1 が無くても単独で価値を持つ。

**Independent Test（独立したテスト方法）**: SDD化前のテスト対象フォルダ `C:\work\test\test01` と、User Story 1 でSDD化した後の同フォルダの2状態に対して「準備状況を診断」をクリックし、前者ではほぼ全項目が未達、後者では Spec Kit 導入とコミットに関する項目が達成へ変わり憲法・CLAUDE.md に関する項目が未達として残ること、かつどちらの実行でもフォルダに一切変更が加わらないことを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 7項目すべてを満たすフォルダである、**When**（動作） ユーザーが「準備状況を診断」をクリックする、**Then**（結果） 7項目すべてが「達成」として表示され、最初の `/speckit-specify` を実行してよい旨が示される。
2. **Given**（前提） Spec Kit 導入と初回コミットは済んでいるが憲法が未記入テンプレートのままのフォルダである、**When**（動作） ユーザーが「準備状況を診断」をクリックする、**Then**（結果） 憲法に関する項目が「未達」として表示され、次に取るべき行動として `/speckit-constitution` の実行が示される。
3. **Given**（前提） 任意のフォルダである、**When**（動作） 診断を実行する、**Then**（結果） 対象フォルダ内のファイルは一切作成・変更・削除されない。

### User Story 3 - 憲法・CLAUDE.md までの準備手順を案内される (Priority: P3)

診断で未達だった項目のうち、Claude Code との対話が必要で自動実行できないもの（テスト方針の決定、`/speckit-constitution` による憲法の制定、憲法を反映した `/init` の再実行、技術スタックの CLAUDE.md への記録）について、開発者は実行すべきコマンドとその順序を画面上で確認できる。案内はコマンドをそのまま Claude Code のパネルへ貼り付けられる形で提示される。

**Why this priority（この優先度である理由）**: これらは本ツールが代行できない、人間の判断を伴う工程である。案内があることで作業の抜けを防げるが、診断（User Story 2）が「次に取るべき行動」を示せていれば最低限の目的は満たされるため、優先度は下がる。

**Independent Test（独立したテスト方法）**: 憲法が未制定のフォルダを診断した状態で案内表示を開き、`/speckit-constitution` → `/init` → 技術スタック記録の順序と各コマンドが正しい順に提示されること、およびコマンド文字列をコピーできることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 憲法が未制定で CLAUDE.md も未作成のフォルダを診断済みである、**When**（動作） ユーザーが案内を表示する、**Then**（結果） テスト方針の決定 → `/speckit-constitution` → `/init` → 技術スタックの記録、の順に手順が提示される。
2. **Given**（前提） 憲法は制定済みだが CLAUDE.md が憲法より古いフォルダである、**When**（動作） ユーザーが案内を表示する、**Then**（結果） 既に完了している手順は完了として示され、`/init` の再実行以降のみが未完了の手順として提示される。

### Edge Cases（エッジケース）

- 「参照」のフォルダ選択ダイアログでユーザーがキャンセルした場合、表示中のフォルダパスは変更されない。
- 選択した種別と、対象フォルダに実際に配置されているプロジェクトの種別が食い違う場合（例: 「Webアプリ」を選んだがフォルダには `.sln` しか無い）、システムはその不一致を警告として表示し、ユーザーの確認を得ずに導入手順を実行しない。
- 対象フォルダに `.specify` と `.claude` の一方だけが存在する（中途半端な状態）場合、システムはその旨を警告として表示し、上書きせず手動確認を促す。
- 対象フォルダに既に `.git` が存在するがコミットが1件も無い場合、システムはGit初期化を「スキップ」とし、初回コミットの作成のみを行う。
- 対象フォルダが**既にコミット済みのリポジトリで、かつユーザーの未コミット変更が存在する**場合、システムはそれらの変更を巻き込んでコミットしてはならない。この状況は、`.gitignore` に追記ブロックが欠けているために Git 手順が再実行される場合に起こりうる。システムは未コミット変更の有無を確認し、存在する場合は `.gitignore` の変更のみをコミットするか、ユーザーに確認を求める。
- 対象フォルダが既存リポジトリのサブフォルダである場合（親階層に `.git` がある場合）、入れ子リポジトリになる旨を警告し、Git初期化を実行する前にユーザーへ確認する。
- `.gitignore` が既に存在する場合、システムは既存の内容を上書きせず、Spec Kit 用およびプロジェクト固有の追記ブロックが未記載であれば末尾に追記する。追記済みであれば何もしない。
- `winget`・`git`・`code` コマンドが PATH 上に存在しない場合、システムは該当手順を「失敗」とし、そのコマンドが必要である旨を案内する。
- PowerShell の実行ポリシーによって内部で呼び出すコマンドがブロックされた場合、システムは実行ポリシーを自動変更せず、対処方法を案内するに留める。
- 処理の実行中にユーザーが別のフォルダを選び直したり、種別を変更したり、ボタンを連打したりしても、二重実行や不整合な状態が起きない。
- 対象フォルダに対する書き込み権限が無い場合、システムは処理を開始する前に検出し、権限不足である旨を案内して何も変更しない。
- 「テスト方針が決まっている」のように機械的に断定できない項目は、「未達」ではなく「判定不能（人間の確認が必要）」として、達成・未達と区別して表示する。

### テスト方針

本フィーチャーの検証は、**静的テスト**（アプリケーションを実行せずに行う検査）と**動的テスト**（実際にダイアログを操作して行う検査）の2層で構成する。静的テストを設けるのは、本フィーチャーの処理が外部コマンドの実行とファイルシステムの変更を伴い、動的テストの実行コストと環境依存が大きいためである。動的テストで確認するしかない項目を絞り込むことで、検証の再現性を高める。

#### 静的テスト（アプリケーションを実行せずに検査する）

- **ST-001 コンパイラ警告の検査**: MSBuild による Debug/Release × x64/Win32 の全構成のビルドが、新規追加コードに起因する警告を出さずに完了すること。
- **ST-002 コード解析の検査**: Visual Studio のコード解析（静的解析）を新規追加コードに対して実行し、未初期化変数・リソースリーク・バッファ関連の指摘が出ないこと。
- **ST-003 仕様と実装の対応の検査**: 新規追加した各関数・各分岐が、どの機能要件（FR-001〜FR-022）に対応するかをコード上で追跡できること。憲法の原則IV（変更の追跡可能性）に基づき、テストスイート不在を補う一次的な検証手段として位置づける。
- **ST-004 UIリソースの検査**: ダイアログのリソース定義（コントロールID、タブ順序、ラベル文字列）が、FR-001・FR-003・FR-004・FR-017 が要求するコントロールをすべて備えていること。リソースファイルの内容検査のみで確認できる。
- **ST-005 文字列リソースの検査**: ユーザーに表示するすべてのメッセージが日本語であること（憲法の原則II）。また、未選択・不在・失敗の各ケースに対応するメッセージが定義されていること。
- **ST-006 生成物の内容検査**: 動的テスト実行後に生成された `.gitignore` を、アプリケーションを介さずファイルとして開き、Visual Studio 用の内容・Spec Kit 用の追記ブロック・プロジェクト固有の追記ブロックがすべて含まれ、かつ重複していないことを確認する（FR-010）。
- **ST-007 コミット内容の検査**: 動的テスト実行後のリポジトリを `git` コマンドで検査し、初回コミットに `.vs/`・`*.vcxproj.user`・`*.aps` 等の作業ファイルが含まれていないことを確認する。

#### 動的テスト（ダイアログを操作して検査する）

対象フォルダは `C:\work\test\test01` を用いる。

| No. | 検証内容 | 対応する受け入れシナリオ |
|---|---|---|
| DT-001 | フォルダ・種別ともに正しく選択してSDD化が完走する | US1-1 |
| DT-002 | SDD化済みフォルダへの再実行で全手順が「スキップ」になる（べき等性） | US1-3 |
| DT-003 | **フォルダ未選択のまま「生成」を押下する** | US1-4 |
| DT-004 | 種別未選択のまま「生成」を押下する | US1-5 |
| DT-005 | フォルダ選択後にキャンセルしても選択済みパスが保持される | US1-6 |
| DT-006 | 対象プロジェクトが存在しないフォルダで「生成」を押下する | US1-7 |
| DT-007 | 選択種別とフォルダ内容の不一致を検出する | Edge Case |
| DT-008 | 診断が読み取り専用である（実行前後でフォルダが不変） | US2-3 |
| DT-009 | SDD化の前後で診断結果が正しく変化する | US2-1, US2-2 |

**DT-003（フォルダ未選択での「生成」押下）の詳細手順**: アプリケーションを起動し、「参照」を一度も押さずにパス表示欄が空であることを確認したうえで「生成」を押下する。確認すること — (a) フォルダ選択を促す日本語メッセージが表示される、(b) 導入手順が1つも実行されない（結果表示欄に手順が並ばない）、(c) `C:\work\test\test01` を含むいかなるフォルダにもファイルが作成・変更されない、(d) メッセージを閉じた後もダイアログが操作可能で「生成」ボタンが無効化されたままにならない、(e) アプリケーションが異常終了しない。

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

**対象の選択（User Story 1）**

- **FR-001**: システムはダイアログ上に、フォルダ選択ダイアログを開くための「参照」ボタンを提供しなければならない。
- **FR-002**: フォルダが選択されると、システムはそのフォルダの完全パスをダイアログ上に表示しなければならない。選択がキャンセルされた場合、表示は変更されない。
- **FR-003**: システムはダイアログ上に、対象プロジェクトの種別（MFCアプリ／Webアプリ）をユーザーが選択できる手段を提供しなければならない。
- **FR-004**: システムはダイアログ上に、SDD化を実行するための「生成」ボタンを提供しなければならない。
- **FR-005**: フォルダまたは種別のいずれかが未選択の状態で「生成」がクリックされた場合、システムは不足している選択を促すメッセージを表示し、以降の処理を実行してはならない。

**SDD化の実行（User Story 1）**

- **FR-006**: 「生成」がクリックされると、システムはまず対象フォルダ配下に、選択された種別に対応するプロジェクトマーカー（MFCアプリなら `.sln`、Webアプリなら `package.json`・`.csproj` など）が1つ以上存在するかを確認しなければならない。
- **FR-007**: 選択された種別に対応するプロジェクトが存在しない場合、システムは Visual Studio 2022 等のプロジェクトウィザードで対象プロジェクトを先に生成・配置するよう促すメッセージを表示し、以降の導入手順を実行してはならない。**本ツールはプロジェクトの雛形を保持してはならず、いかなる方法でも雛形を生成してはならない。**
- **FR-008**: 対象フォルダに配置されているプロジェクトの種別が、ユーザーの選択した種別と食い違う場合、システムは不一致を警告として表示し、ユーザーの確認を得るまで導入手順を実行してはならない。
- **FR-009**: 対象プロジェクトの存在が確認できた場合、システムは以下の5手順を順に確認・実行しなければならない。各手順は既に完了している場合、実行せず「スキップ」としなければならない。
  1. uv の導入確認とインストール
  2. specify CLI の導入確認とインストール
  3. VS Code の Claude Code 拡張の導入確認とインストール
  4. 対象フォルダ直下への Spec Kit 足場（`.specify` / `.claude`）の配置
  5. Gitリポジトリの初期化、`.gitignore` の配置、初回コミットの作成
- **FR-010**: システムは配置する `.gitignore` の内容を、選択された種別に応じて決定しなければならない。いずれの種別でも、Spec Kit 用の追記ブロック（`.specify/feature.json` の扱いに関する記述を含む）とプロジェクト固有の追記ブロックを含めなければならない。既存の `.gitignore` がある場合は上書きせず、未記載のブロックのみを末尾に追記しなければならない。
- **FR-011**: システムは各手順の実行結果を「成功」「スキップ」「失敗」のいずれかとして、理由とともにユーザーがダイアログ上で確認できる形で表示しなければならない。
- **FR-012**: いずれかの手順が失敗した場合、システムはその手順に依存する後続手順を実行せず「スキップ（前提未達）」として表示し、依存しない手順は続行しなければならない。
- **FR-013**: システムは同一フォルダに対して導入処理が複数回実行されても、既に完了している手順を壊したり重複実行したりしてはならない（べき等性）。
- **FR-013a**: Git 手順を実行する際、システムは対象リポジトリに既存の未コミット変更が無いかを確認しなければならない。存在する場合、システムはそれらをコミットに含めてはならず、自らが作成・変更したファイルのみをステージするか、ユーザーに確認を求めなければならない。
- **FR-014**: システムは処理の実行中、二重実行を防止しなければならない（例: 実行中は該当ボタンを無効化する）。
- **FR-015**: システムは処理を開始する前に対象フォルダへの書き込み権限を確認し、権限が無い場合は何も変更せずに案内メッセージを表示しなければならない。
- **FR-016**: システムは、対象フォルダの親階層に既存のGitリポジトリが存在する場合、入れ子リポジトリになる旨を警告し、Git初期化を実行する前にユーザーの確認を求めなければならない。

**準備完了チェックリストの診断（User Story 2）**

- **FR-017**: システムはダイアログ上に、対象フォルダの準備状況を診断するボタンを提供しなければならない。
- **FR-018**: 診断は以下の7項目それぞれについて、「達成」「未達」「判定不能」のいずれかを判定して表示しなければならない。
  1. ビルドが通る雛形がある
  2. `.git`・`.gitignore`・`.specify`・`.claude` が対象フォルダ直下に並んでいる
  3. コミットが1件以上ある
  4. テスト方針が決まっている
  5. 憲法がある（未対応のプレースホルダーやTODOがゼロである）
  6. CLAUDE.md が憲法を反映している
  7. 技術スタック（言語・ビルド構成・テストランナー）が記録されている
- **FR-019**: システムは「未達」と判定した各項目について、次に取るべき行動を具体的に表示しなければならない。
- **FR-020**: 診断処理は読み取り専用でなければならず、対象フォルダ内のファイルを作成・変更・削除してはならない。
- **FR-021**: システムは機械的に断定できない項目を「未達」ではなく「判定不能」として、達成・未達と区別して表示しなければならない。

**準備手順の案内（User Story 3）**

- **FR-022**: システムは、自動実行できない工程（テスト方針の決定、`/speckit-constitution`、`/init` の再実行、技術スタックの CLAUDE.md への記録）について、実行すべきコマンドと順序を表示しなければならない。既に完了している工程は完了として区別して示さなければならない。

### Key Entities（主要エンティティ）

- **対象プロジェクトフォルダ**: ユーザーがGUIで選択した1つのフォルダ。完全パス、検出されたプロジェクトマーカー、Spec Kit足場の有無、Gitリポジトリの状態（初期化済みか、コミット件数）、親階層のリポジトリの有無、書き込み権限の可否を持つ。本フィーチャーのすべての操作はこのフォルダを対象とする。
- **プロジェクト種別**: ユーザーが選択する対象の種別。「MFCアプリ」または「Webアプリ」の2種。それぞれ、その種別を判別するプロジェクトマーカーと、配置すべき `.gitignore` の内容を持つ。本ツールは種別に応じた判定と設定を行うだけで、その種別の雛形を生成することはない。
- **セットアップ手順**: SDD化処理を構成する個々の工程。名称、実行順序、依存する先行手順、完了しているかの判定条件、実行結果（成功・スキップ・失敗）、結果の理由を持つ。
- **準備完了チェック項目**: 診断が判定する7項目のそれぞれ。項目名、完了条件、判定結果（達成・未達・判定不能）、未達時に次に取るべき行動を持つ。

## Assumptions（前提事項）

- 本機能は既存の `MFCApplication1` のダイアログに追加する（新規の別アプリは作らない）。
- **プロジェクトの雛形生成は本フィーチャーのスコープ外である。本ツールは雛形を一切持たず、生成もしない。** 対象となるMFCアプリ／Webアプリは、ユーザーが Visual Studio 2022 等の統合開発環境のプロジェクトウィザードを用いて生成し、任意のフォルダへ配置しておくことを**前提条件**とする。本ツールが行うのは、その配置済みプロジェクトをSDDの土台を持った状態にすることのみである。
- ウィザードで生成する理由は、MFC の `.vcxproj` / `.rc` / `resource.h` が ID 番号レベルで整合している必要があり、ウィザード以外の手段では最初のビルドが通らないためである。ウィザードでの生成時は、Git リポジトリをソリューション側に作らない設定とし（入れ子リポジトリの回避）、生成直後に一度ビルドを通しておくことが望ましい。
- **テスト対象フォルダ**: 本フィーチャーの動作確認には `C:\work\test\test01` を使用する。これは Visual Studio 2022（v17）のウィザードで生成された MFC ダイアログアプリケーションであり、`test01.sln`・`test01.vcxproj`・`test01.rc`・`Resource.h` 等が**フォルダ直下に**配置されている。検証開始時点では `.git`・`.gitignore`・`.specify`・`.claude` のいずれも存在しない、SDD化前の状態である。
- 上記テストフォルダはソリューション一式がフォルダ直下にあるため、SDD化を実行すると `.specify`・`.claude`・`.gitignore` が `.sln` と同じ階層に並ぶ。この配置でも Spec Kit は正しく動作する（Claude Code が開くフォルダに `.claude` があればよい）。本ツールは選択されたフォルダを常にリポジトリのルートとして扱い、ソリューションが直下にあるか1階層下にあるかを区別しない。
- **テストの実施形態**: 静的テスト（ST-001〜ST-007）・動的テスト（DT-001〜DT-009）はいずれも手順として定義された検査であり、自動テストランナーによる実行は本フィーチャーのスコープ外とする。憲法の技術的制約が「自動テストスイートおよびlint設定が存在しない」と記載しているとおり、本リポジトリにテストランナーを新規導入することはしない。静的テストのうち ST-001・ST-002 は MSBuild と Visual Studio のコード解析という既存ツールで実施でき、新たな依存関係を追加しない。
- テスト実行時、対象フォルダには Visual Studio が生成する作業ファイル（`.vs/`・`*.vcxproj.user`・`*.aps` 等）が含まれる。これらは Visual Studio 用 `.gitignore` の対象であり、初回コミットには含まれないことが期待される。
- 対象OSはWindowsである。フォルダ選択には標準的なWindowsのフォルダ選択ダイアログを使用する。
- 対象フォルダは1つだけであり、複数フォルダの一括処理は本フィーチャーのスコープ外とする。
- プロジェクト種別は「MFCアプリ」と「Webアプリ」の2種とする。それ以外の種別（コンソールアプリ等）への対応は本フィーチャーのスコープ外とする。
- 種別ごとのプロジェクトマーカーは、MFCアプリが `.sln`（および `.vcxproj`）、Webアプリが `package.json`・`.csproj` などとする。
- 準備完了チェック項目1「ビルドが通る雛形がある」は、実際のビルドを実行して確認しない。実ビルドは所要時間と外部ツール依存が大きいためスコープ外とする。判定は次のとおり確定する — **プロジェクトマーカーが存在すれば「達成」、存在しなければ「判定不能」**。マーカーがあってもビルドが実際に通るかは確認していないため、この「達成」はマーカーの存在を示すものであり、ビルドの成功を保証しない旨を表示に併記する。
- 準備完了チェック項目4「テスト方針が決まっている」は機械的に断定できないため、憲法内にテスト方針に関する記述が存在するかどうかを手がかりとし、断定できない場合は「判定不能」とする。
- 準備完了チェック項目6「CLAUDE.md が憲法を反映している」は、内容の実質的な整合を判定せず、ファイルの更新時刻で判定する。判定は次のとおり確定する — **CLAUDE.md が存在しなければ「未達」、存在して更新時刻が憲法より新しければ「達成」、存在するが憲法より古ければ「未達」**。ファイル時刻は Git のチェックアウトやファイルコピーで容易に変わるため、時刻に基づく参考判定である旨を表示に併記する。
- 準備完了チェック項目7「技術スタックが記録されている」は、CLAUDE.md 内に言語・ビルド構成・テストランナーに相当する記述が存在するかどうかで判定する。
- `/speckit-constitution` と `/init` は Claude Code との対話が必要なため自動実行せず、実行の案内のみを行う。
- Gitのユーザー設定（`user.name` / `user.email`）は設定済みであることを前提とし、本機能では変更しない。
- PowerShell の実行ポリシーは自動変更しない。ブロックされた場合は対処方法の案内に留める。
- Spec Kit 足場の配置には specify CLI の初期化機能を利用し、エージェント指定は Claude Code 向けとする。
