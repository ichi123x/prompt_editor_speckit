# Feature Specification: 高DPI環境でレイアウトが崩れない

**Feature Branch**: `015-support-high-dpi`

**Created**: 2026-09-14

**Status**: Implemented

**Input**: User description: "高DPI環境(Windowsのディスプレイ拡大率125%/150%/200%等)で本アプリのダイアログを起動した際、UIコントロール(フォルダパス表示欄、ボタン、ラベル等)が正しいサイズ・配置で表示されるようにする。背景: 006(readable-at-startup)のクラリファイ時、パス表示欄の折り返し対応(FR-504a)を検討する中でDPI対応の必要性が判明したが、対応範囲が大きいため006のスコープからは除外し、後続の別機能で対応することになっていた。本機能はその後続対応にあたる。現状の課題: 標準DPI(100%)以外の設定で実行した場合、コントロールの重なり・文字切れ・ウィンドウサイズとコントロール配置のバランス崩れが起こりうる。求める振る舞い: 主要なDPIスケール(100%/125%/150%/200%)でダイアログのレイアウトが崩れずに表示されること／テキストが可読なサイズで表示されること／マルチモニタ環境で異なるDPI設定のディスプレイ間をウィンドウが移動した場合も表示が破綻しないこと。対象外: DPIスケーリングの基盤対応(per-monitor DPI awareness化)を主眼とし、006で先送りされたパス折り返し表示そのものの実装は本機能の対象外とする。"

## 001〜014 との関係

本フィーチャーは**アプリが起動・表示される表示環境そのもの**を扱う。手順・文言・追従方針・配色には触れない。

| 既存の要件 | 本フィーチャーでの扱い |
|---|---|
| 001〜005・007〜014 | 変更しない |
| 006 FR-501〜513（起動直後の可読性） | **前提を検証・拡張する**。006 の寸法は開発機（115 DPI）でのみ実測されていた |

006 の `/speckit-clarify`（2026-09-10・2026-09-11）で、表示スケールとフォントへの対応は「後続の別機能で扱う」と2度先送りされている。本機能はその後続対応にあたる。ただし、いったん007として仕様化を試みた際に実測の結果ほぼ全て充足済みと判明し取り下げた経緯があり（`specs/006-readable-at-startup/checklists/ux.md` の「2026-09-11 の調査結果」に記録）、本機能でも**着手前に現状を再実測**した。

## 現状の実測値（2026-09-14 に実施）

### 1. アプリは既に `SYSTEM_DPI_AWARE` である

`.vcxproj` に DPI の明示設定は無いが、MSBuild の既定によりビルド時のマニフェストに `<dpiAware>true</dpiAware>` が自動で埋め込まれる。ビルド済み exe の埋め込みマニフェストと `GetProcessDpiAwareness` で確認済み（値 `1` = `SYSTEM_DPI_AWARE`）。`PerMonitorV2` の宣言は無い。

### 2. 固定DPIでの起動は、100%〜150%相当まで比率計算により破綻しない

`SYSTEM_DPI_AWARE` のアプリは、DLU→px 変換に実際のフォント計量を使うため、ログオン時のシステムDPIに応じてコントロールも文字も**同じ倍率で**拡大される。列幅比率 `kColumnRatio = {20, 17, 63}`（004 FR-308・006 FR-509）は除算ではなく比率で再計算されるため、DPI が変わっても維持される。

9pt フォントを各DPI相当のピクセルサイズで生成し、現在（013までの変更を含む）の最長文字列を実測:

| DPI（スケール） | 項目列 最長必要幅 | 結果列 最長必要幅 | 内容列 最長必要幅 |
|---|---|---|---|
| 96（100%） | 143 px | 100 px | 441 px |
| **115（120%、開発機）** | 178 px | 126 px | 552 px |
| 120（125%） | 178 px | 126 px | 552 px |
| 144（150%） | 214 px | 151 px | 662 px |
| 192（200%） | 286 px | 200 px | 881 px |

列も同じ倍率で拡大するため、比率の計算自体は200%相当でも数値上は成立する。ただし200%は Q2 の結論により保証範囲外（FR-1502）とし、参考値として記載するに留める（実測方法は [research.md](./research.md) に記載予定）。

### 3. ただし、開発機の実DPI(115)において「項目」列の余裕がすでに枯渇している

006 は列内部の余白を「実測不可のため20px + 安全余裕8pxを見積もる」という基準を定めていた（006 FR-501, research.md R-505）。013（`/init` 自動化）で6番目の手順名 `CLAUDE.md の生成とコミット` が追加されたことにより、この基準で測ると:

```
項目列の実幅（現状）: 185 px
項目列の必要文字幅　: 178 px（新しい最長: CLAUDE.md の生成とコミット）
006 基準の必要幅　　: 178 + 20(余白) + 8(安全余裕) = 206 px
現在の余裕　　　　　: 185 − 206 = -21 px（基準未達）
```

**これは DPI に起因しない、006 完了後の013で生じた既存の回帰である。** 100% 未満の環境（開発機の115 DPI）で既に発生しているため、DPI を上げるほど絶対ピクセル数としては比率的に拡大し続ける一方、この不足分もまた同じ比率で拡大する（是正されない）。本フィーチャーの前提条件として是正する（FR-1505）。

### 4. 未検証・本フィーチャーの主眼になりうる領域: マルチモニタでの DPI 変更

`SYSTEM_DPI_AWARE` のアプリは、**ウィンドウ生成後にモニタ間を移動してDPIが変わっても再描画されない**。Windows が「ログオン時のDPIで描画されたビットマップ」を新しいDPIに合わせて引き伸ばす（ビットマップストレッチ）ため、文字がぼやける。レイアウト比率が崩れるわけではないが、鮮明さは失われる。この挙動は `PER_MONITOR_AWARE_V2` を宣言し `WM_DPICHANGED` を処理して初めて解消する。現時点でこの実装は無い。

## Clarifications

### Session 2026-09-14

- Q: マルチモニタでDPIが異なる場合、何を保証しますか? → A: 対応しない。既知の制限として明記し、ビットマップの引き伸ばし（ぼやけ）を許容する
- Q: 200%までを保証範囲に含めますか? → A: 100%〜150%を保証範囲とする。200%は既知の制限として記載する
- Q: 013由来の「項目」列の余裕枯渇を、本フィーチャーで直しますか? → A: 本フィーチャーの前提条件として先に直す

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - 固定スケールで起動しても崩れない (Priority: P1)

利用者は自分のPCの表示スケールを125%や150%に設定しており、電源を入れ直してもその設定のまま使い続けている（＝アプリ起動中にスケールが変わることはない）。この状態で本ツールを起動し、結果一覧と完了案内を読む。

**Why this priority（この優先度である理由）**: 実測の結果、この経路は比率計算によりほぼ機能している。**証跡を検証手順として固定し、将来の変更（新しい手順の追加等）で壊れたことを検出できるようにする**ことが主目的である。

**Independent Test（独立したテスト方法）**: 96/115/120/144/192 DPI相当（100%/120%/125%/150%/200%）のフォント計量でコントロールの必要幅を再計算し、実際の列幅・案内欄寸法が各スケールで文字列を収められることを確認する。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given** 表示スケール100%相当、**When** 結果一覧・完了案内を表示する、**Then** すべての列・案内欄が対応する最長文字列を、006 が定める安全余裕とともに収める
2. **Given** 表示スケール125%・150%相当、**When** 同様に確認する、**Then** 同じく収める（200%は保証対象外。FR-1502）
3. **Given** いずれのスケールでも、**When** ウィンドウを見る、**Then** コントロール同士が重ならない
4. **Given** いずれのスケールでも、**When** 文字を見る、**Then** ビットマップ引き伸ばしによるぼやけが無い（固定スケールでの起動である限り、ビットマップ引き伸ばしは発生しないはずだが、実機で確認する）

---

### User Story 2 - モニタ間を移動しても表示が破綻しない (Priority: P2)

利用者はノートPCを外部モニタに接続しており、ノート内蔵ディスプレイ（150%）と外部モニタ（100%）でDPIが異なる。アプリを起動したままウィンドウをモニタ間でドラッグする。

**Why this priority（この優先度である理由）**: US1 と異なり、これは実装が存在しない領域である。ただし影響を受けるのは複数モニタで異なるDPIを使っている利用者に限られ、全利用者に及ぶ US1 より優先度は下がる。

**Independent Test（独立したテスト方法）**: 異なるDPIに設定した2つのモニタ間でウィンドウを移動させ、文字の鮮明さとレイアウトの崩れの有無を確認する。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given** DPIの異なる2つのモニタがある環境、**When** アプリのウィンドウを一方から他方へドラッグする、**Then** レイアウトは崩れない（比率は保たれる）が、Windowsによるビットマップ引き伸ばしのため文字がぼやけることがある。これは既知の制限として許容する（FR-1504）
2. **Given** 移動後の状態、**When** 結果一覧・完了案内を見る、**Then** US1 と同じ基準で全文が読める

---

### Edge Cases（エッジケース）

- **150%を超える表示スケール**: 200%を含め、保証対象外とする（FR-1502）。表示は破綻しうるが、致命的なクラッシュは起きないことのみ確認する
- **項目列の既存の余裕枯渇（013由来）**: DPIとは独立した既存の回帰。本フィーチャーの前提条件として是正する（FR-1505）
- **フォントの置き換わり**: 006 の調査で対応しないと決定済み（`MS UI Gothic` が無い環境は対象外、日本語環境専用として扱う）。本フィーチャーでも変更しない
- **モニタ間移動中（ドラッグ中）の一時的な表示**: 移動完了後の定常状態のみを対象とし、ドラッグ中の過渡的な見た目は対象外とする

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

- **FR-1501**: 表示スケール100%〜150%相当で起動した場合、結果一覧の3列と完了案内・初期案内が、利用者のウィンドウ操作なしで最後まで読めなければならない（006 FR-501〜511 の保証範囲をこの範囲まで検証・固定する）
- **FR-1502**: 保証する表示スケールの範囲は**100%〜150%**とする。200%は既知の制限として明記し、保証対象外とする（Clarification 2026-09-14）
- **FR-1503**: 固定スケールでの起動時、コントロール同士が重ならず、枠からはみ出してはならない
- **FR-1504**: マルチモニタ環境でDPIの異なるディスプレイ間をウィンドウが移動したとき、本フィーチャーでは per-monitor DPI awareness 化を行わない。Windows による表示のビットマップ引き伸ばし（ぼやけ）は既知の制限として許容し、`spec.md` に明記する（Clarification 2026-09-14）。将来 per-monitor 対応が必要になった場合は、別のフィーチャーとして立てる
- **FR-1505**: 013で追加された手順名により発生した「項目」列の安全余裕の枯渇（開発機実測で-21px）は、本フィーチャーの前提条件として是正しなければならない（Clarification 2026-09-14）。「項目」「結果」「内容」の3列は、それぞれの現在の最長文字列に対して006 FR-501 が定める安全基準（余白20px以上＋余裕8px以上）を満たさなければならない。是正に必要な列幅比率・ダイアログ幅の具体値は計画時に算出する
- **FR-1506**: 001〜014 の機能（5〜6手順、検証チェーン、`.gitignore` のべき等な生成、案内の複写、リサイズ追従、タイトルバーの着色）を変更してはならない
- **FR-1507**: フォントの置き換わりへの対応は006の決定（対応しない）を維持し、本フィーチャーでは変更しない
- **FR-1508**: 追加・変更した各箇所には、対応する FR 番号をコメントで記載しなければならない（憲章 原則IV）
- **FR-1509**: 本フィーチャーで行う判定・実測は、目視ではなく実測に基づかなければならない（憲章 原則V）

## Success Criteria（成功基準） *(必須)*

### Measurable Outcomes（測定可能な成果）

- **SC-1501**: 保証範囲内の表示スケールのいずれでも、利用者はウィンドウ操作0回で結果一覧の内容と完了案内を最後まで読める
- **SC-1502**: 保証範囲内の表示スケールのいずれでも、コントロールの重なり・はみ出しが無い
- **SC-1503**: 判定は目視ではなく、実行中のダイアログから取得した値（列幅・クライアント矩形・文字列の描画幅）をピクセルで比較して行う
- **SC-1504**: 001〜014 で合格していた検証項目が、開発機の環境（115 DPI）においてすべて再現する
- **SC-1505**: ビルド警告が0件で、コード分析の指摘が0件

## Assumptions（前提事項）

- **実行中の表示スケール変更（同一モニタ内でのユーザーによる設定変更）は US2 の範囲に含めない**。US2 はモニタ間の移動のみを扱う。設定変更はサインアウトを伴うのが通例であり、そのまま再ログオンした場合はUS1の固定スケール起動と同じ扱いになる
- **文字を小さくして詰め込む方法は採らない**（006 から継承）
- **メッセージの文言を短くして解決しない**（006 FR-511 を継承）
- **測定はGDIの `TextRenderer.MeasureText` で行い、フォントサイズをDPI相当のピクセル値で生成することで、実機の表示スケール変更（サインアウトを要する）を伴わずに検証する**（既存機能007の調査で確立した方法を踏襲）
