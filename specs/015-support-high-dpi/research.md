# Phase 0 リサーチ: 高DPI環境でレイアウトが崩れない

**Feature**: 015-support-high-dpi
**Date**: 2026-09-14

本書の結論はすべて**実測**に基づく（憲章 原則V）。ビルド済みexeが013までの変更を反映していない**古いもの**だった（2026/09/11ビルド）ため、まず再ビルドしてから測り直した。

**測定環境**: Windows 11 Pro／開発機の実DPI 115（実測、`GetDpiForWindow`）／ダイアログフォント `MS UI Gothic` 9pt

---

## R-1501: アプリの現在のDPI認識レベル

**測定**: `GetProcessDpiAwareness` で値 `1`（`SYSTEM_DPI_AWARE`）。ビルド済みexeの埋め込みマニフェストにも `PerMonitorV2` の宣言は無い。`.vcxproj` に明示設定は無く、MSBuildの既定で `<dpiAware>true</dpiAware>` が自動挿入されている。

**Decision**: このレベルを変更しない（FR-1504 により per-monitor 化はしないと決定済み）。

---

## R-1502: 固定DPIでの拡大縮小は比率計算により成立する（96〜144 DPI）

`SYSTEM_DPI_AWARE` のアプリは、DLU→px 変換に実際のフォント計量を使うため、ログオン時のシステムDPIに応じてコントロールも文字も同じ倍率で拡大される。9pt フォントをDPI相当のピクセルサイズ（`pxSize = 9.0 * dpi / 72.0`）で生成し、`TextRenderer.MeasureText` で計量する手法は、機能007（取り下げ済み）の調査で確立し、CLAUDE.mdに記録済みの方法をそのまま踏襲した。

**測定（013までの現在の最長文字列）**:

| DPI（スケール） | 項目列 描画幅 | 結果列 描画幅 | 内容列 描画幅 |
|---|---|---|---|
| 96（100%） | 143 px | 100 px | 441 px |
| 115（120%、開発機） | 178 px | 126 px | 552 px |
| 120（125%） | 178 px | 126 px | 552 px |
| 144（150%） | 214 px | 151 px | 662 px |
| 192（200%、参考） | 286 px | 200 px | 881 px |

**Decision**: 比率ベースの列幅システム（004 FR-308・006 FR-509）は変更しない。DPIに依存する寸法計算の仕組みそのものは正しく機能している。

## R-1503: 013由来の「項目」列margin枯渇（FR-1505 の是正）

### 問題の特定

013で追加された6番目の手順名 `CLAUDE.md の生成とコミット` により、006が定めた安全基準（余白20px+安全余裕8px = 合計28px）を、**開発機の実DPI(115)で現状の列幅がすでに割り込んでいる**。

```
項目列の実幅（現状 545 DLU 時）: 185 px
項目列の必要文字幅　　　　　　: 178 px
006 基準の必要幅（178+28）　　: 206 px
現在の余裕　　　　　　　　　　: 185 − 206 = -21 px
```

### 是正方針の探索（ダイアログ幅と列比率の再計算）

006 のR-505と同じ方法論（各DPIでの必要幅を満たす最小のダイアログ幅と比率の組をしらみつぶし探索する）を用いた。ただし今回は**単一DPIではなく、保証範囲である96/115/120/144 DPIすべてで同時に成立する**組を探す必要がある。

**制約条件**:
1. 96/115/120/144 の各DPIで、項目・結果・内容の3列すべてが「文字幅+20px+8px」以上であること
2. 006 FR-506（1024x768の画面に収まる。開発機の実DPI=115で判定）を維持すること（FR-1506により継承）

**試行1: 006と同じ「20+8」基準のまま探索** → 545 DLU幅のままでは比率変更だけでは達成不可能（項目・結果・内容の合計必要幅940pxに対し、現行の一覧クライアント幅は925pxしかない）。ダイアログ幅の拡張が必要と判明。

**試行2: 幅を拡張しつつ探索したところ、570 DLU・比率22/17/61で理論上は全DPIを満たせたが、115 DPIの「内容」列で余裕が正確に0pxだった。**

これは006が実際に踏んだ失敗（`/speckit-analyze` B3: 「検査と実装が同じ見積もり（20+8px）を共有すると、見積もりが誤っていても検査は通ってしまう」）と同型のパターンである。憲章 原則V（「検査と実装が同じ見積もりを共有する場合は、誤差を吸収する余裕を別枠で確保しなければならない」）に従い、**この解は採用しない**。

**試行3: 006の基準（20+8=28px）に加えて、さらに8pxの独立した余裕を全DPIで要求して再探索。**

- 1024px制約（115 DPI）を厳守した場合の最良解（**この時点では紙上の概算**）: DLU幅583・比率22/17/61で、最小余裕は**6px**（8pxにわずかに届かない）、115 DPIでのウィンドウ幅は**1020px**と見積もった
- 1024px制約を無視して8px以上を full に満たす場合の最小解: DLU幅586・比率23/17/60で、115 DPIでのウィンドウ幅は1026px（1024pxを2pxだけ超過）

この時点の紙上計算では583 DLU案（ウィンドウ幅1020px、余裕4px）を採用する予定だった。

### 実装時の実測で発覚した誤り: ウィンドウ幅の見積もりが非クライアント領域を含んでいなかった

`/speckit-implement` で実際に583 DLUで`.rc`を書き換えビルドし、`GetWindowRect`で実測したところ、**ウィンドウ幅は1020pxではなく1038pxだった**（1024px制約を14pxオーバー）。

原因を切り分けたところ、上記の「1020px」という値は `583 DLU × 1.75px/DLU ≈ 1020px` という計算で求めた**ダイアログのクライアント幅**であり、実際に`GetWindowRect`で測るウィンドウ全体の幅には、タイトルバー・枠などの非クライアント領域（実測で**一律18px**、DPIに関わらずウィンドウスタイルが同じなら一定）が別途加算されることを見落としていた。

検算: 006の旧基準（545 DLU）でも同じ関係が成立する。545 DLU → クライアント幅 954px（`545×1.75=953.75`を四捨五入） + 18px = 972px。これは006 R-508が実際に採用した「幅972px」という値と完全に一致した。つまり**972pxも972pxで初めから非クライアント領域込みの値であり、583 DLU側の計算だけがクライアント幅とウィンドウ幅を混同していた**。

この見落としは、憲章 原則V（実測に基づく検証）が防ごうとしている典型的な失敗であり、実際に実装フェーズでの実機ビルド・実測によって発見できた。紙上の概算のみで`/speckit-tasks`・`/speckit-implement`を進めていたら、1024px制約への違反を見逃したまま完了させていたところだった。

### 実測に基づく再探索

正しい関係式（115 DPI・実測ベース）:

```
ウィンドウ幅(D) = round(D DLU × 1.75) + 18px（非クライアント領域、実測で一定）
```

FR-506（1024px制約）を余裕を持って満たすダイアログ幅の上限を探るため、候補値を実際に`.rc`へ適用してビルド・実測する方式に切り替えた（分析のみに頼らない）。**DLU幅570**（545から+25）で実機ビルドし、`GetWindowRect`・`LVM_GETCOLUMNWIDTH`で実測したところ:

- ウィンドウ幅（115 DPI実測）: **1016px**（1024pxに対し余裕**8px**）
- 列幅の余裕（実測、20+8px基準に対して）は、紙上概算より大きく出た（下表）

**Decision**

| 項目 | 値 |
|---|---|
| ダイアログ幅（DLU） | 545 → **570**（+25。583案は非クライアント領域を見落としており不採用） |
| 列幅比率 `kColumnRatio` | `{20, 17, 63}` → **`{22, 17, 61}`** |
| 115 DPI（開発機）でのウィンドウ幅（`GetWindowRect`実測） | 972 → **1016 px**（1024px制約に対し余裕8px） |

**検算（実測、各DPIでの余裕、20+8px基準に対して。96/120/144は115 DPIの実測値をDPI比で投影し、文字幅はTextRenderer.MeasureTextで各DPI相当フォントを実測）**:

| DPI | 項目 余裕 | 結果 余裕 | 内容 余裕 |
|---|---|---|---|
| 96 | **+6px（最小）** | +9px | +23px |
| 115（開発機、実機実測） | +7px | +10px | +11px |
| 120 | +16px | +17px | +36px |
| 144 | +24px | +27px | +49px |

**Rationale**: 006自身が確立した「余裕ゼロは危険」という教訓（憲章 原則Vとして明文化済み）を守りつつ、006 FR-506（1024px制約）という既存の契約も破らない値を、実測により確定した。紙上計算だけに頼った583 DLU案は、まさにその原則Vが警戒する「検証と実装が同じ未検証の見積もりを共有する」典型例になっていた（今回は列余裕ではなくウィンドウ幅の見積もり自体が対象だった点が006 B3の教訓とは異なるが、根は同じ）。

**参考（保証対象外の192 DPI/200%相当）**: 115 DPIの実測値からの投影では、192 DPIでも項目+41px・結果+46px・内容+77pxとすべて正の余裕がある。200%はFR-1502により保証対象外のままとするが、実際にはレイアウトが破綻する可能性は低いことが分かった（それでも保証はしない。Clarification 2026-09-14の決定を変更する理由にはならない）。

**Alternatives considered**:
- **583 DLU・比率22/17/61（当初案）** — 却下。実機実測でウィンドウ幅1038pxとなり、FR-506の1024pxを14pxオーバーすることが判明した
- **570 DLU・比率22/17/61（紙上計算段階での旧却下案）** — 当初は「115 DPIの内容列余裕が紙上計算で0pxになる」という理由で却下していたが、これも紙上の概算誤りだった。実機ビルドで実測したところ全DPIで正の余裕（最小+6px）を確保できることを確認し、**最終的にこの値を採用した**
- **586 DLU・比率23/17/60（1024pxを超過する案）** — 却下。006 FR-506を破る
- **文言を短縮して項目名を縮める** — 却下。006 FR-511・015 FR-1506（文言を変更しない）に反する
- **列幅を自動計算（内容に応じた動的幅）にする** — 却下。004 FR-308の「比率で計算する」契約を壊し、YAGNI（原則III）にも反する過剰な設計になる

## R-1504: 横方向のコントロール再配置（幅 545→570 DLUに伴う一律シフト）

004の追従システム（`InitAnchors`/`ApplyAnchors`）は実行時に初期矩形を読み取って差分計算するため、コードの変更は不要。`.rc` の初期座標のみを、幅の増分(+25 DLU。R-1503で583→570に修正した後の最終値)だけ右方向のコントロールにシフトする。

| コントロール | 現在 (x, w) | 新 (x, w) |
|---|---|---|
| ラベル | 7, 45（不変） | 7, 45 |
| パス欄 | 54, 430 | 54, **455** |
| 参照ボタン | 490, 48 | **515**, 48 |
| 生成ボタン | 7, 70（不変） | 7, 70 |
| 結果一覧 | 7, 531 | 7, **556** |
| 案内欄 | 7, 531 | 7, **556** |
| OK | 434, 50 | **459**, 50 |
| キャンセル | 488, 50 | **513**, 50 |

**検算**: キャンセルの右端 = 513+50 = 563 = 570−7（右余白7DLU、既存の隙間を維持）／参照ボタンの右端 = 515+48 = 563、同じく余白7。縦方向（y座標・高さ）は変更しない。

## R-1505: マルチモニタでのDPI変更（FR-1504、対応しない）

**測定**: `SYSTEM_DPI_AWARE` のアプリは `WM_DPICHANGED` を受け取らない（Per-Monitorではないため）。Windows はウィンドウ生成時のDPIで描画されたビットマップを、移動先モニタのDPIに合わせて引き伸ばして表示する。実機での2モニタ間移動テストは、開発機が単一モニタ構成のため実施していない（**未実測**。挙動はWindowsの公式ドキュメントに基づく既知の仕様であり、実装非依存で決定論的なため実測を必須としない）。

**Decision**: 対応しない（Clarification 2026-09-14 Q1）。`PerMonitorV2`宣言・`WM_DPICHANGED`処理・全コントロールの動的再計算は、004の座標計算モデル（初期矩形からの固定倍率の差分）を「DPI変更時の再基準化」に拡張する規模の実装になり、本フィーチャーのスコープ外とする。

**Rationale**: 006・013までの一貫した設計判断（YAGNI、原則III）に従う。影響を受ける利用者は複数モニタで異なるDPIを使っている場合に限られる。

## R-1506: 検証方法

006・007（取り下げ）で確立した方法をそのまま踏襲する。

- **表示スケールのシミュレーション**: `New-Object System.Drawing.Font('MS UI Gothic', pxSize, [System.Drawing.GraphicsUnit]::Pixel)` で `pxSize = 9.0 * dpi / 72.0` として、実際にサインアウトすることなく各DPI相当の文字幅を測る。文字幅そのものは `TextRenderer.MeasureText`（`TextFormatFlags.NoPadding`）で測る。`Graphics.MeasureString` は内部の余白計算がわずかに異なり値がずれるため使わない
- **実行中のダイアログからの実測**: `LVM_GETCOLUMNWIDTH`・`GetClientRect`・`GetWindowRect`等、クロスプロセスで安全なメッセージのみを使う。`LVM_GETSTRINGWIDTH`は使わない（アプリが異常終了する既知の問題）
- **ウィンドウ全体の寸法（FR-506判定）は必ず `GetWindowRect` で実測する。** `GetClientRect`（ダイアログのクライアント幅）で代用すると、タイトルバー・枠などの非クライアント領域（実測18px）を見落とす。本フィーチャーの実装フェーズで実際にこの誤りを犯し、583 DLU案が1024px制約を超過していることを紙上計算では検出できず、実機ビルドでの`GetWindowRect`実測で初めて発覚した（このファイルのR-1503参照）
- **マルチモニタ（US2）**: 開発機が単一モニタ構成のため、実機での自動検証はできない。既知の制限として文書化することを持って完了とする（DT-1506として、目視・手動確認が可能な環境がある場合のみ実施する任意項目とする）

## 測定に使ったもの

一時的なPowerShellスクリプト（本セッション内で使用、リポジトリには追加しない。憲章の技術的制約による）。

- DPI相当フォントによる文字幅計測（9pt×DPI/72のピクセルサイズ）
- ダイアログ幅・列比率のしらみつぶし探索（96/115/120/144の4DPI同時制約＋1024px制約）
- 実行中アプリからの `GetWindowRect`/`GetClientRect`/`LVM_GETCOLUMNWIDTH` によるベースライン確認

**注意**: ビルド済みexeが古いと実測が無意味になる。DPI関連の測定前は必ず `Get-Process | Stop-Process` → `msbuild /t:Rebuild` → 起動、の順で確認すること（本セッションで実際に古いexeを掴んで最初の測定をやり直した）。
