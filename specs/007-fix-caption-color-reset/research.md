# Phase 0 Research: フォルダ選択ダイアログ後もタイトルバーの色を保つ

**Feature**: [spec.md](./spec.md) | **Date**: 2026-09-12

## R-701: 不具合の実在確認と自動再現の試行

**Decision**: 不具合は利用者の実機報告（スクリーンショット3枚）を一次証拠として実在すると判断する。一方、同一の開発機上でビルドした exe に対し、実際のマウス入力（`SendInput` 相当の `mouse_event`）でフォルダ選択ダイアログを操作する自動再現を試みたが、**再現できなかった**。

**試行した手順とその結果**（すべて実際のマウス移動＋クリックで実施。`PostMessage` によるボタンクリックだけでなく、実際の座標へのハードウェア相当の入力を使用）:

| 手順 | 結果 |
|---|---|
| 起動直後に「参照...」→フォルダ選択→「フォルダーの選択」で閉じる | タイトルバーは濃紺のまま |
| 起動直後に「参照...」→「キャンセル」で閉じる | タイトルバーは濃紺のまま |
| 「参照...」→キャンセルを6回連続で繰り返す（FR-702 相当） | 毎回、濃紺のまま |
| フォルダ選択ダイアログを開いたまま8秒待機してから閉じる | 濃紺のまま |
| フォルダ選択ダイアログを開いた状態で、無関係な別アプリのウィンドウへ実際にフォーカスを移してから、フォルダ選択ダイアログに戻って閉じる | 濃紺のまま |

**Rationale（この結果をどう解釈するか）**: 自動化した範囲では再現しなかったが、これは不具合が存在しないことを意味しない。以下のいずれか、または組み合わせが再現条件の可能性がある。

- タイミング依存（DWM の非同期な再描画のタイミングが、スクリプトの実行間隔と噛み合わなかった）
- 実際の人手によるマウス操作（移動速度、クリック間隔、ダブルクリックでの階層移動など）と `mouse_event` による合成入力との間の、OS/DWM 側の扱いの違い
- 本ツールを実行していたセッションや直前の操作履歴など、今回のスクリプトでは再現していない環境要因

これ以上の自動再現の追求は、**GUI 自動操作の限界**（CLAUDE.md に既述の「フォルダ選択ダイアログは合成入力を受け付けない」という既知の制約と同根）に突き当たり、かつ誤操作で無関係なウィンドウを操作するリスクを伴う（本調査中に実際に無関係なアプリの画面を誤クリックした）。したがって、原因の完全な特定は追求せず、**症状に直接効く防御的な修正**を採用する方針とする。

**Alternatives considered**:
- 原因を完全に特定してから修正する: 上記の理由により、実機再現なしにこれ以上の自動調査を続けても収穫が見込みにくく、誤操作のリスクの方が大きいと判断し却下
- Web検索による既知不具合の特定: `DWMWA_CAPTION_COLOR` と共通アイテムダイアログ（`IFileDialog`）の相互作用について検索したが、公開されている一次情報は見つからなかった（一般的な DWM 属性の解説のみ）

## R-702: 修正方針

**Decision**: `CFolderPickerDialog::DoModal()` が返った直後（`IDOK` / それ以外を問わず）に、005 で `OnInitDialog` に実装した着色処理と同じ内容を再適用する。

**Rationale**:
- 005 の知見（R-407, R-408: 非アクティブ・最大化・最小化・復帰では**再設定不要**）と矛盾しない。今回追加するのは「フォルダ選択ダイアログを閉じた」という**別の、限定された契機**であり、005 が禁じた「`OnSize` など無関係な場所での塗り直し」には当たらない
- 原因が「非クライアント領域の再描画を促す何らかのメッセージ」であれ、別の要因であれ、**症状（色が既定色に戻る）そのものを直接打ち消す**ため、原因を特定できていなくても確実に効く
- 実装コストが最小（005 で書いた2行の API 呼び出しを、共通の非公開メンバ関数に切り出して2箇所から呼ぶだけ）
- 着色できない環境（005 FR-408）では、再適用も同様に `E_INVALIDARG` を返すだけで何も起こらない。新たな分岐を増やさないため FR-703 を自然に満たす

**Alternatives considered**:
- **`WM_ACTIVATE` / `WM_NCACTIVATE` ハンドラで再適用する**: フォルダ選択ダイアログ以外の要因（例: 「バージョン情報」ダイアログや `AfxMessageBox`）でも再適用が走ることになり、005 FR-411（着色の対象はメインダイアログ1枚、他のダイアログの開閉を意識した仕組みは作らない）の趣旨から外れる。また 005 が明示的に避けた「アクティブ状態の変化を契機にした再描画」に近く、意図しない副作用（ちらつきなど）のリスクもある。今回の不具合は「参照」ボタンの経路に限定されていることが利用者の報告から明らかなため、契機をそこに絞る
- **DWM のバージョン別分岐や `GetProcAddress` による動的解決**: 005 で既に不採用と判断済み（research.md R-405）であり、本フィーチャーでも状況は変わらない
- **色を保持するメンバ変数を持ち、`OnActivate` で比較して再設定**: 状態を持つ分だけ複雑になり、YAGNI に反する。`DoModal()` の直後という1箇所に対応点があるため、状態を持たずに書ける

## R-703: 実装箇所

**Decision**: `MFCApplication1Dlg.cpp` の `OnInitDialog` にある着色処理（2行）を `ApplyCaptionColor()` という非公開メンバ関数に切り出し、`OnInitDialog` と `OnBnClickedButtonBrowse` の両方から呼び出す。

**Rationale**: 同じ2行の API 呼び出しを2箇所に書く重複は、憲章 原則III が許容する「3行程度の重複」の範囲内ではあるが、今回は**色の定数や呼び出し順を将来変える際に2箇所を同期させ忘れるリスク**の方が、1個の非公開関数を足すコストより高いと判断した。関数はクラスの状態を一切持たず、呼び出し元も2箇所のみであるため、抽象化としては最小限に留まる。

**Alternatives considered**:
- 2箇所に同じ2行をそのまま書く: 却下はしないが、上記の理由で関数化を選んだ
- `CaptionStyler` のような新しいクラスを作る: 005 で既に「呼び出し元が1箇所しかない」ことを理由に却下しており、今回2箇所になっても状態を持たない2行のためだけに新クラスを作るのは YAGNI に反する

## R-704: 動的検証の実施方法

**Decision**: 修正の効果を確認する動的テスト（DT-701）は、**利用者による手動実行**とする。

**Rationale**: R-701 のとおり、フォルダ選択ダイアログの開閉を伴う操作は自動化での再現に成功しておらず、CLAUDE.md に既述のとおりフォルダ選択ダイアログは合成入力を受け付けない。したがって「修正前は再現し、修正後は再現しない」ことを自動テストで示すことができない。004〜006 までの前例（フォルダ選択を伴う動的テストは手動実行）を踏襲する。

## R-705: `/speckit-analyze` による設計見直し（DoModal() 直前の呼び出しを追加）

**Decision**: R-702・R-703 で決めた「`DoModal()` が返った直後の1箇所」という設計を、「`DoModal()` を呼ぶ直前」と「返った直後」の**2箇所**に改める。`ApplyCaptionColor()` の呼び出し元は `OnInitDialog` と合わせて計3箇所になる。

**Rationale**: `/speckit-analyze` により、spec.md の User Story 1 Acceptance Scenario 1（「フォルダ選択ダイアログを**開く**」という When に対し、メインダイアログのタイトルバーが濃紺のままであることを Then として要求している）と、FR-701 の当初の文言（開閉の**前後**とのみ記載）・Assumptions（**閉じた後**に再設定する対応を前提とする記載）との間に食い違いがあると指摘された。利用者の実機報告（「参照ボタンを押下すると白色に変化する」）も、閉じた後だけでなく**開いた時点**で色が崩れる可能性を示唆している。

R-702 時点では「`DoModal()` の直後」だけで症状を打ち消せると判断していたが、これは「開いている間に崩れて、そのまま戻らない」ケースにしか対応できず、「開いた瞬間に崩れ、ダイアログが開いている間ずっと崩れたまま」というケースには対応できない。両方に備えるため、開く直前にも同じ再適用を行うことにした。

この変更は R-702 の他の論拠（005 の知見との非矛盾、原因不明でも症状を直接打ち消せる、着色できない環境で新たな分岐を増やさない）を損なわない。呼び出し箇所が1つ増えるだけで、状態は増えない。

**Alternatives considered**:
- 変更しない（`DoModal()` の直後のみ）: 却下。Acceptance Scenario 1 を満たせない可能性が残る
- Acceptance Scenario 1 の方を「開閉の前後のみ」に緩めて、実装を変えない: 却下。実装コストが2行程度追加するだけで済むのに対し、spec を緩めると「開いた瞬間は直っていない」という利用者体験のギャップが残るため、実装を強める方を選んだ
