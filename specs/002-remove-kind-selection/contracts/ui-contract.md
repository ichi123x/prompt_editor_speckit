### 3.1 「生成」ボタン

001 の6段階の検証チェーンから、**種別に関わる2つを削除**して4段階になる。

```
押下
 │
 ├─ 1. フォルダ未選択？        → 「対象フォルダを選択してください。」で中止   [001 US1-4]
 ├─ ✂ 2. 種別未選択？          → 削除 (FR-102)
 ├─ 2. 書き込み権限なし？      → 権限不足の案内で中止                       [001 FR-015]
 ├─ 3. プロジェクトマーカーなし？ → ウィザードでの作成を促して中止           [FR-103, FR-104]
 │      ✂ 他方の種別のマーカーあり → 不一致の警告 … 削除 (FR-105)
 ├─ 4. .specify と .claude の一方だけ存在？ → 警告して手動確認を促し中止      [001 Edge Case]
 ├─ 5. GitState = NestedUnderParent？ → 入れ子リポジトリの警告               [001 FR-016]
 │
 ├─ 生成・診断・参照ボタンを無効化（3種）
 ├─ 対象フォルダパスをワーカースレッドへコピーして渡す
 ├─ ワーカースレッドを起動し、5手順を順に実行
 └─ 完了通知の受信 → ボタンを有効に戻す → 完了案内を表示
```

**契約（research.md R-104）**:
- 削除するのは種別に関わる2箇所のみ。**残る検証の順序を変えてはならない**。特に「書き込み権限の確認」が「マーカーの確認」より先である点は維持する。権限が無いフォルダでマーカーを探しても意味がないため。
- 検証で中止する場合、**生成ボタンを無効化してはならない**（001 の契約を継承。DT-103 が検証）。

### 3.2 実行中に無効化するコントロール（**回帰注意箇所**）

001 では5コントロール（生成・診断・参照・ラジオ2件）を無効化していた。002 では**ラジオ2件のみを取り除き、3コントロールを無効化する**。

| コントロールID | 002 での扱い |

| `IDC_BUTTON_GENERATE` | **無効化する**（二重実行の防止） |
| `IDC_BUTTON_DIAGNOSE` | **無効化する**（処理途中の中間状態を表示させない） |

## 4-2. 案内表示コントロールの契約（欠陥修正）

**発見の経緯**: 002 の手動テスト（T032）で、完了時の案内文が**3行目の途中で切り詰められて**表示されることが判明した。案内文は5行あるのに、`LTEXT` の高さが 28 DLU（約3行分）しかなかったためである。

調査の結果、同じ箇所にもう1つ、より深い欠陥があることが分かった。001 の User Story 3 は「案内はコマンドを**そのまま Claude Code のパネルへ貼り付けられる形**で提示される」と定め、検証タスク T050 も「コマンド文字列を**コピーできる**こと」を要求している。しかし静的テキスト（`LTEXT`）は**選択もコピーもできない**。切り詰め以前に、仕様の要求を満たしていなかった。

**Decision**: `IDC_STATIC_GUIDE` を静的テキストから**読み取り専用の複数行エディット**へ変更する。

```
EDITTEXT IDC_STATIC_GUIDE,7,147,306,28,
         ES_MULTILINE | ES_READONLY | ES_AUTOVSCROLL | WS_VSCROLL | NOT WS_TABSTOP
```

| スタイル | 目的 |
|---|---|
| `ES_MULTILINE` | 複数行を表示する |
| `ES_READONLY` | ユーザーが編集できない（FR-112）。選択とコピーは妨げない |
| `ES_AUTOVSCROLL` / `WS_VSCROLL` | 領域に収まらない場合にスクロールできる（FR-110） |
| `NOT WS_TABSTOP` | Tab 巡回に含めない。案内は読むためのものであり入力対象ではない |

**契約**:
- 案内文の行数が増減しても表示が壊れてはならない。**高さのピクセル調整で対処してはならない**（FR-110）
- テキストは選択・コピーできなければならない（FR-111）
- コントロールIDは `IDC_STATIC_GUIDE` のまま変更しない。名称に `STATIC` を含むが、ID を変えると 001 の成果物との対応が切れるため維持する
- 表示の設定は `SetDlgItemText` のままでよい。エディットでも同じ API で設定できる

**なぜ高さを広げるだけにしないか**: 現在の案内は完了時が5行、診断時も5行である。将来 `/speckit-constitution` の手順が増えれば6行、7行になりうる。そのたびにレイアウトを調整するのは症状への対処にすぎない。スクロール可能にすれば行数に依存しなくなる。加えて、高さを広げるだけでは FR-111（コピー可能）は解決しない。

**タブ順序への影響**: `NOT WS_TABSTOP` を指定するため、「2. レイアウト」のタブ順序から `IDC_STATIC_GUIDE` が外れる。変更後の順序は次のとおり。

```
ラベル → IDC_EDIT_TARGET_PATH → IDC_BUTTON_BROWSE
      → IDC_BUTTON_GENERATE → IDC_BUTTON_DIAGNOSE
      → IDC_LIST_RESULT → IDOK → IDCANCEL
```

### 統合 `.gitignore` の契約

**不変条件（FR-106 / SC-105）**: 生成される `.gitignore` の内容は、**対象フォルダの状態にかかわらず常に同一**でなければならない。フォルダ内のマーカーを見て内容を切り替えてはならず、ユーザーに選択させてもならない。

含まれなければならないパターン（ST-104 が検査する代表例）:

| 系統 | 代表パターン |
|---|---|
| Visual Studio | `[Dd]ebug/`・`[Rr]elease/`・`[Oo]bj/`・`.vs/`・`*.vcxproj.user`・`*.aps`・`*.suo` |
| Node / Web | `node_modules/`・`dist/`・`build/`・`.env`・`coverage/` |
| 共通 | `Thumbs.db`・`.DS_Store`・`Desktop.ini` |

**重複の禁止（research.md R-101）**: 統合にあたり、2ファイルで重複していた16パターンはセクション1（共通）へ集約し、セクション2・3からは取り除く。同じパターンが2回現れてはならない。`.gitignore` の動作としては無害だが、ST-104 が追記ブロックの重複を検出する際に「意図した重複」と「実装ミス」を区別できなくなるため。

**追記ブロック（FR-106a）**: 001 の2ブロック（Spec Kit 用 / プロジェクト固有）は変更なし。目印行による判定でべき等性を保つ挙動、既存 `.gitignore` の本体を書き換えず未記載のブロックのみを追記する挙動も、いずれも 001 のまま。

**既存フォルダへの再実行**: 001 で VS 用の本体を書き込んだフォルダに本バージョンを実行しても、既存ファイルの本体は書き換えられず Node 用のパターンは追加されない。これは既存ファイルを尊重する 001 の設計として意図どおりであり、変更しない。
