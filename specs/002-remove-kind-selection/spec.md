# Feature Specification: プロジェクト種別選択の廃止

**Feature Branch**: `ver.0.2`

**Created**: 2026-09-08

**Status**: Draft

**Input**: User description: "MFCアプリかWEBアプリの選択は機能として不要です。/speckit-constitution を実施したときに判定されることを期待しています。"

## 背景と、001 との関係

フィーチャー 001（[SDDプロジェクトのベース作成ツール](../001-sdd-project-bootstrap/spec.md)）では、ユーザーが「MFCアプリ」「Webアプリ」のいずれかをラジオボタンで選んでから「生成」を押す設計とした。本フィーチャーはその**種別選択を廃止**する。

廃止する理由は、種別の判定が本ツールの役割ではないためである。プロジェクトが MFC なのか Web なのかは、`/speckit-constitution` を実行して憲章を制定する段階で、Claude Code がリポジトリを読んで判断し、技術的制約として憲章に記録される。本ツールは SDD の土台を敷くだけであり、その土台に種別の区別を持ち込む必要がない。

本フィーチャーが置き換える 001 の要件は次のとおり。

| 001 の要件 | 本フィーチャーでの扱い |
|---|---|
| FR-003（種別を選択できる手段の提供） | **廃止**。ラジオボタンをダイアログから削除する |
| FR-005（フォルダまたは種別が未選択なら中止） | **縮小**。フォルダ未選択のみを対象とする |
| FR-006（選択種別に対応するマーカーの確認） | **変更**。種別を問わず、いずれかのマーカーの有無を確認する |
| FR-008（種別の不一致を警告） | **廃止**。種別を選ばないため不一致が発生しない |
| FR-010（種別に応じた `.gitignore` の決定） | **変更**。種別選択に依存しない決定方法へ置き換える |

上記以外の 001 の要件（診断の7項目、手順の実行と結果表示、べき等性、入れ子リポジトリの警告など）はすべてそのまま有効である。

## User Scenarios & Testing（ユーザーシナリオとテスト） *(必須)*

### User Story 1 - フォルダを選ぶだけでSDD化する (Priority: P1)

開発者は、Visual Studio 2022 等のウィザードであらかじめ生成し任意のフォルダに配置しておいたプロジェクトに対して、本ツールで「参照」ボタンからそのフォルダを選び、「生成」ボタンをクリックする。**種別を選ぶ操作は存在しない。** それだけで、uv・specify CLI・VS Code 拡張の導入確認とインストール、Spec Kit 足場の配置、Git 初期化、`.gitignore` の配置、初回コミットまでが完了する。

**Why this priority（この優先度である理由）**: 本フィーチャーの目的そのものである。操作が1つ減り、ユーザーが「自分のプロジェクトはどちらなのか」を判断する必要がなくなる。この判断は後段の `/speckit-constitution` が担う。

**Independent Test（独立したテスト方法）**: `C:\work\test\test01`（MFCダイアログアプリ）を選択し、種別を選ばずに「生成」をクリックして、`.specify`・`.claude`・`.git`・`.gitignore` が揃いコミットが1件以上作成されることを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） ダイアログが表示されている、**When**（動作） ユーザーが画面を確認する、**Then**（結果） プロジェクト種別を選ぶラジオボタンやその他の選択手段が画面上に存在しない。
2. **Given**（前提） MFCアプリのソリューションが配置済みのフォルダを選択している、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 種別の選択を促されることなく導入処理が実行され、5手順の結果が一覧表示される。
3. **Given**（前提） Webアプリのプロジェクトが配置済みのフォルダを選択している、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 同様に導入処理が実行される。MFCアプリの場合と操作手順に違いがない。
4. **Given**（前提） フォルダが選択されていない、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 先にフォルダを選択するよう促すメッセージが表示され、導入手順は実行されず、いかなるファイルも作成・変更されない。
5. **Given**（前提） MFCアプリとWebアプリの両方のマーカーが存在するフォルダを選択している、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） 警告や確認を求められることなく導入処理が実行される。種別の不一致という概念が存在しないため。

### User Story 2 - 対象プロジェクトが無いフォルダで安全に停止する (Priority: P2)

対象フォルダにプロジェクトが1つも配置されていない場合、開発者はウィザードでプロジェクトを作成するよう促され、導入処理は実行されない。種別を選ばなくなっても、この安全弁は維持される。

**Why this priority（この優先度である理由）**: 001 の FR-007 が定めるスコープ境界（本ツールは雛形を生成しない）を守るための安全弁であり、種別選択の廃止によって失われてはならない。ただし User Story 1 が動けば主目的は達成されるため、優先度は下がる。

**Independent Test（独立したテスト方法）**: 空のフォルダを選択して「生成」をクリックし、案内メッセージが表示されて `.specify`・`.git` などが作成されないことを確認するだけでテストできる。

**Acceptance Scenarios（受け入れシナリオ）**:

1. **Given**（前提） 選択したフォルダに認識可能なプロジェクトマーカーが1つも存在しない、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） Visual Studio 2022 等のウィザードでプロジェクトを作成し配置するよう促すメッセージが表示され、導入手順は実行されず、雛形も生成されない。
2. **Given**（前提） 認識可能なプロジェクトマーカーが1つ以上存在する、**When**（動作） ユーザーが「生成」をクリックする、**Then**（結果） マーカーの種類にかかわらず導入処理が実行される。

---

### Edge Cases（エッジケース）

- 対象フォルダに MFC のマーカーと Web のマーカーが同時に存在する場合、システムは警告を出さず処理を続行する。種別を区別しないため、この状態は異常ではない。
- 対象フォルダに、MFC でも Web でもない種類のプロジェクト（例: コンソールアプリ）のマーカーだけが存在する場合の扱いは、認識可能なマーカーの定義に依存する。認識可能なマーカーが1つも無ければ User Story 2 の経路になる。
- 種別選択の廃止によって画面に空きができるが、他のコントロールの位置がずれてラベルとコントロールの対応が崩れてはならない。
- 001 で実装済みの機能（診断の7項目、手順結果の表示、べき等性、入れ子リポジトリの警告、実行中のコントロール無効化）は、本変更によって動作が変わってはならない。

### テスト方針

001 と同じく、静的テスト（アプリケーションを実行せずに行う検査）と動的テスト（ダイアログを操作して行う検査）の2層で検証する。本フィーチャーは既存機能の削除と変更が中心のため、**回帰の検出**に重点を置く。

#### 静的テスト

- **ST-101 UIリソースの検査**: ダイアログのリソース定義から種別選択のコントロールが削除されていること。残るコントロールのIDとタブ順序が整合していること。
- **ST-102 未使用コードの検査**: 種別選択に伴って不要となった定義・分岐・メッセージ文字列が残っていないこと。参照されないコードを残さない。
- **ST-103 コンパイラ警告の検査**: 全構成のビルドが、本変更に起因する警告（未使用変数・未使用関数など）を出さずに完了すること。
- **ST-104 生成物の内容検査**: 動的テスト実行後に生成された `.gitignore` を、アプリケーションを介さずファイルとして開き、Visual Studio 系（`[Dd]ebug/`・`.vs/`・`*.vcxproj.user`・`*.aps`）と Node 系（`node_modules/`・`dist/`・`.env`）の**双方**の除外パターンが含まれていることを確認する。加えて、Spec Kit 用とプロジェクト固有の追記ブロックの目印行がそれぞれ1回だけ出現することを確認する（FR-106、FR-106a）。
- **ST-106 決定性の検査**: `.gitignore` が存在しない状態の MFCアプリのフォルダと Webアプリのフォルダに対して**新規作成された** `.gitignore` を突き合わせ、追記ブロックも含めて完全に同一であることを確認する。内容がフォルダによって変わるなら、種別による分岐が実装に残っている（FR-106 違反）。既存ファイルがあるフォルダは対象外（FR-106a により本体が保持されるため）。
- **ST-107 既存ファイルの保持の検査**: 独自の内容を持つ `.gitignore` をあらかじめ置いたフォルダに対して「生成」を実行し、**既存の本体が1行も書き換えられていない**こと、および追記ブロックだけが末尾に足されていることを確認する（FR-106a）。統合版で丸ごと上書きしていないかを検出する。
- **ST-108 案内表示コントロールの検査**: 案内表示のリソース定義が、静的テキストではなく**選択可能かつスクロール可能なコントロール**であり、読み取り専用に設定されていることを確認する（FR-110〜FR-112）。
- **ST-105 仕様と実装の対応の検査**: 本フィーチャーで変更した各箇所が、どの機能要件に対応するかをコード上で追跡できること。

#### 動的テスト

対象フォルダは `C:\work\test\test01`（MFCダイアログアプリ）を用いる。

| No. | 検証内容 | 対応する受け入れシナリオ |
|---|---|---|
| DT-101 | 画面に種別選択のコントロールが存在しない | US1-1 |
| DT-102 | フォルダを選ぶだけでSDD化が完走する | US1-2 |
| DT-103 | フォルダ未選択で「生成」を押下する | US1-4 |

| DT-106 | 診断の7項目が 001 と同じ判定を返す（回帰確認） | 001 FR-018 |
| DT-107 | 実行中に参照ボタンが無効化される（回帰確認） | 001 の実行中無効化 |

## Requirements（要件） *(必須)*

### Functional Requirements（機能要件）

- **FR-101**: システムはダイアログからプロジェクト種別を選択するコントロールを削除しなければならない。画面上に種別を選ぶ手段が存在してはならない。
- **FR-102**: 「生成」ボタンがクリックされたとき、システムはフォルダが選択されているかのみを確認しなければならない。種別の選択状態を確認してはならない。
- **FR-103**: システムは対象フォルダ配下に、認識可能なプロジェクトマーカーが1つ以上存在するかを、種別を区別せずに確認しなければならない。
- **FR-104**: 認識可能なプロジェクトマーカーが1つも存在しない場合、システムは Visual Studio 2022 等のウィザードでプロジェクトを作成・配置するよう促すメッセージを表示し、以降の導入手順を実行してはならない。本ツールは引き続き、プロジェクトの雛形を保持してはならず、いかなる方法でも雛形を生成してはならない。
- **FR-105**: システムは、対象フォルダに複数種類のプロジェクトマーカーが存在する場合でも、警告や確認を求めずに導入処理を続行しなければならない。
- **FR-106**: **`.gitignore` を新規作成する場合**、システムは**すべての種別の除外パターンを統合した単一の内容**を、対象フォルダの内容にかかわらず常に同じ内容で書き出さなければならない。フォルダ内のマーカーを見て内容を切り替えてはならず、ユーザーに選択させてもならない。統合された内容には、少なくとも Visual Studio 系（ビルド出力・中間ファイル・ユーザー固有ファイル・`.vs/`）と Node 系（`node_modules/`・ビルド成果物・環境変数ファイル）の双方の除外パターンが含まれなければならない。
- **FR-106a**: **`.gitignore` が既に存在する場合**、システムは既存の本体を書き換えてはならず、未記載の追記ブロックのみを末尾に追記しなければならない（001 の FR-010 の挙動を継承）。この場合、既存の本体が統合された内容と異なっていても、それを統合版で置き換えてはならない。FR-106 が定める「常に同じ内容」は新規作成の場合にのみ適用される。
- **FR-106b**: 新規作成・既存への追記のいずれの場合も、001 の FR-010 が定める2つの追記ブロック（Spec Kit 用とプロジェクト固有）が、目印行による判定を経て**それぞれ1回だけ**含まれなければならない。同じ操作を繰り返してもブロックが重複してはならない。
- **FR-107**: システムは、種別選択の廃止に伴って不要となったコード・リソース定義・メッセージ文字列を残してはならない。
- **FR-108**: システムは、001 で実装された以下の機能の動作を変更してはならない — 準備完了チェックリストの7項目の診断、5手順の実行と結果表示、べき等性、入れ子リポジトリの警告、書き込み権限の確認、処理実行中のコントロール無効化。
- **FR-109**: 種別選択のコントロールを削除した後も、残るコントロールのラベルとコントロールの対応関係、およびタブ順序が正しく保たれなければならない。

**案内表示の欠陥修正（002 の手動テストで発見）**

- **FR-110**: 案内表示は、**表示する文字列の行数にかかわらず全文を読める**手段を備えなければならない。表示領域に収まらない場合はスクロールできること。行数に依存して末尾が切り詰められてはならない。
- **FR-111**: 案内表示のテキストは、**ユーザーが選択してコピーできる**ものでなければならない。001 の User Story 3 が「案内はコマンドをそのまま Claude Code のパネルへ貼り付けられる形で提示される」と定めており、選択できない表示ではこの要求を満たさない。
- **FR-112**: 案内表示は読み取り専用であり、ユーザーが内容を編集できてはならない。

### Key Entities（主要エンティティ）

- **プロジェクトマーカー**: 対象フォルダにプロジェクトが配置されていることを示すファイル。001 では種別ごとに区別していたが、本フィーチャーでは**区別せず1つの集合として扱う**。個々のマーカーが何の種別を示すかは、本ツールの判断材料ではなくなる。
- **対象プロジェクトフォルダ**: 001 の定義から `ProjectKind` への依存が取り除かれる。完全パス、プロジェクトマーカーの有無、Spec Kit足場の有無、Gitリポジトリの状態、書き込み権限の可否を持つ点は変わらない。

## Success Criteria（成功基準） *(必須)*

### Measurable Outcomes（測定可能な成果）

- **SC-101**: プロジェクトを配置済みのフォルダに対して、GUI操作が **3回から2回へ減る**（フォルダ選択と生成ボタンのクリックのみ）。
- **SC-102**: ユーザーは、自分のプロジェクトが MFC と Web のどちらに該当するかを判断することなく、SDD化を完了できる。
- **SC-103**: 種別選択の廃止後も、001 で合格していた検証項目が100%再現する（診断の7項目、べき等性、未選択ガード、実行中の無効化）。
- **SC-104**: MFCアプリのフォルダと Webアプリのフォルダで、ユーザーの操作手順が完全に同一である。
- **SC-105**: `.gitignore` が存在しない MFCアプリのフォルダと Webアプリのフォルダに対して新規作成した場合、生成される `.gitignore` が1バイトの差異もなく同一である（FR-106）。既に `.gitignore` があるフォルダは FR-106a により本体が保持されるため、本基準の対象外とする。

## Assumptions（前提事項）

- 本フィーチャーは 001 の実装に対する変更であり、新規の別アプリは作らない。
- プロジェクト種別の判定は `/speckit-constitution` の実行時に Claude Code がリポジトリを読んで行い、憲章の技術的制約として記録される。本ツールはその判定に一切関与しない。
- 「認識可能なプロジェクトマーカー」は 001 と同じ集合（`.sln`・`.vcxproj`・`.csproj`・`package.json` など）とする。集合の定義自体は本フィーチャーでは変更せず、種別ごとの区別をやめるだけである。
- 001 で作成済みの `.gitignore` 埋め込みリソース2件は、**1つの統合されたリソースに置き換える**（FR-106）。統合により、種別という概念が実装から完全に消える。
- 統合された `.gitignore` は無関係な行を含むことになる（MFCプロジェクトに `node_modules/` の行が入るなど）が、これは許容する。除外パターンが余分にあっても実害はなく、逆に不足すると初回コミットに大量の不要ファイルが混入する。取りこぼしのリスクと冗長さを比べ、冗長さを選ぶ。
- ファイル長は約500行になる見込みだが、`.gitignore` はユーザーが日常的に読むファイルではないため可読性の低下は問題にならない。
- 既に 001 の実装でSDD化を済ませたフォルダに対して本バージョンを再実行しても、べき等性は保たれる（`.gitignore` の追記ブロックは目印行で判定されるため、決定方法が変わっても重複しない）。
- **001 でSDD化済みのフォルダでは、`.gitignore` の本体が更新されない。** 001 は種別に応じて VS 用または Node 用の本体を書き込んでおり、002 を実行しても FR-106a により既存の本体は保持される。したがって 001 で MFC として処理したフォルダには Node 系のパターン（`node_modules/` 等）が追加されない。これは既存ファイルを尊重する設計として意図どおりであり、不具合ではない。統合版の内容を適用したい場合は、`.gitignore` を削除してから再実行する必要がある。
- 上記の制約が実害を持つのは、001 で MFC として処理したフォルダに後から npm を導入する場合に限られる。その時点で `.gitignore` を手で調整するか削除して再実行すればよく、本フィーチャーで自動移行の仕組みを設けることはしない（憲章 原則III のYAGNI）。
- 本フィーチャーの検証には、001 と同じく `C:\work\test\test01` を用いる。
