# Phase 0 リサーチ: プロジェクト種別選択の廃止

**Feature**: 002-remove-kind-selection
**Date**: 2026-09-08
**前提**: [001 の research.md](../001-sdd-project-bootstrap/research.md) の R-001〜R-009 は引き続き有効。本書はその差分のみを扱う。

本フィーチャーは既存実装からの削除が中心であり、新しい外部依存や未知の技術要素は無い。調査項目は「何をどこまで消すか」と「統合 `.gitignore` をどう作るか」の2点に絞られる。

---

## R-101: 統合 `.gitignore` の構成

**Decision**: 2つの埋め込みリソース（`gitignore_vs.txt` / `gitignore_node.txt`）を、**重複を排除した単一ファイル `gitignore_all.txt`** へ統合し、リソースIDを `IDR_GITIGNORE` 1件にする。

**重複の実測**: 現在の2ファイルからコメントと空行を除いて突き合わせた結果は次のとおり。

| ファイル | パターン数 |
|---|---|
| `gitignore_vs.txt` | 83 |
| `gitignore_node.txt` | 53 |
| **重複** | **16** |
| 統合後（重複排除） | 120 |

重複していた16パターン:

```
$RECYCLE.BIN/   *.log          *.rsuser    *.suo
*.swp           *.user         .DS_Store   .env
.vs/            Desktop.ini    Thumbs.db   [Bb]in/
[Oo]bj/         artifacts/     ehthumbs.db project.lock.json
```

**Rationale**:
- 単純に2ファイルを連結すると、これら16パターンが二重に並ぶ。`.gitignore` の動作としては無害（同じパターンが2回あっても結果は変わらない）だが、ST-104 の内容検査で「意図した重複」と「実装ミスによる重複」を区別できなくなる。追記ブロックの重複を検出する ST-104 の目的が濁るため、重複は排除する。
- 共通項目（Windows のシェルが生成するファイル、エディタの一時ファイル、環境変数ファイル）を独立したセクションにまとめることで、どちらの由来かを追わずに読めるようになる。

**統合後の構成**:

| セクション | 内容 | 由来 |
|---|---|---|
| 1. 共通 | `Thumbs.db`・`.DS_Store`・`Desktop.ini`・`$RECYCLE.BIN/`・`*.swp`・`*.log`・`.env` 系 | 両方 |
| 2. Visual Studio / .NET | ユーザー固有ファイル・ビルド出力・C++ 中間ファイル・リソースエディタ・NuGet・プロファイラ | VS用 |
| 3. Node / Web | `node_modules/`・ログ・テストカバレッジ・ビルド成果物・各種キャッシュ | Node用 |
| 4. 追記ブロック | Spec Kit 用 / プロジェクト固有 | 001 FR-010 |

**Alternatives considered**:
- *2ファイルを実行時に連結する*: リソースを2件のまま保持でき変更が小さいが、`ProjectKind` を消すという本フィーチャーの目的に対して「種別ごとのファイルが残っている」状態が残る。FR-107（不要となったリソース定義を残さない）にも反する。却下。
- *重複を許して単純連結する*: 上記のとおり ST-104 の検査を濁らせる。却下。

**べき等性への影響なし**: 追記ブロックの有無は目印行（`# ---- Spec Kit ----` / `# ---- このプロジェクト固有 ----`）で判定しており、本体の内容が変わっても判定条件は変わらない。001 でSDD化済みのフォルダに本バージョンを再実行しても、ブロックが重複することはない（001 FR-013 / 002 FR-106a）。

**既存フォルダの本体は更新されない**: 001 の挙動として、既存の `.gitignore` がある場合は本体を書き換えず追記ブロックのみを足す。したがって 001 で VS 用の本体を書き込んだフォルダに本バージョンを実行しても、本体は VS 用のまま残り Node 用のパターンは追加されない。これは既存ファイルを尊重する設計として意図どおりであり、変更しない。

## R-102: `ProjectKind` の削除範囲

**Decision**: `ProjectKind` 列挙とその関連要素を**完全に削除**する。内部的にも残さない。

現在の参照箇所を実コードから洗い出した結果は次のとおり。

| ファイル | 削除・変更する要素 |
|---|---|
| `TargetFolderState.h` | `enum class ProjectKind` の削除。`hasSlnMarker` / `hasWebMarker` を `hasProjectMarker` へ統合。`HasMarkerFor()` と `KindDisplayName()` の削除 |
| `TargetFolderState.cpp` | `HasMarkerFor()` / `KindDisplayName()` の実装削除。マーカー検出を1つのフラグへ集約 |
| `GitignoreWriter.h/.cpp` | `Ensure()` から `kind` 引数を削除。リソースID の分岐を削除 |
| `SetupRunner.h/.cpp` | `RunAll()` / `RunInitGit()` から `kind` 引数を削除 |
| `ReadinessChecker.cpp` | `hasSlnMarker \|\| hasWebMarker` を `hasProjectMarker` へ |
| `MFCApplication1Dlg.h` | `m_kind` / `m_workerKind` の削除。ラジオのハンドラ宣言の削除 |
| `MFCApplication1Dlg.cpp` | ハンドラ2件、メッセージマップ2行、初期化2行、無効化リストの2要素、種別未選択の検証、不一致の検証の削除 |
| `Resource.h` | `IDC_RADIO_KIND_MFC` / `IDC_RADIO_KIND_WEB` の削除。`IDR_GITIGNORE_VS` / `IDR_GITIGNORE_NODE` を `IDR_GITIGNORE` へ |
| `MFCApplication1.rc` | グループボックスとラジオ2件の削除。RCDATA を1件へ |

**Rationale**: FR-107 が「種別選択の廃止に伴って不要となったコード・リソース定義・メッセージ文字列を残してはならない」と定めている。列挙だけを残して常に片方を渡すような実装は、後から読んだときに「なぜ選択肢があるのに固定なのか」という疑問を生む。消し切ることで、種別という概念が実装から消えたことがコード上で自明になる。

**`hasProjectMarker` への統合について**: マーカーの検出ロジック自体（`*.sln` / `*.vcxproj` / `*.csproj` / `package.json` を探す）は変更せず、結果を2つのフラグに分けて保持するのをやめて1つにする。診断の項目1は現在 `hasSlnMarker || hasWebMarker` で判定しているため、統合しても判定結果は変わらない（FR-108 の「診断の動作を変更しない」を満たす）。

**Alternatives considered**:
- *`ProjectKind` を残し、常に統合リソースを使う*: 変更は最小だが未使用の列挙が残り FR-107 に反する。却下。
- *`hasSlnMarker` / `hasWebMarker` を両方残す*: 将来どちらかを使いたくなる可能性を見越した設計だが、憲法 原則III（YAGNI）が「現時点で必要とされていない拡張ポイントを導入してはならない」と定めている。却下。

## R-103: ダイアログのレイアウト

**Decision**: グループボックスとラジオ2件を削除し、その空きに「生成」「準備状況を診断」ボタンを左詰めで移動する。結果一覧の上端を引き上げて表示領域を広げる。

**変更前**（320 x 200 DLU）:

```
y=7    対象フォルダ: [____________] [参照...]
y=27   ┌ プロジェクト種別 ──────┐  [生成]  [準備状況を診断]
y=40   │ (o)MFCアプリ (o)Webアプリ │
y=58   └────────────────┘
y=63   ┌ 結果一覧 (79 DLU) ─────────────────┐
y=147  案内テキスト
y=179  [OK] [キャンセル]
```

**変更後**:

```
y=7    対象フォルダ: [____________] [参照...]
y=30   [生成]  [準備状況を診断]
y=52   ┌ 結果一覧 (90 DLU) ─────────────────┐
y=147  案内テキスト
y=179  [OK] [キャンセル]
```

**Rationale**:
- 空白をそのまま残すと、削除の痕跡が画面に残って未完成に見える。
- 一覧の高さが 79 → 90 DLU に増える。診断は7行、導入処理は5行を表示するため、スクロールなしで全行が見える余裕が生まれる。SC-004（表示を見るだけで判断できる）に寄与する。
- ボタンを左詰めにするのは、上のパス欄・下の一覧と左端を揃えるため。

**タブ順序（FR-109）**: `.rc` 内の記述順がタブ順序を決める。変更後の順序は「ラベル → エディット → 参照 → 生成 → 診断 → 一覧 → 案内 → OK → キャンセル」とする。ラジオ削除に伴い `WS_GROUP` の指定も消えるが、残るコントロールにグループ化が必要なものは無い。

**Alternatives considered**:
- *ボタンを元の位置（x=165, x=243）に残し、一覧だけ引き上げる*: 変更が小さいが、左半分が空いたままになり不自然。却下。

## R-104: 回帰を防ぐうえで注意する箇所

削除作業で壊しやすい箇所を、実コードを見て特定した。

**(1) 実行中に無効化するコントロールの配列**（`MFCApplication1Dlg.cpp`）

```cpp
CWnd* controls[] = {
    GetDlgItem(IDC_BUTTON_GENERATE),
    GetDlgItem(IDC_BUTTON_DIAGNOSE),
    GetDlgItem(IDC_BUTTON_BROWSE),      // ← 残す
    GetDlgItem(IDC_RADIO_KIND_MFC),     // ← 削除
    GetDlgItem(IDC_RADIO_KIND_WEB)      // ← 削除
};
```

ラジオ2件だけを消し、**`IDC_BUTTON_BROWSE` を巻き添えで消さないこと**。参照ボタンの無効化は 001 の analyze で HIGH として指摘し追加した項目であり、処理中にフォルダを変更されるとワーカースレッドの処理対象と画面表示が食い違う。DT-107 がこの誤りを検出する。

**(2) 検証チェーンの順序**（`ValidateBeforeGenerate`）

種別未選択のチェック（手順2）と不一致のチェック（手順4の一部）を削除するが、**残る手順の順序を変えないこと**。特に「書き込み権限の確認」が「マーカーの確認」より先である点は維持する。権限が無いフォルダでマーカーを探しても意味がないため。

**(3) 未選択エラーでボタンを無効化しない契約**

001 の contracts/ui-contract.md「2. ボタンの有効・無効の契約」で定めた「未選択エラーの経路で生成ボタンを無効化してはならない」は引き続き有効。DT-103 が検証する。
